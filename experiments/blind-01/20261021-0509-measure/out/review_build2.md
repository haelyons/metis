# Review of build 2 (m4), execution layer

Read: EXEC_NOTE.md, GATE_COMMIT.md (Pre-authorisation, Labels), run_m4.py (all 2,737 lines), onbox_m4.sh, lambda_run_m4.sh, remote_run_m4.sh, frozen/lambda_run.sh, frozen/remote_run.sh, frozen/provenance.py, out/selftest_build2.log, out/build2_return.json. Nothing run, nothing edited.

Checks that pass: checklist 3 (record convention, run_valid in every record, anchor record, RUN_VALID.json, m4_summary.json, anchor miss voids C1 to C4), 4 (nothing reads `.keys`, no environment dump, `env.txt` names variables only), 6 launcher (differs from frozen only at the declared points; terminate retry, EXIT trap, on_signal/BACKSTOP_ARMED, backstop, setsid, RUN_DONE poll, CRLF guard, unhealthy aborts, criticals-first fetch all intact), 6 remote (only the `cd` line and the comment on it differ), 7 (log ends `selftest: PASS`, 169 of 169, plausible for the planted cases present), 8 (`bash remote_run_m4.sh bash onbox_m4.sh` is what the launcher runs with RUNNER=onbox_m4.sh).

## BLOCKING

1. **BLOCKING. A guard or ceiling stop sets run_valid false.** run_m4.py:2244-2249 (`fail_stage`) calls `set_run_invalid` for every exit code. onbox_m4.sh calls `fail ... 3` at lines 109, 125, 133, 144, 147, 152, 158-160, 170 (no time left, stage hit its ceiling, generate hit the cap), so each of those writes `run_valid: false` into RUN_VALID.json, the summary and every record written after it. EXEC_NOTE item 29 and item 27: a guard stop does not set run_valid false; it voids the unfinished inputs and exits 3. Selftest has no case for `fail_stage` or the stage flow, so it did not catch this.

2. **BLOCKING. A time-guard or ceiling stop inside generate exits 0, not 3.** run_m4.py:1573-1576 (`stage_af2` returns early), 1517-1518 (`stage_aux` breaks), 1718-1719 (`stage_md` breaks). None raises `GuardStop`; the stage returns normally (and `af2` is not added to `stages_done`), the later stages run, `stage_endpoints` runs, and `run_stages` ends in `finish(state, EXIT_OK)` at 2237-2238. EXEC_NOTE items 27 and 29: a guard stop voids the unfinished inputs and exits 3. A run that stopped on its time guard with C1 or C2 unmeasured would report exit 0 and no early-stop label, and the A2(b) relaunch condition (stopped on its time guard with inputs unmeasured) would not be recognisable from RUN_DONE.

3. **BLOCKING. A timed-out AlphaFold or MD call is treated as broken infrastructure and voids everything.** run_tool (1052-1069) turns a timeout (`code = -9`) into `ToolError`. stage_af2 (1589-1611) passes `min(stage_left, seconds_left)` as the timeout and re-raises on any failed row; stage_md (1734-1744) does the same. `run_stages` (2227-2231) then marks the run not valid and `void_unmeasured` writes all four inputs VOID, including C3 (finished) and any finished AlphaFold or MD rows, because no endpoint record exists yet. The first estimate is a planning 700 s (1563) and the build's own expected run time is 600 to 900 s against a 2,100 s ceiling, so a third run overrunning its estimate is the expected case, not a corner. EXEC_NOTE items 28 and 29: a stage that hits its ceiling stops, its unfinished inputs are VOID, finished inputs keep their decisions, run_valid is untouched, exit 3.

4. **BLOCKING. REMOTE_TIMEOUT is not forwarded to the box.** lambda_run_m4.sh:168 forwards `PRICE_USD_PER_HOUR`, `BUDGET_LEFT_USD`, `INSTANCE_TYPE` but not `REMOTE_TIMEOUT` (it is used only in the local `timeout $REMOTE_TIMEOUT`). EXEC_NOTE Box ("forwarded env `PRICE_USD_PER_HOUR BUDGET_LEFT_USD REMOTE_TIMEOUT INSTANCE_TYPE`") and item 9. onbox_m4.sh:46 therefore always sees its default 7200. At the declared 7200 nothing changes; at any shorter launch cap (a second launch sized to the money left) the launcher kills the job at the shorter cap while the on-box guard still plans for 7200, so there is no clean stop and no void record. The header at lambda_run_m4.sh:3-5 declares only three added variables, so the omission matches the header but not the EXEC_NOTE.

5. **BLOCKING. Anchor overlap compares keys that cannot match unless the receptor chain id is "B".** run_m4.py:1408 builds `native_pairs` from `rec_atoms` carrying the entry's own chain id; the pose is re-read from a PDB (`read_pdb_atoms`, 1371) written with the receptor chain forced to "B" (1388, 1727 area, `write_pdb` chain_map). `contact_overlap` (1421) intersects (chain, resseq) keys, so any receptor chain id other than "B" gives overlap 0.0 regardless of the pose. Anchor then rests on the RMSD alternative alone. EXEC_NOTE item 21; a spurious miss is an exit 4, run_valid false, and A2 forbids relaunch after an anchor miss. The selftest tests overlap on hand-built key sets only (2387-2389), not the native-versus-pose round trip.

6. **BLOCKING. No check that the declared tools start before the expensive stages, and the install line is likely to fail late.** onbox_m4.sh:134-136 installs unpinned `colabfold[alphafold]`, `jax[cuda12]`, `openmm`, `lightdock`, then only `pip freeze`. run_m4.py:1662 requires the OpenMM CUDA platform; to the reviewer's recollection (not verified, nothing may be run) the PyPI `openmm` wheel does not carry the CUDA platform (that is `openmm[cuda12]` or conda), and a later unpinned `jax[cuda12]` can break `colabfold_batch` imports. `colabfold_batch` first starts at the AlphaFold stage (after docking) and OpenMM at the MD stage (last). A failure there is exit 2 after most of the 2 h is spent, and A2(a) only authorises a second launch for a halt before the anchor decision. EXEC_NOTE item 8 wants tool-start failures to stop the run; a version/platform smoke check in the install stage (import, `Platform.getPlatformByName("CUDA")`, `colabfold_batch --help`, `lightdock3.py --help`) would put that failure inside the install ceiling. Checklist 2: would spend money without producing a valid record.

## ADVISORY

7. **ADVISORY. HF_TOKEN reaches every subprocess.** lambda_run_m4.sh:168 (inherited from frozen) and remote_run_m4.sh:84-85 put the token in the environment; run_m4.py:1042 (`run_tool`) passes the whole environment to pip-installed tools, colabfold, lightdock and OpenMM. No download here uses it (urllib at 1081 sends no token). EXEC_NOTE item 5: `HF_TOKEN` is used by downloads only. Nothing prints it. `unset HF_TOKEN HUGGING_FACE_HUB_TOKEN` at the top of onbox_m4.sh would satisfy the item.

8. **ADVISORY. Docking and analysis have no stage ceiling.** EXEC_NOTE item 28 lists install 2,000, controls and anchor 700, AlphaFold 2,100, MD 1,800, endpoints 100, margin 500 = 7,200; aux (stage_aux, up to 3 x 600 s, 1522-1523) has no slot. The build's own expected shape (aux 200 to 600 s, anchor up to 600, install up to 1,800) leaves less than the AlphaFold and MD ceilings at the top of the ranges, so C1 or C2 can miss its minimum and be VOID. The 7,200 s cap itself is held by the outer timeouts and `STOP_AT`.

9. **ADVISORY. "incomplete run" label missing.** GATE_COMMIT Labels: records from an early-stopped run are labelled "incomplete run: unmeasured inputs are VOID, not holding". run_m4.py has only `LABEL_UNMEASURED = "unmeasured, not holding"` (line 182); grep for "incomplete run" finds nothing. EXEC_NOTE item 28 names only the shorter text, which is carried.

10. **ADVISORY. "Interface backbone RMSD" is the whole receptor chain.** run_m4.py:1409 and 1423 take all N, CA, C, O of the receptor chain with no superposition, not the interface residues. Stricter than the gate's readout (item 21); the label overstates what is computed.

11. **ADVISORY. `sudo -n apt-get` does not keep DEBIAN_FRONTEND.** onbox_m4.sh:113-118 exports it inside `bash -c`, but sudo resets the environment by default. Use `sudo -n env DEBIAN_FRONTEND=noninteractive apt-get ...`. Stdin is /dev/null under the launcher, so the likely effect is none.

12. **ADVISORY. Outer `timeout` stops only run_m4.py.** onbox_m4.sh:153-164 on rc 124: a running `colabfold_batch` or the OpenMM worker survives and keeps the GPU while the endpoints stage runs. The inner guard's tool timeout (`seconds_left` = stop_at minus elapsed minus 500, run_m4.py:877) also outlasts the outer kill (stop_at minus elapsed minus 600), so the outer one fires first and routes into finding 1.

13. **ADVISORY. Wheel URLs and hashes are not recorded.** EXEC_NOTE items 7 and 14: each URL and sha256 recorded. The two direct downloads are (run_m4.py:1085-1087); pip and apt packages are recorded as versions only (`pip freeze`, `package_version`).

14. **ADVISORY. Build return does not match the files.** build2_return.json says run_m4.py is 1,650 lines and onbox_m4.sh 150; the files are 2,737 and 176. The selftest log therefore may not be of the files as they stand (the log has no hash). Checklist 7: counts plausible, provenance of the log unverified.

15. **ADVISORY. Selftest does not exercise the stage flow.** `run_stages`, `fail_stage` and the stage functions' guard returns have no planted case; items 27 and 29 are tested at function level only (guard_check, void_unmeasured, decide_*). Findings 1 to 3 sit in the untested layer.
