## Card calibration (U54)
- Purpose: a calibration run measures a tree card's load-bearing GUESS and PROXY inputs on the card's own protocol, and the measured values return to the card. Owner approval 2026-11-03 (contract gap G2 of the blind-02 science route): the tree's calibration record names those inputs, but nothing passed the record to an m5 run or wrote a measurement back, so a run's result could not be read against the card's value. A measured input that does not hold refutes the card's value; that is a result and never fails a stage. Science checks s10 and s11 (2026-11-03) fixed the rest: no agent of the run sees the card's values, bands, gate thresholds, predictions or anchor value; how each input is read from the run's output is fixed before the workload runs and applied by the pipeline, not by a harness script; the card record is sealed before any box command; where the card sets a gate on an input, the gate decides it. Without `args.card`, every stage is unchanged.
- Optional `args.card` is an object with exactly the keys `result` and `key`, and optionally `bands`. `result` is a non-empty path, resolved relative to the pipeline working directory, to a tree run's `result.json`; `key` is a non-empty string. The card's record is the entry of that file's `calibration` array whose `key` equals `key`. It must have `state` `"calibration_required"` and a non-empty `required` array whose items each have a unique string `id` matching `^[a-z][a-z0-9_]{0,30}$` and `basis` `"GUESS"` or `"PROXY"`. `bands`, when present, maps some of those ids to `{"abs": x}` with `x` a finite number above 0: absolute bands fixed before the run by whoever launches it, for inputs a multiplicative band cannot judge. An invalid `args.card`, a missing or unreadable file, invalid JSON, no matching record, any other state, an invalid `required` or `bands`, or `args.card` together with `args.units_check` or `args.units_probe` fails intake with `error_class: parse` before any agent call.
- Optional `args.pipeline_commit` is a string naming the commit of the pipeline copy the run executes; `launch.js` writes it into every m5 `args.json` (the short commit it already records in RUN.md, or null when unknown). It changes no behaviour.
- Before the intake agent call and any box command, the pipeline writes, atomically and in this order: `C/card.json`, exactly `{source, source_sha256, record, bands}` (`source` the absolute path of `result`, `source_sha256` the lowercase hexadecimal SHA-256 of its exact bytes, `record` the matching record unchanged, `bands` the launch bands or `{}`); `C/card_seal.json`, exactly `{card_sha256, sealed_utc}` (the SHA-256 of the exact bytes of `C/card.json` and a UTC ISO time); and `A/card_inputs.json`, exactly `{inputs, anchor}`. `inputs` has one entry per `required` item in order, each exactly `{id, name, unit, measured_by, phase}`, with `phase` the item's `phase.what` or null and `name`/`unit` null when absent. `anchor` is `{"what": <the record anchor's what>}` when the record's anchor has a finite numeric `published_value`, otherwise null. `A/card_inputs.json` holds no value, basis, band, gate, cost line, budget, prediction or published value. Every later read of the card uses `C/card.json`, never `result`.
- Agents see only `A/card_inputs.json`. Card-mode prompts name it and never name `C/` or `result`; the existing rule that agents never read `control/` stands. Intake prompt, card mode only: this run calibrates the listed inputs, and EXECUTION.json's representative workload is the protocol of the phases they name (their `measured_by` and `phase`), not another workload. Harness prompt, card mode only: the representative run must write outputs from which each listed input, and the anchor quantity when `anchor` is non-null, can be read, and the harness agent declares in `harness/card_extract.json` how each one is read; no harness script computes, writes or asserts a card value.
- `A/harness/card_extract.json` is exactly `{"rules": [...]}`: one rule per `inputs` entry in order, then one rule with id `"anchor"` when `anchor` is non-null. Each rule is exactly `{id, file, kind, expr}`. `file` is a relative path under the run's `out/`, one or more `/`-separated components made of `[A-Za-z0-9._+=-]`, none `.` or `..`. `kind` `"json"`: `expr` is a JSON Pointer (RFC 6901) into that file, and the value there must be a finite JSON number (never a boolean). `kind` `"regex"`: `expr` is a Python `re` pattern with exactly one capturing group; the file is read as UTF-8 with replacement, the last match's group is parsed with `float()` and must be finite. With `args.harness_from`, the source harness directory must also hold `card_extract.json`, copied like the other scripts. It then writes `C/card_extract_seal.json`, exactly `{extract_sha256, sealed_utc}`. No repair changes `card_extract.json`.
- Scoring: after `run_anchors.sh` exits 0 and its output gate passes, before anchor scoring and whatever the anchors score, the pipeline runs `python3 -I m5/score_card.py <C dir> <A/harness/card_extract.json> <A/results/reproduce/out dir> --run <run tag> --commit <pipeline_commit, or - when null>`. The script first checks the SHA-256 of `C/card.json` against `C/card_seal.json` and that of `card_extract.json` against `C/card_extract_seal.json`; then applies each rule to the fetched outputs (a missing or unreadable file, no match, or a value that is not a finite number gives null); then writes `C/card_scored.json` atomically, exactly `{key, run, pipeline_commit, box_type, box_started_utc, card_sha256, extract_sha256, predictions, anchor, rows, inputs_total, measured_total, holds_total, refuted_total}`. `box_type` and `box_started_utc` come from `C/box.json` (`type`, `started_utc`), null when unavailable; `pipeline_commit` is null for `-`; `predictions` is the record's `predictions` unchanged (null when absent).
  - `anchor` is null when `A/card_inputs.json` has no anchor; otherwise exactly `{published_value, tolerance, measured_value, difference, passed}`: `published_value` and `tolerance` copy the record anchor's; `difference` is measured minus published, null when unmeasured; `passed` is `abs(difference) <= t` for a finite nonnegative numeric tolerance `t` or `{"abs": t}`, `abs(difference) <= t * abs(published_value)` for `{"rel": t}`, and null for any other tolerance or when unmeasured. The anchor never decides an input.
  - `rows` follows `required` order, one row per item, each exactly `{id, name, unit, basis, value, band_source, band_lo, band_hi, measured_value, verdict, gate_passed, decided_by, decision, rule}`. `name` and `unit` copy the item's (null when absent); `basis` and `value` copy the item's; `rule` is the item's extraction rule without its `id`.

  - `gate_passed` is null unless the item's `phase.gate` is an object whose `on` equals the item's `id`, whose `op` is `">="` or `"<="` and whose `value` is a finite number, and `measured_value` is a number; then it is the boolean `measured_value <op> gate.value`.
  - `decided_by` is `"gate"` when `gate_passed` is a boolean, otherwise `"band"` when `verdict` is `within_band`, `below_band` or `above_band`, otherwise null. `decision` is `"holds"` or `"refuted"` by the gate (`gate_passed` true or false) when it decides, otherwise by the band (`within_band` holds; `below_band` and `above_band` refute); `"not_measured"` when unmeasured; `"undecidable"` when measured with neither a gate nor a band.
