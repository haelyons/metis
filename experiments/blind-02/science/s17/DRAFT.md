## Sealed comparison (U57, U58)
- Purpose: compare several published arms on one box under a design fixed before the run. Owner approval 2026-11-03 (contract gaps G1 comparison arms, G3 tolerance and equivalence, G6 compute metadata of the blind-02 science route); requirements from science steps s13 to s17. Arms are published programs or configurations that need no new code. Each invocation runs one arm on one input, and invocations are interleaved on one box. No agent computes a number: every number comes from the pipeline's trusted wall time, from rules fixed before the run and applied by the pipeline, from a trusted comparator of two arms' outputs, or from a published evaluator that the pipeline runs on each arm's output without naming the arm. Criteria, margins, thresholds, reference values and timeouts are fixed by a science step before the run, sealed, and unreadable by the run's agents. Compute is recorded twice and never mixed: per invocation as attribution (the arm's own subprocesses only) and per box allocation as the bill. Never change a criterion after a result: every decision uses the sealed design. An outcome that is not supported is a result and never fails a stage. Comparisons that need more than one run are split by the science step into one design per run; a design whose launch depends on an earlier run's outcomes is launched only when the science step finds them in that run's `C/comparison_scored.json`. Without `args.comparison`, every stage is unchanged.
- Optional `args.comparison` is an object with exactly the key `design`: a non-empty path, resolved relative to the pipeline working directory, to a design JSON file. It is exclusive with `args.card`, `args.units_check` and `args.units_probe`. The design is exactly `{arms, inputs, outputs, metrics, evaluator, replicates, warmup, order_seed, timeout_s, budget_s, bootstrap_seed, bootstrap_resamples, comparisons}`:
  - `arms`: 2 to 5 items, each exactly `{id, what, commands, env}`; ids `"A0"`, `"A1"`, ... in order; `what` a non-empty string. `A0` is the published baseline that intake and reproduce handle as usual.
    - `commands`: null, or 1 to 8 commands, each a non-empty array of non-empty strings: the exact published command lines of the arm, in order, as argument vectors run without a shell. When non-null, the pipeline runs them itself (see Evaluate) and the arm's adapter only prepares.
    - `env`: null or an object mapping names that match `^[A-Z_][A-Z0-9_]{0,63}$` and do not start with `CMP_` to strings; set for the arm's commands.
    - Placeholders, in command and `env` strings only: `{input}` (the input id), `{run}`, `{out}` (the absolute paths of the invocation's `run/` and `out/`) and `{spec:<p>}` with `<p>` a JSON Pointer (RFC 6901) into the input's `spec`, which must resolve in every input's `spec` to a string (inserted as is) or a finite number (inserted as `json.dumps` writes it). `{{` and `}}` stand for literal braces; any other `{` or `}` makes the design invalid. Substitution replaces every occurrence and is not repeated on its result.
  - `inputs`: 1 to 10 items, each exactly `{id, spec}`: `id` a unique string matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`; `spec` any JSON value (pins, case, configuration).
  - `outputs`: 0 to 10 items, each exactly `{name, what, format, select}`: a logical result each arm, or the evaluator, writes for an input, compared across arms. `name` unique, matching `^[a-z][a-z0-9_]{0,30}$`; `what` a non-empty string; `format` `"bytes"`, `"text_numbers"` (every number in the file's UTF-8 text, in order, as matched by `[-+]?(\d+\.?\d*|\.\d+)([eE][-+]?\d+)?` together with `nan`, `inf` and `-inf` tokens) or `"json_numbers"` (every number leaf of the JSON document, in document order; booleans are not numbers). `select` is null (the whole content) or, for `bytes` and `text_numbers` only, a Python `re` pattern with at least one capturing group: the content is read as UTF-8 with replacement, and the selected content is every group of every match of `re.finditer(select, text, re.MULTILINE)`, in order (an unmatched group as the empty string), joined by `"\n"`; `format` then applies to the selected content (`bytes` to its UTF-8 encoding). Several outputs may select different parts of the same file, each with its own comparison and tolerance.
  - `metrics`: 1 to 10 items, each exactly `{name, unit, what, source, scope, reduce, expect_count}`: `name` unique, matching `^[a-z][a-z0-9_]{0,30}$`; `unit` and `what` non-empty strings; `source` `"trusted_wall"` or `"sealed_extraction"`.
    - `trusted_wall`: `scope` `"commands"` (the summed wall seconds of the arm's commands; every arm must have non-null `commands`), `"invocation"` (the adapter's wall plus its commands' walls) or `"invocation_and_evaluator"` (that plus the evaluator's wall; needs a non-null `evaluator`). `reduce` and `expect_count` are null.
    - `sealed_extraction`: read from fetched files by a rule the harness agent fixes before the run, reduced as the design states. `scope` null; `reduce` `"last"`, `"first"`, `"min"`, `"max"`, `"mean"`, `"value_at_max_key"` or `"value_at_min_key"`; `expect_count` null or a positive integer, the number of matched values the rule must find.
  - `evaluator`: null or exactly `{what, spec, timeout_s}`: a published, pinned program that reads one arm's output for one input, with data that only it may read, and writes evaluation files. `what` a non-empty string; `spec` any JSON value (program, pin, command, and where its private data come from); `timeout_s` null or a positive integer.
  - `replicates` an integer from 1 to 30; `warmup` an integer from 0 to 3; `order_seed` and `bootstrap_seed` integers; `bootstrap_resamples` an integer from 1000 to 1000000; `budget_s` a positive integer, the evaluate stage's time budget for this comparison. When `args.run_ceiling_s` is present, `budget_s` must be below it.
  - `timeout_s`: null, a positive integer for every invocation, or an object mapping every arm id to a positive integer or to an object mapping every input id to a positive integer: the cap of one invocation's arm part.
  - `comparisons`: 1 to 12 items, each exactly `{id, arm, against, measure, criterion, direction, unit, pairing, rule, confidence, margin, threshold, strict, reference, missing, given, parts}`:
    - `id` unique, matching `^K[0-9]{1,2}$`; `arm` an arm id; `against` a different arm id or `"reference"`; `parts` a non-empty array of unique non-empty strings.
    - `measure` is exactly `{metric}` (a metric name) or exactly `{output, comparator}` (an output name and one of `"exact"`, `"elementwise_abs"`, `"elementwise_rel"`, `"elementwise_abs_plus_rel"`, `"elementwise_abs_plus_rel_max"`). An output comparison needs an arm as `against`.
    - `criterion` `"equivalence"`, `"non_inferiority"`, `"superiority"`, `"ratio_at_least"` or `"agreement"`. `agreement` is the criterion of every output comparison and of no metric comparison.
    - `direction` `"higher_better"`, `"lower_better"` or `"two_sided"`: the metric as measured (for wall seconds, `lower_better`). `equivalence` and `agreement` use `two_sided`; `non_inferiority` and `ratio_at_least` use `higher_better` or `lower_better`; `superiority` takes any.
    - `unit` `"pooled_mean"` (each replicate's value is the mean over inputs, decided once), `"per_input_all"` (decided per input; the comparison holds only if it holds on every input) or `"per_input_each"` (decided and reported per input). `ratio_at_least` uses `pooled_mean`.
    - `pairing` `"paired_replicate"` or `"unpaired"`; output comparisons use `paired_replicate`.
    - `rule` `"all_pairs"` or `"bootstrap"`; `confidence` a number in `[0.5, 1)` for `bootstrap` and null for `all_pairs`. Output comparisons use `all_pairs`.
    - `margin`: null, `{"abs": x}`, `{"rel": y}` or `{"abs": x, "rel": y}` with `x` and `y` finite and nonnegative. For an output comparison it is the comparator's tolerance: `elementwise_abs` needs `abs`, `elementwise_rel` needs `rel`, `elementwise_abs_plus_rel` and `elementwise_abs_plus_rel_max` need both, `exact` needs null. For a metric comparison it is null, `abs` or `rel`; `rel` scales by `abs(reference)` against a reference, else by `abs(mean of the against arm's values)` for the same unit.
    - `threshold`: a finite number above 0 for `ratio_at_least`, otherwise null. `strict`: a boolean for `ratio_at_least` (true: the bound must exceed `threshold`; false: it may equal it), otherwise null.
    - `reference`: exactly when `against` is `"reference"`, an object `{source, values}`: `source` a non-empty string naming where the values come from (for example an earlier run of this route and the rule that derived them), `values` mapping every input id to a finite number; otherwise null.
    - `missing`: `"drop"`, `"void"` or `"fail"`, how a missing value is decided (see Scoring). `agreement` uses `void` or `fail`.
    - `given`: an array, possibly empty, of unique ids of comparisons that come earlier in `comparisons`; a decision unit is decided only when each of them is supported for it (see Scoring).
  An invalid argument or design, or a path that cannot be read as JSON, fails intake with `error_class: parse` before any agent call.
- Before the intake agent call and any box command, the pipeline writes atomically, in this order: `C/comparison.json`, exactly `{source, source_sha256, design}`; `C/comparison_seal.json`, exactly `{comparison_sha256, sealed_utc}` (the SHA-256 of the exact bytes of `C/comparison.json`); and `A/comparison_view.json`, exactly `{arms, inputs, outputs, metrics, evaluator, replicates, warmup}` copied from the design, with `evaluator` reduced to `{what, spec}` (null when the design's is null). The view holds no comparison, criterion, margin, threshold, reference value, timeout, part, seed or budget. Agents see only the view; comparison-mode prompts name it and never `C/` or the design path. The science step that writes the design is responsible for the view's free text (`what`, `spec`, `select`) stating no expectation, criterion or result.
- Isolation, comparison mode only: every agent call of the run (intake, harness, and every setup and anchors repair) is dispatched with wf `isolation` (see Implement), `box_access` false, and `hidden` containing at least the run's absolute `C/` directory and the design's absolute path. A call that cannot be dispatched so fails as an isolation failure does; there is no fallback. Agents therefore cannot read criteria, margins, thresholds, references or timeouts from files, not only from prompts.
- Intake prompt, comparison mode only: the run compares the view's arms on the view's inputs; `A0` is the benchmark intake records as usual; intake also records, in `benchmark.json` under the key `arms`, each other arm's published source, pin and commands, under the key `evaluator` the evaluator's published source, pin and command when the view has one, and in `data.json` every input any arm or the evaluator needs, marking the evaluator's private data.
- Harness prompt, comparison mode only: `setup.sh` also builds or installs every arm's published program and configuration, and the evaluator, as published. `setup.sh` places every file only the evaluator may read under the top-level directory `cmp-private/` of the shared run directory and nowhere else. The harness agent writes, besides the usual scripts:
  - one adapter `harness/arms/<arm id>.sh` per arm, `A0` included. For an arm with `commands`, the adapter only prepares the invocation (stages the input named by `CMP_INPUT` under `run/` or `CMP_OUT`) and does not run the arm's program; the pipeline runs the commands. For an arm without `commands`, the adapter runs that arm's published program and configuration on that input and writes its results under `CMP_OUT`. Adapters never write or patch source, never compute, write or assert a metric, and never name `cmp-private` or `CMP_PRIVATE`;
  - when the view has an evaluator, `harness/evaluate.sh`, which runs the published, pinned evaluator on the arm output in `CMP_ARM_OUT` for the input named by `CMP_INPUT`, reads private data only under `CMP_PRIVATE`, writes its results under `CMP_EVAL_OUT`, and never writes under `CMP_ARM_OUT`;
  - `harness/cmp_files.json`, exactly `{"files": {...}}`, mapping each arm id to an object that maps every output name to a location: a relative path, or exactly `{glob, order}` with `glob` a pattern of relative-path components that may also use `*`, `?`, `[` and `]`, and `order` `"lexical"` or `"natural"`. Locations are relative to the invocation directory, and their first component is `out` (the arm's files) or `eval` (the evaluator's files);
  - `harness/cmp_extract.json`, exactly `{"rules": [...]}`, one rule per arm and `sealed_extraction` metric, each exactly `{arm, metric, file, kind, expr}`, with `file` a relative path whose first component is `out` or `eval`, and `kind` and `expr` as defined for `harness/card_extract.json` (U54), extended by the metric's `reduce`: `kind` `"json"`: `expr` points to a finite number, to an array of finite numbers, or (for `value_at_max_key` and `value_at_min_key`) to an array of two-element arrays `[key, value]` of finite numbers; `kind` `"regex"`: exactly one capturing group, or exactly two (key, then value) for `value_at_max_key` and `value_at_min_key`;
  - `harness/versions.sh`, which prints one JSON object mapping each arm id, and `"evaluator"` when the view has one, to exactly `{version, executable}`: the program's version string and the path, absolute or relative to the shared run directory, of its main executable file.
  Relative paths are one or more `/`-separated components made of `[A-Za-z0-9._+=-]`, none `.` or `..`. `run_anchors.sh` and `run_command.sh` keep their meaning for `A0`.
- After harness generation or copy (with `args.harness_from`, the source directory must also hold `arms/`, `cmp_files.json`, `cmp_extract.json`, `versions.sh` and, when the design has an evaluator, `evaluate.sh`, copied like the scripts) and before the harness upload, those files must exist and be valid: `harness/arms/` holds exactly one non-empty adapter per arm; `evaluate.sh` exists exactly when the design has an evaluator; `cmp_files.json` maps every arm and every output, with `eval` locations only when the design has an evaluator; `cmp_extract.json` has exactly one rule per arm and `sealed_extraction` metric, whose group count matches the metric's `reduce`; and no adapter's bytes contain `cmp-private` or `CMP_PRIVATE`. Otherwise reproduce fails with `error_class: parse` before the upload. The pipeline then writes `C/arms_seal.json`, exactly `{files, sealed_utc}`, mapping each of those files' names (adapters as `arms/<id>.sh`) to the SHA-256 of its bytes. They upload with the harness, in the same encoding. No repair changes them.
- In comparison mode reproduce runs exactly as usual for `A0`. Profile, seal, propose and implement are SKIPPED. Evaluate runs the comparison when reproduce passed, and is SKIPPED otherwise, as after any failed gate.
- Evaluate, comparison mode (U57):
  - Versions: one box command, operation `versions`, runs `bash harness/versions.sh` with stdout to `out/comparison/versions.json`, then the trusted `python3 profiler/cmp_system.py` (written inline by the pipeline) writes `out/comparison/system.json`, exactly `{cpu_model, cpu_logical, kernel, driver_version, cuda_version, gpus, executables}`: `lscpu` model name and logical CPU count; `uname -r`; the driver and CUDA versions that `nvidia-smi` reports; `gpus` one row per GPU, exactly `{index, name, uuid, memory_total}`, from `nvidia-smi --query-gpu=index,name,uuid,memory.total --format=csv,noheader`; and `executables` mapping each key of `versions.json` to exactly `{version, executable, sha256, libraries}`, with `sha256` the SHA-256 of the executable's resolved file and `libraries` one row per `ldd` line of the form `<name> => <absolute path> ...`, exactly `{name, path, sha256}` (the resolved file's SHA-256), or `[]` when `ldd` fails or reports a static executable. Any field that cannot be read is null.
  - Rounds: `warmup` warmup rounds, then `replicates` replicate rounds. Each round runs every (arm, input) pair once, in an order drawn from one `random.Random(order_seed)` stream: one `shuffle` of the round's pairs per round, warmups included.
  - Each invocation is one box command, operation `comparison`, from the shared run directory. It builds a fresh invocation directory `comparison-work/<w<k> or r<k>>/<arm>/<input>/` holding `run/` (a symbolic link to every top-level entry of the shared run directory except `out`, `profiler`, `concurrency-work`, `evaluation-work`, `units-check`, `comparison-work` and `cmp-private`), an empty `out/` and an empty `eval/`, then runs the trusted wrapper `python3 profiler/cmp_wrap.py` (written inline by the pipeline, as the profile stage writes its probe). The wrapper:
    1. sets the mode of `cmp-private`, when it exists, to `000`;
    2. arm part: runs `bash harness/arms/<arm>.sh` with working directory `run/`; then, when the adapter exits 0 and the arm has `commands`, runs each command in order with working directory `run/`, after placeholder substitution, with its standard output and error written to `out/cmd<k>.stdout` and `out/cmd<k>.stderr` (`k` from 1), stopping at the first nonzero exit. A first argument containing `/` resolves relative to `run/`, otherwise through `PATH`. The arm's `env` applies to its commands;
    3. restores the mode of `cmp-private` to `700`; when the mode was not `000` just before the restore, the invocation is `invalid`;
    4. evaluator part, only when the design has an evaluator and the arm part's status is `ok`: runs `bash harness/evaluate.sh` with working directory `run/`;
    5. writes `wrap.json` in the invocation directory, atomically and last, exactly `{status, adapter_rc, adapter_wall_s, commands, gpu_busy_s, gpu_busy_known, eval_status, eval_rc, eval_wall_s, eval_gpu_busy_s, eval_gpu_busy_known}`. `status` is `"ok"` (the adapter and every command exited 0), `"failed"` (a nonzero exit), `"timeout"` or `"invalid"`; `commands` has one row per command started, exactly `{argv, rc, wall_s, executable, sha256}` (the substituted argument vector, exit status, `perf_counter` wall seconds, the resolved executable path and its SHA-256, null when unresolved); `eval_status` is `"ok"`, `"failed"`, `"timeout"` or `"skipped"` (no evaluator, or the arm part was not `ok`). Walls are `perf_counter` seconds and exit statuses null on timeout. GPU-busy seconds are sampled separately for the arm part and the evaluator part (`nvidia-smi --query-gpu=utilization.gpu` immediately and every second; each finite sample in [0,100] contributes `utilization / 100` seconds, summed over GPUs; the matching `known` flag is false when no valid sample was taken).
    The environment of the adapter and the commands carries `CMP_ARM`, `CMP_INPUT` (the input id), `CMP_INPUT_SPEC` (the JSON of that input's `spec`), `CMP_MODE` (`warmup` or `replicate`), `CMP_ROUND` (the index) and `CMP_OUT` (the absolute path of `out/`). The evaluator's environment carries `CMP_INPUT`, `CMP_INPUT_SPEC`, `CMP_MODE`, `CMP_ROUND`, `CMP_ARM_OUT` (the absolute path of `out/`), `CMP_EVAL_OUT` (the absolute path of `eval/`) and `CMP_PRIVATE` (the absolute path of `cmp-private`), and never the arm id. The invocation's `out/`, `eval/` and `wrap.json` are fetched to `A/results/evaluate/comparison/<w<k> or r<k>>/<arm>/<input>/`.
  - Timeouts: the arm part's timeout is the smallest of its `timeout_s` (when non-null), the time left in `budget_s`, and the time left before the run ceiling; the evaluator part's is the smallest of `evaluator.timeout_s` (when non-null) and the same two. On a timeout the wrapper kills the part's whole process group and records `"timeout"`. When the time left in `budget_s` is below 1 s, the remaining invocations are not run, and their status is `"not_run"`. A missing or invalid `wrap.json` gives status `"invalid"`.
  - Values: for an invocation with status `ok`, a `trusted_wall` metric is, by `scope`, the sum of its commands' `wall_s` (`commands`), `adapter_wall_s` plus that sum (`invocation`), or that plus `eval_wall_s` (`invocation_and_evaluator`, null unless `eval_status` is `ok`). A `sealed_extraction` metric is its rule applied to the fetched file: the matched values are every `float()`-parsed match of the regex in order, or the number or array at the pointer. With `reduce` `last`, `first`, `min`, `max` or `mean`, the value is that function of the matched values; with `value_at_max_key` or `value_at_min_key`, it is the value of the first pair whose key is the largest or smallest. A file under `eval` needs `eval_status` `ok`. A missing or unreadable file, no match, a nonfinite matched number, or a match count other than a non-null `expect_count` gives null. Every value of an invocation with any other status is null. A null value is a missing value.
  - Compute (G6): `A/results/evaluate/comparison_compute.json`, written atomically after the last invocation, is exactly `{invocations, arms, all_invocations, system, versions, allocation}`.
    - `invocations` has one row per scheduled invocation in run order, each exactly `{round, arm, input, status, wall_s, gpu_busy_s, gpu_busy_known, eval_status, eval_wall_s, eval_gpu_busy_s, attributed_usd}`, from `wrap.json`: `wall_s` is `adapter_wall_s` plus the commands' walls, and `attributed_usd` is `(wall_s + eval_wall_s) / 3600 * C/box.json.price_usd_h`, with a null wall counted as 0 and null when the price is unavailable. Rows of `not_run` invocations have null numbers.
    - `arms` has one row per arm, each exactly `{arm, invocations, wall_s, gpu_busy_s, gpu_busy_known, eval_wall_s, eval_gpu_busy_s, attributed_usd}`, summed over that arm's replicate invocations whatever their status, with a null counted as 0; `gpu_busy_known` is true only when every summed row's flag is.
    - `all_invocations` is exactly `{invocations, wall_s, eval_wall_s, attributed_usd}`, summed over every row, warmups and failures included, with a null counted as 0.
    - `system` and `versions` copy the fetched `system.json` and `versions.json` (null when missing or invalid).
    - `allocation` is the bill of the whole box allocation, which may include work outside this run, exactly `{type, price_usd_h, started_utc, ended_utc, hours, usd, final}` from `C/box.json`. When that record has `ended_utc` and `hours`, they are copied and `final` is true; otherwise `ended_utc` is null, `hours` is the time from `started_utc` to when the file is written, and `final` is false. `usd` is `hours * price_usd_h`. Unavailable fields are null. At takeaways, after a matching allocation record refreshes `C/box.json` (see Compute metadata), the pipeline rewrites the file atomically with only `allocation` recomputed. The run's own share stays `run_box_usd`.
    Uploads, links and fetches are outside every invocation row; they remain in the stage's receipts.
- Scoring (U58): after the last invocation, `python3 -I m5/score_comparison.py <C dir> <A/results/evaluate/comparison dir> <A/harness dir> <C/comparison_scored.json>`. It checks the SHA-256 of `C/comparison.json` against `C/comparison_seal.json` and of each sealed harness file against `C/arms_seal.json`, then scores each comparison, in design order, from the replicate rounds only.
  - Locations: a relative path names one file. A `{glob, order}` location names the regular files that Python `glob.glob(glob, root_dir=<invocation dir>)` returns, sorted by their relative path (`lexical`), or by a key that splits the relative path into runs of digits and non-digits, compares digit runs as integers and breaks ties by the path (`natural`); their contents, each after `select`, are joined by `"\n"` (by `b"\n"` for `bytes`). A side of an (input, replicate) pair is missing when its invocation's status is not `ok`, when the location is under `eval` and `eval_status` is not `ok`, when the location names no file or an unreadable one, when the content cannot be parsed as the output's `format`, or when the selected content is empty (no bytes for `bytes`, no numbers otherwise).
  - Output comparisons (`agreement`): for each input and replicate where neither side is missing, the comparator compares the two contents. `exact`: identical bytes. Otherwise both contents are parsed as the output's `format` into number lists; different lengths, or a NaN in one list but not at the same position in the other, disagree; equal infinities agree; finite pairs agree when `abs(a - b) <= abs_tol` (`elementwise_abs`), `abs(a - b) <= rel_tol * abs(b)` (`elementwise_rel`, `b` the `against` arm's element), `abs(a - b) <= abs_tol + rel_tol * abs(b)` (`elementwise_abs_plus_rel`) or `abs(a - b) <= abs_tol + rel_tol * max(abs(a), abs(b))` (`elementwise_abs_plus_rel_max`). A pair agrees when every element agrees. Each compared pair records `max_abs_error` and `max_rel_error` over its finite elements (null when none).
  - Metric comparisons: an arm's value for (replicate, input) is the metric value above. For `pooled_mean`, a replicate's value is the mean over inputs, null when any input's value is null. The statistics are, per decision unit (the pooled value, or each input), over the replicates where the values they need are present: for `paired_replicate`, the difference `arm - against` per replicate where both have values (or `arm - reference value`); for `unpaired`, the differences of every arm value with every against value (or with the reference value). `ratio_at_least` uses the ratio of means `mean(arm) / mean(against)` for `higher_better` and `mean(against) / mean(arm)` for `lower_better`, over the replicates where both have values. For `pooled_mean` against a reference, the reference value is the mean of `values` over inputs.
  - Missing values, per decision unit: `n_missing` counts the arm's missing values and, against an arm, the against arm's (for `pooled_mean` a replicate counts once; for agreement a pair with a missing side counts once). With `missing` `"drop"`, they are left out as above. With `"void"`, any missing value makes the unit void with reason `"missing_values"`. With `"fail"`, a missing value of `arm` makes the unit `"not_supported"` with reason `"missing_values"`, and otherwise a missing value of `against` makes it void with reason `"missing_values"`.
  - Eligibility (`given`): for each listed comparison, its outcome for this unit is that comparison's row for the same input when both comparisons are decided per input, and otherwise that comparison's outcome, where `"per_input"` counts as supported only when every row is. When any of these is not `"supported"`, the unit is void with reason `"not_eligible"`.
  - Interval: for `all_pairs`, `[lo, hi]` is the minimum and maximum of the differences (for a ratio, of the per-replicate ratios in the same orientation), and needs at least one difference. For `bootstrap`, the statistic (the mean difference, or the ratio of means) is recomputed on `bootstrap_resamples` resamples (`B`) with replacement of the unit's paired replicates (for `unpaired`, of each arm's values separately), drawn from one `random.Random(bootstrap_seed)` stream in comparison order, and `[lo, hi]` is the `(1 - confidence) / 2` and `(1 + confidence) / 2` empirical quantiles (sorted resamples, index `floor(q * (B - 1))`); it needs at least two replicates. `estimate` is the statistic on the full data. Too few values gives outcome `"void"` with reason `"insufficient_replicates"`; no values at all gives reason `"missing_values"`.
  - Margin value `m`: 0 for a null margin, `x` for `{"abs": x}`, and for `{"rel": y}` `y * abs(reference value)` or `y * abs(mean of the against arm's values in the unit)`.
  - Outcome per decision unit, in this order: eligibility; then, for agreement, any compared pair that disagrees makes the unit not supported; then the missing-value rule; then the interval's minimum count; then the criterion. The criterion gives `"supported"`, `"not_supported"` or else `"inconclusive"`: agreement is supported when at least one pair was compared, every compared pair agrees and none is missing (with no compared pair, it is void with reason `"missing_values"`); equivalence is supported when `-m <= lo` and `hi <= m`, not supported when `hi < -m` or `lo > m`; non-inferiority (`higher_better`) is supported when `lo >= -m`, not supported when `hi < -m`; non-inferiority (`lower_better`) is supported when `hi <= m`, not supported when `lo > m`; superiority (`higher_better`) is supported when `lo > m`, not supported when `hi <= m`; superiority (`lower_better`) is supported when `hi < -m`, not supported when `lo >= -m`; superiority (`two_sided`) is supported when `lo > m` or `hi < -m`, not supported when `-m <= lo` and `hi <= m`; ratio with `strict` false is supported when `lo >= threshold`, not supported when `hi < threshold`; ratio with `strict` true is supported when `lo > threshold`, not supported when `hi <= threshold`.
  - `sign` of a unit is `"higher"` when a `two_sided` superiority is supported with `lo > m`, `"lower"` when it is supported with `hi < -m`, and null otherwise.
  - A comparison's outcome: for `pooled_mean`, its one unit's outcome; for `per_input_all`, supported when every input is supported, not supported when any input is not supported, void when any input is void and none is not supported, otherwise inconclusive; for `per_input_each`, `"per_input"`, with each input's outcome in its rows.
  - `C/comparison_scored.json`, atomic, is exactly `{comparison_sha256, comparisons, totals}`. `comparisons` follows the design's order, each exactly `{id, arm, against, criterion, unit, outcome, rows}`; `rows` has one row per decision unit (`input` null for `pooled_mean`), each exactly `{input, n, n_missing, estimate, lo, hi, margin_value, threshold, outcome, sign, reason, pairs}`. `n` counts the differences, ratios or compared pairs; `pairs` is null for metric comparisons and, for agreement, the per-replicate rows `{replicate, agrees, missing, max_abs_error, max_rel_error}` (`agrees` null and `missing` true when a side is missing). Numbers are null when void; `reason` is `"missing_values"`, `"insufficient_replicates"` or `"not_eligible"` for a void unit, `"missing_values"` for a unit made not supported by the `"fail"` rule, and null otherwise. `totals` is exactly `{supported, not_supported, inconclusive, void}`, counting decision units over all comparisons.
  - Exit 0 after writing; exit 1 for invalid or missing input, a seal mismatch or a failed write, with no output file. A missing or invalid `wrap.json` or fetched file is not invalid input; it is a missing value. Diagnostics contain no input content. A scoring failure fails evaluate with `error_class: parse`.
- Evaluate status in comparison mode is PASS once `C/comparison_scored.json` was written, whatever the outcomes. Evaluate facts keep every existing key, null in comparison mode, and add optional `comparisons_total`, `comparisons_supported`, `comparisons_not_supported`, `comparisons_inconclusive` and `comparisons_void` (decision units, nonnegative integers), all null outside comparison mode, on SKIPPED/stub records and whenever the scored file was not written; records without them stay valid.
