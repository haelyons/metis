## Sealed comparison (U57, U58)
- Purpose: compare several published arms on one box under a design fixed before the run. Owner approval 2026-11-03 (contract gaps G1 comparison arms, G3 tolerance and equivalence, G6 compute metadata of the blind-02 science route); requirements from science steps s13 to s21. Arms are published programs or configurations that need no new code, run by the pipeline from sealed argument vectors. Each invocation runs one arm on one input, and invocations are interleaved on one box. No agent computes a number: every number comes from the pipeline's trusted wall time, from rules fixed before the run and applied by the pipeline, from a trusted comparator of two arms' outputs, or from a published evaluator that runs on each arm's output without access to the arm's identity. Criteria, margins, thresholds, reference values and timeouts are fixed by a science step before the run, sealed, and unreadable by the run's agents and by the processes of arms and evaluator. Compute is recorded twice and never mixed: per invocation as attribution and per box allocation as the bill. Never change a criterion after a result: every decision uses the sealed design. An outcome that is not supported is a result and never fails a stage. Comparisons that need more than one run are split by the science step into one design per run; a design whose launch depends on an earlier run's outcomes is launched only when the science step finds them in that run's `C/comparison_scored.json`. Without `args.comparison`, every stage is unchanged. Declared residual risks, which no rule below removes: the evaluator reads the arm's output files by design, so file names or content under `out/` that identify the program can reach it (the sealed `evaluate.sh` bytes make any dependence on them auditable after the run); and state of shared hardware (device memory, caches, timing) is not cleared between parts.
- Optional `args.comparison` is an object with exactly the key `design`: a non-empty path, resolved relative to the pipeline working directory, to a design JSON file. It is exclusive with `args.card`, `args.units_check` and `args.units_probe`. The design is exactly `{arms, inputs, outputs, metrics, evaluator, replicates, warmup, order_seed, timeout_s, budget_s, bootstrap_seed, bootstrap_resamples, comparisons}`:
  - `arms`: 2 to 5 items, each exactly `{id, what, commands, env}`; ids `"A0"`, `"A1"`, ... in order; `what` a non-empty string. `A0` is the published baseline that intake and reproduce handle as usual.
    - `commands`: 1 to 8 commands, each a non-empty array of non-empty strings: the exact published command lines of the arm, in order, as argument vectors run without a shell. The pipeline runs them (see Evaluate); the arm's adapter only prepares.
    - `env`: null or an object mapping names that match `^[A-Z_][A-Z0-9_]{0,63}$` and do not start with `CMP_` to strings; set for the arm's commands.
    - Placeholders, in command and `env` strings only: `{input}` (the input id), `{run}`, `{out}` (the absolute paths of the invocation's `run/` and `out/`) and `{spec:<p>}` with `<p>` a JSON Pointer (RFC 6901) into the input's `spec`, which must resolve in every input's `spec` to a string (inserted as is) or a finite number (inserted as `json.dumps` writes it). `{{` and `}}` stand for literal braces; any other `{` or `}` makes the design invalid. Substitution replaces every occurrence and is not repeated on its result.
  - `inputs`: 1 to 10 items, each exactly `{id, spec}`: `id` a unique string matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`; `spec` any JSON value (pins, case, configuration).
  - `outputs`: 0 to 10 items, each exactly `{name, what, format, select}`: a logical result each arm, or the evaluator, writes for an input, compared across arms. `name` unique, matching `^[a-z][a-z0-9_]{0,30}$`; `what` a non-empty string; `format` `"bytes"`, `"text_numbers"` (every number in the file's UTF-8 text, in order, as matched by `[-+]?(\d+\.?\d*|\.\d+)([eE][-+]?\d+)?` together with `nan`, `inf` and `-inf` tokens) or `"json_numbers"` (every number leaf of the JSON document, in document order; booleans are not numbers). `select` is null (the whole content) or, for `bytes` and `text_numbers` only, a Python `re` pattern with at least one capturing group: the content is read as UTF-8 with replacement, and the selected content is every group of every match of `re.finditer(select, text, re.MULTILINE)`, in order (an unmatched group as the empty string), joined by `"\n"`; `format` then applies to the selected content (`bytes` to its UTF-8 encoding). Several outputs may select different parts of the same file, each with its own comparison and tolerance.
  - `metrics`: 1 to 10 items, each exactly `{name, unit, what, source, reduce, expect_count}`: `name` unique, matching `^[a-z][a-z0-9_]{0,30}$`; `unit` and `what` non-empty strings; `source` `"trusted_wall"` or `"sealed_extraction"`.
    - `trusted_wall`: the invocation's wall seconds: the adapter's wall plus its commands' walls, plus the evaluator's wall when the design has an evaluator. `reduce` and `expect_count` are null.
    - `sealed_extraction`: read from fetched files by a rule the harness agent fixes before the run, reduced as the design states. `reduce` `"first"`, `"max"` or `"value_at_max_key"`; `expect_count` null or a positive integer, the number of matched values the rule must find.
  - `evaluator`: null or exactly `{what, spec, timeout_s}`: a published, pinned program that reads one arm's output for one input, with data that only it may read, and writes evaluation files. `what` a non-empty string; `spec` any JSON value (program, pin, command, and where its private data come from); `timeout_s` null or a positive integer.
  - `replicates` an integer from 1 to 30; `warmup` an integer from 0 to 3; `order_seed` and `bootstrap_seed` integers; `bootstrap_resamples` an integer from 1000 to 1000000; `budget_s` a positive integer, the evaluate stage's time budget for this comparison. When `args.run_ceiling_s` is present, `budget_s` must be below it.
  - `timeout_s`: null, a positive integer for every invocation, or an object mapping every arm id to a positive integer or to an object mapping every input id to a positive integer: the cap of one invocation's arm part.
  - `comparisons`: 0 to 12 items (0: a run that only records values and compute, for example to derive later reference values), each exactly `{id, arm, against, measure, criterion, direction, unit, pairing, rule, confidence, margin, threshold, strict, reference, missing, given, parts}`:
    - `id` unique, matching `^K[0-9]{1,2}$`; `arm` an arm id; `against` a different arm id or `"reference"`; `parts` a non-empty array of unique non-empty strings.
    - `measure` is exactly `{metric}` (a metric name) or exactly `{output, comparator}` (an output name and one of `"exact"`, `"elementwise_abs"`, `"elementwise_abs_plus_rel_max"`). An output comparison needs an arm as `against`.
    - `criterion` `"agreement"` (every output comparison and no metric comparison), `"non_inferiority"`, `"superiority"` or `"ratio_at_least"`.
    - `direction` `"higher_better"`, `"lower_better"` or `"two_sided"`: the metric as measured (for wall seconds, `lower_better`). `agreement` and `superiority` use `two_sided`; `non_inferiority` and `ratio_at_least` use `higher_better` or `lower_better`.
    - `unit` `"pooled_mean"` (each replicate's value is the mean over inputs, decided once), `"per_input_all"` (decided per input; the comparison holds only if it holds on every input) or `"per_input_each"` (decided and reported per input).
    - `pairing` `"paired_replicate"` or `"unpaired"`; `rule` `"all_pairs"` or `"bootstrap"`; `confidence` a number in `[0.5, 1)` for `bootstrap` and null for `all_pairs`. `ratio_at_least` uses exactly `pooled_mean`, `paired_replicate` and `bootstrap`; every other criterion uses `all_pairs` and a per-input unit; agreement uses `paired_replicate`.
    - `margin`: for an output comparison, the comparator's tolerance: null for `exact`, `{"abs": x}` for `elementwise_abs`, `{"abs": x, "rel": y}` for `elementwise_abs_plus_rel_max`. For `non_inferiority` and `superiority`, null or `{"abs": x}`. For `ratio_at_least`, null. `x` and `y` are finite and nonnegative.
    - `threshold`: a finite number above 0 for `ratio_at_least`, otherwise null. `strict`: a boolean for `ratio_at_least` (true: the bound must exceed `threshold`; false: it may equal it), otherwise null.
    - `reference`: exactly when `against` is `"reference"`, an object `{source, values}`: `source` a non-empty string naming where the values come from (for example an earlier run of this route and the rule that derived them), `values` mapping every input id to a finite number; otherwise null. A reference needs a metric `measure`, a per-input unit and `unpaired`.
    - `missing`: `"void"` or `"fail"`, how a missing value is decided (see Scoring).
    - `given`: an array, possibly empty, of unique ids of comparisons that come earlier in `comparisons`; a decision unit is decided only when each of them is supported for it (see Scoring).
  An invalid argument or design, or a path that cannot be read as JSON, fails intake with `error_class: parse` before any agent call.
- Before the intake agent call and any box command, the pipeline writes atomically, in this order: `C/comparison.json`, exactly `{source, source_sha256, design}`; `C/comparison_seal.json`, exactly `{comparison_sha256, sealed_utc}` (the SHA-256 of the exact bytes of `C/comparison.json`); and `A/comparison_view.json`, exactly `{arms, inputs, outputs, metrics, evaluator, replicates, warmup}` copied from the design, with `evaluator` reduced to `{what, spec}` (null when the design's is null). The view holds no comparison, criterion, margin, threshold, reference value, timeout, part, seed or budget. Agents see only the view; comparison-mode prompts name it and never `C/` or the design path. The science step that writes the design is responsible for the view's free text (`what`, `spec`, `select`) stating no expectation, criterion or result, and for keeping no copy of the design on the pipeline host outside the paths hidden below.
- Isolation of agent calls, comparison mode only. Every agent call of the run (intake, harness, and every setup and anchors repair) is dispatched with wf `isolation` (see Implement) as implement's calls are: `directory` a fresh private view created for that call under the system temporary directory, `box_access` false, and `hidden` holding the run root, the workflow journal directory, the design file's parent directory and, when the design file lies inside a git work tree, that work tree's top-level directory (the nearest ancestor that contains `.git`). Under `isolation` the rest of the host is read-only and the view is the only writable host directory, so each role gets copies of what it reads today and writes only into its view; the pipeline copies its results back:
  - intake view: `comparison_view.json`; when the brief is a file, `brief/<its file name>` (a copy of its bytes), which the prompt names in place of the brief's path; and an empty `intake/`. After the call the pipeline copies each regular file directly under the view's `intake/` (no symbolic link, no subdirectory) to `A/intake/`.
  - harness view: `comparison_view.json`, `intake/` (a copy of `A/intake/`) and an empty `harness/`; the probe stays in the prompt as today. After the call the pipeline copies each regular file directly under the view's `harness/`, and each regular file `harness/arms/<arm id>.sh`, to the same name under `A/harness/`.
  - setup or anchors repair view: `comparison_view.json`, `intake/` and `harness/` (copies of `A/intake/` and `A/harness/`); the probe and log tail stay in the prompt. After the call the pipeline copies back only the scripts that repair may rewrite today (`setup.sh`; or `run_anchors.sh` and `run_command.sh`), and discards every other change, as the existing restore of protected scripts does.
  Prompts name the view's paths in place of `A/intake/` and `A/harness/`. Network access is unchanged by `isolation`. A call that cannot be dispatched so fails as an isolation failure does; there is no fallback. Views are removed after the stage.
- Intake prompt, comparison mode only: the run compares the view's arms on the view's inputs; `A0` is the benchmark intake records as usual; intake also records, in `benchmark.json` under the key `arms`, each other arm's published source, pin and commands, under the key `evaluator` the evaluator's published source, pin and command when the view has one, and in `data.json` every input any arm or the evaluator needs, marking the evaluator's private data and stating where each private item is published.
- Harness prompt, comparison mode only: `setup.sh` also builds or installs every arm's published program and configuration, and the evaluator, as published, under the shared run directory or with apt, never under the home directory. `setup.sh` never fetches, copies or writes the evaluator's private data; only `fetch_private.sh` does (see Separated users). The harness agent writes, besides the usual scripts:
  - one adapter `harness/arms/<arm id>.sh` per arm, `A0` included, which only prepares the invocation (stages the input named by `CMP_INPUT` under `run/` or `CMP_OUT`) and never runs the arm's program, writes or patches source, or computes, writes or asserts a metric;
  - when the view has an evaluator, `harness/fetch_private.sh`, which fetches every input `data.json` marks as the evaluator's private data from where it is published, writing only under its working directory, and `harness/evaluate.sh`, which runs the published, pinned evaluator on the arm output in `CMP_ARM_OUT` for the input named by `CMP_INPUT`, reads private data only under `CMP_PRIVATE`, writes its results under `CMP_EVAL_OUT`, and never writes elsewhere;
  - `harness/cmp_files.json`, exactly `{"files": {...}}`, mapping each arm id to an object that maps every output name to a location: a relative path, or exactly `{glob}` with `glob` a pattern of relative-path components that may also use `*`, `?`, `[` and `]`. Locations are relative to the invocation directory, and their first component is `out` (the arm's files), `log` (the standard output and error of the arm's adapter and commands) or `eval` (the evaluator's files);
  - `harness/cmp_extract.json`, exactly `{"rules": [...]}`, one rule per arm and `sealed_extraction` metric, each exactly `{arm, metric, file, kind, expr}`, with `file` a relative path whose first component is `out`, `log` or `eval`, and `kind` and `expr` as defined for `harness/card_extract.json` (U54), extended by the metric's `reduce`: `kind` `"json"`: `expr` points to a finite number, to an array of finite numbers, or (for `value_at_max_key`) to an array of two-element arrays `[key, value]` of finite numbers; `kind` `"regex"`: exactly one capturing group, or exactly two (key, then value) for `value_at_max_key`;
  - `harness/versions.sh`, which prints one JSON object mapping each arm id, and `"evaluator"` when the view has one, to exactly `{version, executable}`: the program's version string and the path, absolute or relative to the shared run directory, of its main executable file.
  Relative paths are one or more `/`-separated components made of `[A-Za-z0-9._+=-]`, none `.` or `..`. `run_anchors.sh` and `run_command.sh` keep their meaning for `A0`.
- After harness generation or copy (with `args.harness_from`, the source directory must also hold `arms/`, `cmp_files.json`, `cmp_extract.json`, `versions.sh` and, when the design has an evaluator, `fetch_private.sh` and `evaluate.sh`, copied like the scripts) and before the harness upload, those files must exist and be valid: `harness/arms/` holds exactly one non-empty adapter per arm; `fetch_private.sh` and `evaluate.sh` exist exactly when the design has an evaluator; `cmp_files.json` maps every arm and every output, with `eval` locations only when the design has an evaluator; and `cmp_extract.json` has exactly one rule per arm and `sealed_extraction` metric, whose group count matches the metric's `reduce`. Otherwise reproduce fails with `error_class: parse` before the upload. The pipeline then writes `C/arms_seal.json`, exactly `{files, sealed_utc}`, mapping each of those files' names (adapters as `arms/<id>.sh`) to the SHA-256 of its bytes. They upload with the harness, in the same encoding. No repair changes them.
- When the design has an evaluator, a probe whose `sudo_nopasswd` is not true fails reproduce with `error_class: infra` right after the probe, before the harness call: the separated users below need it. The rule that harness scripts use sudo only for apt is unchanged; only the pipeline's trusted scripts below use it otherwise.
- In comparison mode reproduce runs exactly as usual for `A0`. Profile, seal, propose and implement are SKIPPED. Evaluate runs the comparison when reproduce passed, and is SKIPPED otherwise, as after any failed gate.
- Evaluate, comparison mode (U57):
  - Separated users, only when the design has an evaluator: one box command, operation `comparison-users`, runs the trusted `bash profiler/cmp_users.sh` (written inline by the pipeline). With `sudo -n`, in this order, it:
    1. creates, when absent, two system users without login shell or home, `cmp-arm` and `cmp-eval`, and adds both to every group that owns a `/dev/nvidia*` device file whose permission bits for other users lack read or write;
    2. rejects every outgoing packet of `cmp-arm` except on the loopback interface, with an owner-match rule in both `iptables` and `ip6tables`;
    3. recursively removes group and other write access from the shared run directory and grants other users read access to every file and search access to every directory in it, except `cmp-private`; creates `comparison-work/` and `comparison-jobs/` owned by the box user at modes `711` and `700`; and creates `cmp-private` empty (removing any earlier one), owned by `cmp-eval` at mode `700`;
    4. writes `profiler/cmp_writable.json`, mapping each of the two users to the sorted list of directories outside the shared run directory it can write, as printed by `sudo -n -u <user> find / \( -path /proc -o -path /sys -o -path <shared run directory> \) -prune -o -type d -writable -print`;
    5. runs `bash <shared run directory>/harness/fetch_private.sh` as `cmp-eval` (as a part runs, below) with working directory `cmp-private` and `HOME` and `TMPDIR` set to `cmp-private/.home` (created empty, removed afterwards), then cleans up after `cmp-eval` (below); a nonzero exit fails;
    6. fails when `cmp-private` holds anything other than regular files and directories, and otherwise makes it and everything under it owned by `root` with group `cmp-eval`, with directories at mode `750` and files at mode `640`, so the evaluator can read and never change it;
    7. fails when any regular file in the shared run directory outside `cmp-private`, or under the box user's home directory, has the size and SHA-256 of a regular file under `cmp-private`;
    8. checks that `sudo -n -u <user> nvidia-smi -L` prints, for each of the two users, the same number of GPU lines as for the box user, that `sudo -n -u cmp-arm test -r cmp-private` fails, and that the two rules of step 2 are present (`iptables -C`, `ip6tables -C`).
    Any failure fails evaluate with `error_class: infra` before any invocation. Cleanup after a part user is: kill every process of the user (`pkill -KILL -u <user>`) once per second until `pgrep -u <user>` finds none, for at most the time left in `budget_s`; delete every entry the user owns below each directory listed for it in `profiler/cmp_writable.json` (`find <dir> -mindepth 1 -user <user> -delete`); and remove every System V IPC object the user owns. The arm part therefore cannot read the evaluator's private data or anything the evaluator left behind, cannot reach the network, cannot write any file the evaluator or the wrapper runs, and cannot change modes that protect them, whatever its adapter or commands do.
  - Versions: one box command, operation `versions`, runs `bash harness/versions.sh` with stdout to `out/comparison/versions.json`, then the trusted `python3 profiler/cmp_system.py` (written inline by the pipeline) writes `out/comparison/system.json`, exactly `{cpu_model, cpu_logical, kernel, driver_version, cuda_version, gpus, executables}`: `lscpu` model name and logical CPU count; `uname -r`; the driver and CUDA versions that `nvidia-smi` reports; `gpus` one row per GPU, exactly `{index, name, uuid, memory_total}`, from `nvidia-smi --query-gpu=index,name,uuid,memory.total --format=csv,noheader`; and `executables` mapping each key of `versions.json` to exactly `{version, executable, sha256, libraries}`, with `sha256` the SHA-256 of the executable's resolved file and `libraries` one row per `ldd` line of the form `<name> => <absolute path> ...`, exactly `{name, path, sha256}` (the resolved file's SHA-256), or `[]` when `ldd` fails or reports a static executable. Any field that cannot be read is null.
  - Rounds: `warmup` warmup rounds, then `replicates` replicate rounds. Each round runs every (arm, input) pair once, in an order drawn from one `random.Random(order_seed)` stream: one `shuffle` of the round's pairs per round, warmups included. Invocation `k` (from 1, in run order, warmups included) has the token `i<k>`, which names it on the box; no box path, file name, process argument or environment variable that the evaluator part can read names the arm.
  - Each invocation is two box commands from the shared run directory. First, operation `comparison-job` writes the job file `comparison-jobs/i<k>.json`, exactly `{arm, input, mode, round, arm_timeout_s, eval_timeout_s}` (mode `warmup` or `replicate`; the timeouts resolved as under Timeouts when this command starts), in the harness upload encoding, at mode `600`, owned by the box user. Second, operation `comparison` runs the trusted wrapper `python3 profiler/cmp_wrap.py i<k>` (written inline by the pipeline, as the profile stage writes its probe), whose only argument is the token. The wrapper reads its job file and builds a fresh invocation directory `comparison-work/i<k>/` at mode `711`, holding `run/` (a symbolic link to every top-level entry of the shared run directory except `out`, `profiler`, `concurrency-work`, `evaluation-work`, `units-check`, `comparison-work`, `comparison-jobs` and `cmp-private`), an empty `out/`, an empty `log/` at mode `700` owned by the box user, an empty `eval/`, and empty `home/` and `ehome/`. The part user is `cmp-arm` for the arm part and `cmp-eval` for the evaluator part when the design has an evaluator, and the box user otherwise. With separated users, `run/`, `out/` and `home/` are owned by `cmp-arm`, and `eval/` and `ehome/` by `cmp-eval`. A part runs as `sudo -n -u <part user> -- env -i <variables> <argv>` with separated users, and directly otherwise; its variables are the wrapper's environment without any `CMP_`, `SUDO_` or `HOME` name, with `HOME` set to `home/` (arm part) or `ehome/` (evaluator part), plus the part's `CMP_` variables below. The wrapper opens every log file itself and passes it to the part as standard output or error. The wrapper:
    1. arm part: runs `bash harness/arms/<arm>.sh` with working directory `run/`, with standard output and error written to `log/adapter.stdout` and `log/adapter.stderr`; then, when the adapter exits 0, runs each of the arm's commands in order with working directory `run/`, after placeholder substitution and with the arm's `env`, with standard output and error written to `log/cmd<k>.stdout` and `log/cmd<k>.stderr` (`k` from 1), stopping at the first nonzero exit. A first argument containing `/` resolves relative to `run/`, otherwise through `PATH`. Its variables are `CMP_INPUT` (the input id), `CMP_INPUT_SPEC` (the JSON of that input's `spec`) and `CMP_OUT` (the absolute path of `out/`);
    2. with separated users, after the arm part: cleans up after `cmp-arm` (see Separated users; processes still left make the invocation `invalid`); removes `home/`; makes `run/` and `out/` and everything under them owned by the box user, with `run/` at mode `700`; makes the invocation `invalid` when `out/` holds anything other than regular files and directories (a symbolic link included); then removes group and other write access and grants other users read and search access under `out/`;
    3. evaluator part, only when the design has an evaluator and the arm part's status is `ok`: runs `bash <shared run directory>/harness/evaluate.sh` with the shared run directory as working directory and the variables `CMP_INPUT`, `CMP_INPUT_SPEC`, `CMP_ARM_OUT` (the absolute path of `out/`), `CMP_EVAL_OUT` (the absolute path of `eval/`) and `CMP_PRIVATE` (the absolute path of `cmp-private`); then cleans up after `cmp-eval` as in step 2, removes `ehome/`, and makes `eval/` and everything under it owned by the box user;
    4. sets the invocation directory to mode `700`, so that no later part reads this invocation's files, then writes `wrap.json` in it, atomically and last, at mode `600`, exactly `{status, adapter_rc, adapter_wall_s, commands, gpu_busy_s, gpu_busy_known, eval_status, eval_rc, eval_wall_s, eval_gpu_busy_s, eval_gpu_busy_known}`. `status` is `"ok"` (the adapter and every command exited 0), `"failed"` (a nonzero exit), `"timeout"` or `"invalid"`; `commands` has one row per command started, exactly `{argv, rc, wall_s, executable, sha256}` (the substituted argument vector, exit status, `perf_counter` wall seconds, the resolved executable path and its SHA-256, null when unresolved); `eval_status` is `"ok"`, `"failed"`, `"timeout"` or `"skipped"` (no evaluator, or the arm part was not `ok`). Walls are `perf_counter` seconds and exit statuses null on timeout. GPU-busy seconds are sampled separately for the arm part and the evaluator part (`nvidia-smi --query-gpu=utilization.gpu` immediately and every second; each finite sample in [0,100] contributes `utilization / 100` seconds, summed over GPUs; the matching `known` flag is false when no valid sample was taken).
    The invocation's `out/`, `log/`, `eval/` and `wrap.json` are fetched to `A/results/evaluate/comparison/<w<r> or r<r>>/<arm>/<input>/` (`r` the round index), from the pipeline's own record of each token's job.
  - After the last invocation, with separated users, one box command, operation `comparison-private-remove`, removes `cmp-private` with `sudo -n rm -rf`; its outcome is recorded in the stage's receipts and changes no value or outcome.
  - Timeouts: the arm part's timeout is the smallest of its `timeout_s` (when non-null), the time left in `budget_s`, and the time left before the run ceiling; the evaluator part's is the smallest of `evaluator.timeout_s` (when non-null) and the same two. On a timeout the wrapper kills the part's whole process group (with separated users, every process of the part user, as in cleanup) and records `"timeout"`. When the time left in `budget_s` is below 1 s, the remaining invocations are not run, and their status is `"not_run"`. A missing or invalid `wrap.json` gives status `"invalid"`.
  - Values: for an invocation with status `ok`, a `trusted_wall` metric is `adapter_wall_s` plus its commands' `wall_s`, plus `eval_wall_s` when the design has an evaluator (null unless `eval_status` is `ok`). A `sealed_extraction` metric is its rule applied to the fetched file: the matched values are every `float()`-parsed match of the regex in order, or the number or array at the pointer. With `reduce` `first` or `max`, the value is that function of the matched values; with `value_at_max_key`, it is the value of the first pair whose key is the largest. A file under `eval` needs `eval_status` `ok`. A missing or unreadable file, no match, a nonfinite matched number, or a match count other than a non-null `expect_count` gives null. Every value of an invocation with any other status is null. A null value is a missing value.
  - Compute (G6): `A/results/evaluate/comparison_compute.json`, written atomically after the last invocation, is exactly `{invocations, arms, all_invocations, system, versions, allocation}`.
    - `invocations` has one row per scheduled invocation in run order, each exactly `{round, arm, input, status, wall_s, gpu_busy_s, gpu_busy_known, eval_status, eval_wall_s, eval_gpu_busy_s, attributed_usd}`, from `wrap.json`: `wall_s` is `adapter_wall_s` plus the commands' walls, and `attributed_usd` is `(wall_s + eval_wall_s) / 3600 * C/box.json.price_usd_h`, with a null wall counted as 0 and null when the price is unavailable. Rows of `not_run` invocations have null numbers.
    - `arms` has one row per arm, each exactly `{arm, invocations, wall_s, gpu_busy_s, gpu_busy_known, eval_wall_s, eval_gpu_busy_s, attributed_usd}`, summed over that arm's replicate invocations whatever their status, with a null counted as 0; `gpu_busy_known` is true only when every summed row's flag is.
    - `all_invocations` is exactly `{invocations, wall_s, eval_wall_s, attributed_usd}`, summed over every row, warmups and failures included, with a null counted as 0.
    - `system` and `versions` copy the fetched `system.json` and `versions.json` (null when missing or invalid).
    - `allocation` is the bill of the whole box allocation, which may include work outside this run, exactly `{type, price_usd_h, started_utc, ended_utc, hours, usd, final}` from `C/box.json`. When that record has `ended_utc` and `hours`, they are copied and `final` is true; otherwise `ended_utc` is null, `hours` is the time from `started_utc` to when the file is written, and `final` is false. `usd` is `hours * price_usd_h`. Unavailable fields are null. At takeaways, after a matching allocation record refreshes `C/box.json` (see Compute metadata), the pipeline rewrites the file atomically with only `allocation` recomputed. The run's own share stays `run_box_usd`.
    Uploads, links, job files, user setup, the private-data fetch and removal, cleanups and fetches are outside every invocation row; they remain in the stage's receipts.
- Scoring (U58): after the last invocation, `python3 -I m5/score_comparison.py <C dir> <A/results/evaluate/comparison dir> <A/harness dir> <C/comparison_scored.json>`. It checks the SHA-256 of `C/comparison.json` against `C/comparison_seal.json` and of each sealed harness file against `C/arms_seal.json`, then scores each comparison, in design order, from the replicate rounds only.
  - Locations: a relative path names one file. A `{glob}` location names the regular files that Python `glob.glob(glob, root_dir=<invocation dir>)` returns, sorted by a key that splits the relative path into runs of digits and non-digits, compares digit runs as integers and breaks ties by the path; their contents, each after `select`, are joined by `"\n"` (by `b"\n"` for `bytes`). A side of an (input, replicate) pair is missing when its invocation's status is not `ok`, when the location is under `eval` and `eval_status` is not `ok`, when the location names no file or an unreadable one, when the content cannot be parsed as the output's `format`, or when the selected content is empty (no bytes for `bytes`, no numbers otherwise).
  - Output comparisons (`agreement`): for each input and replicate where neither side is missing, the comparator compares the two contents. `exact`: identical bytes. Otherwise both contents are parsed as the output's `format` into number lists; different lengths, or a NaN in one list but not at the same position in the other, disagree; equal infinities agree; finite pairs agree when `abs(a - b) <= abs_tol` (`elementwise_abs`) or `abs(a - b) <= abs_tol + rel_tol * max(abs(a), abs(b))` (`elementwise_abs_plus_rel_max`). A pair agrees when every element agrees. Each compared pair records `max_abs_error` and `max_rel_error` over its finite elements (null when none).
  - Metric comparisons: an arm's value for (replicate, input) is the metric value above. For `pooled_mean`, a replicate's value is the mean over inputs, null when any input's value is null. Per decision unit (the pooled value, or each input): for `paired_replicate`, the differences are `arm - against` per replicate; for `unpaired`, the differences of every arm value with every against value, or of every arm value with the input's reference value. `ratio_at_least` uses the ratio of means `mean(arm) / mean(against)` for `higher_better` and `mean(against) / mean(arm)` for `lower_better`.
  - Missing values, per decision unit: `n_missing` counts the arm's missing values and, against an arm, the against arm's (for `pooled_mean` a replicate counts once; for agreement a pair with a missing side counts once). With `"void"`, any missing value makes the unit void with reason `"missing_values"`. With `"fail"`, a missing value of `arm` makes the unit `"not_supported"` with reason `"missing_values"`, and otherwise a missing value of `against` makes it void with reason `"missing_values"`.
  - Eligibility (`given`): for each listed comparison, its outcome for this unit is that comparison's row for the same input when both comparisons are decided per input, and otherwise that comparison's outcome, where `"per_input"` counts as supported only when every row is. When any of these is not `"supported"`, the unit is void with reason `"not_eligible"`.
  - Interval: for `all_pairs`, `[lo, hi]` is the minimum and maximum of the differences, and needs at least one difference. For `bootstrap`, the ratio of means is recomputed on `bootstrap_resamples` resamples (`B`) with replacement of the unit's paired replicates, drawn from one `random.Random(bootstrap_seed)` stream in comparison order, and `[lo, hi]` is the `(1 - confidence) / 2` and `(1 + confidence) / 2` empirical quantiles (sorted resamples, index `floor(q * (B - 1))`); it needs at least two replicates. `estimate` is the mean difference (`all_pairs`) or the ratio of means (`bootstrap`) on the full data. Too few values gives outcome `"void"` with reason `"insufficient_replicates"`.
  - Margin value `m`: 0 for a null margin, `x` for `{"abs": x}`.
  - Outcome per decision unit, in this order: eligibility; then, for agreement, any compared pair that disagrees makes the unit not supported; then the missing-value rule; then the interval's minimum count; then the criterion. The criterion gives `"supported"`, `"not_supported"` or else `"inconclusive"`: agreement is supported when at least one pair was compared, every compared pair agrees and none is missing (with no compared pair, it is void with reason `"missing_values"`); non-inferiority (`higher_better`) is supported when `lo >= -m`, not supported when `hi < -m`; non-inferiority (`lower_better`) is supported when `hi <= m`, not supported when `lo > m`; superiority (`two_sided`) is supported when `lo > m` or `hi < -m`, not supported when `-m <= lo` and `hi <= m`; ratio with `strict` false is supported when `lo >= threshold`, not supported when `hi < threshold`; ratio with `strict` true is supported when `lo > threshold`, not supported when `hi <= threshold`.
  - `sign` of a unit is `"higher"` when a superiority is supported with `lo > m`, `"lower"` when it is supported with `hi < -m`, and null otherwise.
  - A comparison's outcome: for `pooled_mean`, its one unit's outcome; for `per_input_all`, supported when every input is supported, not supported when any input is not supported, void when any input is void and none is not supported, otherwise inconclusive; for `per_input_each`, `"per_input"`, with each input's outcome in its rows.
  - `C/comparison_scored.json`, atomic, is exactly `{comparison_sha256, comparisons, totals}`. `comparisons` follows the design's order, each exactly `{id, arm, against, criterion, unit, outcome, rows}`; `rows` has one row per decision unit (`input` null for `pooled_mean`), each exactly `{input, n, n_missing, estimate, lo, hi, margin_value, threshold, outcome, sign, reason, pairs}`. `n` counts the differences, ratios or compared pairs; `pairs` is null for metric comparisons and, for agreement, the per-replicate rows `{replicate, agrees, missing, max_abs_error, max_rel_error}` (`agrees` null and `missing` true when a side is missing). Numbers are null when void; `reason` is `"missing_values"`, `"insufficient_replicates"` or `"not_eligible"` for a void unit, `"missing_values"` for a unit made not supported by the `"fail"` rule, and null otherwise. `totals` is exactly `{supported, not_supported, inconclusive, void}`, counting decision units over all comparisons.
  - Exit 0 after writing; exit 1 for invalid or missing input, a seal mismatch or a failed write, with no output file. A missing or invalid `wrap.json` or fetched file is not invalid input; it is a missing value. Diagnostics contain no input content. A scoring failure fails evaluate with `error_class: parse`.
- Evaluate status in comparison mode is PASS once `C/comparison_scored.json` was written, whatever the outcomes. Evaluate facts keep every existing key, null in comparison mode.
