## 1. `predictions`: `other`, `seal_record_before_box`, `return_in_scored`, `hide_from_agents`
- **`other` (needed, and no listed fix covers it).** The record never contains the plan's `decision_rule`. `main.js:478` builds `predictions` from only `if_lever, if_not, noise_rule, expected` (`s10/ASSESSMENT.md:18`). U54 copies the record unchanged, so every listed fix (sealing it, returning it, hiding it) acts on a record that has already lost the rule. **What `other` needs:** in `dut/pipeline/src/main.js` near line 478 (calibration record construction), add `decision_rule: plan.predictions.decision_rule` to the record's `predictions`. Document it in `dut/pipeline/CONTRACT.md` section 5 "calibration", in the same change that adds `name`/`unit`. This changes the tree's card records (`needs_tree_change: yes`).
- **`seal_record_before_box`.** U54 pins the record with `source_sha256`, but the owner's rule is "seal predictions before each test". The seal has to exist before any box command, and the score has to name it. Otherwise nothing shows the record that was scored is the record that was sealed.
- **`return_in_scored`.** G1 consumes the decision rule later (`s10/ASSESSMENT.md:51`; `s09/ASSESSMENT.md:36-38`). The scored file and the resolved copy must therefore carry `predictions` unchanged. A later step can then show that the final run used the card's own rule (`s09/ASSESSMENT.md:28`).
- **`hide_from_agents`.** This matches s10 fix 3: the agents' copy has `predictions` removed (`s10/ASSESSMENT.md:45`).
- **Not chosen: `judge_decision_rule`.** The admissible record's decision rule is about the full experiment ("Acceleration passes only after agreement and when 95% paired-median CPU/GPU complete-wall ratio…", `s10/ASSESSMENT.md:18`). A calibration that measures `eval_runtime_s` cannot evaluate it. G1 does that.

## 2. `band_rule_unfit`: `gate_decides`, `absolute_band_field`, `sign_aware`
- **`gate_decides`.** This is the core of s10 fix 1. For `eval_runtime_s` the band is [20, 180] s and the gate is ≤ 60 s. A measured 100 s would be `within_band` even though the gate stops the card. A measured 15 s would be `below_band` (refuted) even though the gate passes (`s10/ASSESSMENT.md:27-30`). The gate has to decide, and the band becomes a price-check column only.
- **`absolute_band_field`.** Some inputs have no gate, or their gate is on a different input. For those the band still decides. A value of 0 gets no band (`localized_faults`, `acceptance_contract_ready`), and booleans and small counts (`agreement_pass`, `admissible_caps` = 1) get a meaningless [0.33, 3] (`s10/ASSESSMENT.md:32`). Only a per-input absolute band supplied by the card makes these well defined, for example an exact match for a boolean. This is a new field in the card's records (tree change).
- **`sign_aware`.** In `launch.js:71-73` the band is `[value/k, value*k]`. For a negative value that band is inverted (lo > hi), so every measurement is out of band. No current required input is negative, but the seed's quality comparisons (P5/P6: dense − standard DockQ) are signed. The operator revises once, so I include this latent defect in the same rule.
- **Not chosen: `bounded_range`.** No current input is a fraction or probability. Booleans are better served by an absolute band. **Not chosen: `noise_band`.** Once the gate decides, replicates are not needed for this one-input record. They are needed for P2's tolerances, which is G3, not G2.

## 3. `write_back_unfit`: `as_plan_numbers`, `rejudge_card`, `all_runs_not_latest`, `record_run_identity`
- **`as_plan_numbers` and `rejudge_card`.** The owner asked to "carry promising candidates through calibration". Marking a state does not do that. The measured value must replace the GUESS as a MEASURED plan number with provenance, and the card's plan and cost (USD 9.87 line, `s10/ASSESSMENT.md:21`) must be re-judged with it. Otherwise the tree keeps pricing the card on the guess.
- **`all_runs_not_latest`.** s10's proposed rule uses "the latest entry for any required id" (`s10/ASSESSMENT.md:39`). With latest-wins, a refuting run can be erased by re-running until a pass, which breaks "preserve negative results". Any refuting run must keep the card refuted.
- **`record_run_identity`.** Once the state comes from all runs, the entries have to be comparable. P3 timing depends on box type (`s09/ASSESSMENT.md:43`), so each entry needs box type, pipeline commit and date.
- **Not chosen: `states_unfit`.** With `gate_decides`, `refuted` means "the card's own gate failed", and a re-judged card carries the rest. The two states then serve later steps.

## 4. `leaks_or_biases`: `hide_value`, `hide_predictions`, `hide_anchor_value`, `extraction_rule_before_run`
- **`hide_value`, `hide_predictions`, `hide_anchor_value`.** This is s10 fix 3: the agents' `A/card.json` has `value`, `phase.gate.value`, `predictions` and `anchor.published_value` removed, and the full copy is pipeline-only (`s10/ASSESSMENT.md:42-47`). A harness that knows the target of 60 s can choose scale or timeouts to hit it. The same holds for an anchor's published value.
- **`extraction_rule_before_run`.** U54 keeps the card value out of the measured key "at least by instruction" (`s10/ASSESSMENT.md:7`). Even when the harness is blind, if it chooses which output line becomes `card:<id>`, it still chooses the measurement. Fixing the read rule before the run and having the pipeline apply it closes that gap.
