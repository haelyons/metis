# m5 data contracts (what test authors may rely on; implementers keep this file current)

## Run identity and agent chat names
- `args.blind` is a boolean, default false. `args.raid`, when supplied, is a non-empty single-line string and takes precedence over automatic selection. `launch.js stage --stage m5` also accepts `--raid <name>` and `--blind`.
- `m5/raids.json` is `{theme, public, blind}`: a theme string and two ordered arrays of base names. The heist theme uses separate public and blind lists. Automatic selection skips names already present in `m5/raids_used.jsonl`; after the base names it cycles through the same list with suffixes `2`, `3`, etc. Explicit names are recorded too.
- Each ledger row and `C/raid.json` has exactly `{raid, blind, run_root, utc}`; `run_root` is absolute and `utc` is an ISO UTC timestamp. Reservations are serialised. A run reuses its existing reservation and rejects conflicting raid/blind arguments. The launcher reserves against the original pipeline ledger before freezing its copy.
- m5 sets `args.chat_prefix = "x-<raid>"`. Other scripts opt in using `args.chat_prefix`, an agent option `chat_prefix`, or the workflow flag `--chat-prefix`. Without a prefix, runner naming stays unchanged.
- Names are `<chat_prefix>-<label>[-<descriptor>]`; labels are lowercased, non-`[a-z0-9-]` runs become `-`, edge hyphens are removed, and an empty label becomes `agent`. Concurrent sibling calls sharing a label within a stage add `1of<n>`, `2of<n>`, etc. Repair turns add `retry<k>` (starting at 1); fallback calls add `fb`. When needed together, descriptors appear in that order, separated by hyphens. Harness repair calls supply agent option `retry: 1`.
- wf passes the name to every runner as `name`. OpenCode uses `--title`, Claude uses `--name`, and Codex prepends `[<name>]` as the first prompt line, before role instructions.

## m5 model policy (workflow configuration)
- m5 runs use `node idea/wf.js --config m5/wf_config.json --script m5/pipeline.js ... --profile latent_skeptic --family codex`, without `--disable-family claude`. `m5/wf_config.json` holds a `workflow` section identical to `idea/config.json`'s and an `understudy` section with: `primary_family: "codex"`, `mode: "fallback"`, `on_refusal: "halt"`, `disabled_families: []`, `chain: {"codex": ["opencode"], "opencode": ["codex"], "claude": ["codex"], "cursor": ["codex"]}`, and `routes: [{"match": "^skeptic-[45]$", "primary": "claude/sonnet"}, {"match": "^review$", "primary": "claude/sonnet"}, {"match": "^(intake|harness|[a-z]+-repair|seal|propose|tests|implement)$", "understudy": "claude/opus"}]`.
- Effect: every authoring call (intake, harness, any `*-repair`, seal, propose, tests, implement) resolves to a Codex primary with `claude/opus` as its first understudy and OpenCode second (owner, 2026-10-30: Opus covers Codex authors when Codex fails). Skeptic ballots 1–3 resolve to a Codex primary with only OpenCode behind it; no Claude model appears in their primary or chain. Ballots 4–5 and the launch review resolve to `claude/sonnet` with Codex as the only understudy. A Claude refusal is not handed over (`on_refusal: "halt"`): the call returns null, so a refused ballot is a null ballot (it counts against the gate like a rejection) and a refused review fails as a missing review. Transport failures hand over to Codex as for any other call. Only `claude/sonnet` is routed (never Fable).
- The pipeline writes `S/OPERATOR_TAKEAWAY.md` from validated signatures after all stage records, with the raid only in its header. `m5/operator_takeaway.py` accepts optional `--raid`; its Python `takeaway(records, raid=None)` API preserves the old header when omitted. Raid is not added to stage facts or v1 signature IDs.

## A/intake/ (written by the intake agent; checked by the pipeline)
- benchmark.json, data.json: non-empty JSON objects.
- anchors.json: an array, possibly empty; each item has a unique non-empty string `id`, non-empty `quantity` and `source`, finite numeric `published_value`, and `tolerance`. Its length must equal facts.anchors_count. Zero is a valid published value or tolerance.
  - An item is a reference when its comparison is `"=="` and its `tolerance` is null; every other item is an anchor. A reference records a published value without a published acceptance criterion: it is measured and reported, never passed or failed. Intake never invents a tolerance and never converts a published uncertainty into one.
  - Optional `uncertainty` is null or exactly `{kind, value}`, where `kind` is `"standard_error"`, `"standard_deviation"` or `"interval_halfwidth"` and `value` is finite and nonnegative. It records published uncertainty where available and never affects scoring.
  - Optional `comparison` is one of `"=="` (the default), `">"`, `">="`, `"<"`, or `"<="`. For `"=="`, an anchor passes when `abs(measured_value - published_value) <= resolved_absolute_tolerance`. For inequalities, it passes when `measured_value <comparison> published_value`; tolerance is ignored and may be 0 or null. Intake should specify `comparison` when the published criterion is a threshold.
  - `tolerance` is a finite nonnegative number (absolute tolerance), or an object with exactly one key: `{"abs": x}` or `{"rel": x}`, where `x` is finite and nonnegative. For `"=="`, relative tolerance resolves to `x * abs(published_value)`; a zero reference therefore requires exact agreement.
- baseline.json: non-empty repo, build_commands, run_commands and published_configuration, plus commit or pin. `build_commands` lists every command that builds or installs the baseline, including package-manager installs of released binaries, and is never empty. The intake prompt states both. The intake prompt names every key the completeness check reads exactly as the check reads it, as a JSON key: in baseline.json `repo`, `build_commands`, `run_commands`, `published_configuration`, and `commit` or `pin` (`pin` is any non-empty immutable identifier, such as a release, tag or content hash, when no commit exists); in EXECUTION.json `representative_scale`, `inputs`, `outputs` and `timing_scope`. It states that the check reads only these key names, so an equivalent value under another key does not count. The completeness check itself is unchanged.
- EXECUTION.json: non-empty representative_scale, inputs, outputs and timing_scope. Optional `stage_budgets_s` supplies positive integer seconds in [1, 999999999], with keys `setup`, `anchors`, `profile`, `method_setup`, `method_run`, `tests`, `evaluate`. Keys `method_setup`, `method_run`, `tests` and `evaluate` each resolve independently from `EXECUTION.json.stage_budgets_s`, then `args.stage_budgets_s`, then defaults: method_setup=1200, method_run=1200, tests=900, evaluate=2400. Keys `setup`, `anchors` and `profile` resolve as the next bullet states (U47). Legacy `timeout_s` and `timeouts` no longer set pipeline box budgets. Every box command passes its resolved budget as `boxrun --timeout`. Harness uploads/probes use setup; implementation uploads, baseline snapshots, patch application and integrity checks use method_setup; evaluation uploads/integrity checks use method_setup. Script retries under the other keys retain the original budget.
- Finish-first timing for the baseline workload (U47; owner direction 2026-10-30: intake's budgets are recorded estimates, not timeouts; a run is limited by a 12 h hard ceiling; a reproduction-only result counts). Keys `setup`, `anchors` and `profile` resolve from `args.stage_budgets_s` when the key is present there. Otherwise the budget is the time left before the run ceiling when that box command starts: `run_ceiling_s` minus the whole seconds elapsed since the pipeline script started, rounded down. `run_ceiling_s` is the optional `args.run_ceiling_s`, an integer in [1, 999999999], default 43200 (12 h); any other value is an invalid budget and is handled as an invalid stage budget is. Every box command under these keys resolves its budget when it starts: each setup and anchors attempt, each rerun after a repair, each identical retry, every harness upload, the box probe and its upload, the fixed profiler and the concurrency probe. When the time left is below 1 s, the command does not run and its step fails as a timeout does (`error_class: timeout`, exit 3). `EXECUTION.json.stage_budgets_s` values for these three keys stay in EXECUTION.json unchanged and never set a timeout. Prompts that state setup, anchors or profile budgets give the seconds resolved when the prompt is built and say the figure is the time left before the run ceiling, not a target; one fixed scale and no scale search still apply. The other keys are unchanged. Run evidence (blind-01 run8, 2026-10-31): intake set a 1,200 s anchors budget; in two of three anchors attempts the representative-scale workload was still running at the budget, it completed only partly and wrote no measurements, and an authorized reader judged an anchors budget from a measured or published runtime the smallest fix; the materials were not implicated. The profile stage runs the same `run_command.sh`.
- Every harness, test-author, method-author and repair prompt states the budget for each script it writes. All require one fixed scale from EXECUTION.json, no scale search or doubling loops, and completion well within the budget. Baseline run_evaluation.sh and method run_anchors.sh use method_run per invocation; evaluate bounds each complete scorer, including all repetitions and curves.
- The intake passes only when the files are complete and found is true, data is "available", licence is not "restricted", and stock_environment is not false. Missing executable inputs and an explicit licence restriction block; missing published tolerances do not. A `licence` of "unknown" does not block: local experiments proceed under the owner's standing authorization (2026-10-30), which is recorded separately from licence evidence and never changes it. Intake records `licence` and `licence_basis` as the evidence shows and never relabels ambiguous coverage as permission. The intake prompt states that "unknown" stays "unknown" when permission is not established, that it does not stop the run, and that "restricted" does. `found` means a public benchmark with executable published code, command and inputs; a benchmark without published tolerances qualifies, with its published values recorded as references. The intake prompt states this.
- Intake facts add optional `anchored` (boolean): true exactly when anchors.json holds at least one anchor. Every executed intake stage emits it once anchors.json validates; it is null when anchors.json is missing or invalid and on SKIPPED/stub records. `OPERATOR_TAKEAWAY.md` shows it among the intake gate flags. A run whose intake has `anchored=false` is unanchored: its claims concern the workload as published and run, not agreement with published values.
- An intake FAIL signature names the failed gate conditions in v1 `blockers`, from the existing blocker vocabulary and in this fixed order: `licence` when the `licence` fact is "restricted", `data_unavailable` when the `data` fact is "partial", "unavailable" or "unknown", and `env_irreproducible` when the `stock_environment` fact is false. Each condition is read from the facts the record carries, whatever else failed (missing reply, incomplete or invalid files, or `found` false); a null or absent fact adds no blocker. When no condition applies, and for every PASS, SKIPPED and stub intake, `blockers` stays `["none"]`. Intake `exit_code`, `exit_kind` and `error_class` are unchanged. `OPERATOR_TAKEAWAY.md` lists these blockers in its Blockers section as for any stage.
- Intake facts add optional `licence_basis`, the basis of the licence judgement for the least-covered item among the benchmark code and its required inputs. It is the first of these values that applies to any item, in this fixed order: `"unreachable"` (the licence evidence for the item could not be fetched), `"none"` (no licence, terms of use or owner statement found for the item), `"owner"` (the item's only basis is a permission stated by the run's owner in the brief), `"distribution"` (the item's only basis is a licence of the repository, package or archive that distributes it, and that licence does not state that it covers the item), `"explicit"` (a licence or terms of use states that it covers the item, by name, by path, or as the whole repository, package or archive). The intake prompt defines these values and asks for the fact; a value outside the list makes the reply invalid, as for any other fact. It is null when the reply omits it, and on SKIPPED and stub records. It never changes the gate, the `licence` fact, `blockers` or any other fact. Signatures carry it as an enum fact, and `OPERATOR_TAKEAWAY.md` shows it among the intake gate flags.
- `OPERATOR_TAKEAWAY.md` shows the intake `licence` fact among the intake gate flags, next to `licence_basis`. When intake PASSes with `licence` other than "permitted", the takeaway adds exactly one line: "Execution authority: owner's standing instruction (2026-10-30), not licence evidence." No other record carries the authorization, and no fact changes because of it.

## A/results/probe/probe.json (collected before the harness agent)
- The pipeline uploads the committed `m5/box_probe.sh` and runs it through boxrun in the same remote working directory as the harness. Both operations write receipts under `C/receipts/`, using the setup timeout. Fetched `out/probe.json` is validated as a JSON object and copied to `A/results/probe/probe.json`. Logs and fetched `out/` remain under `A/results/probe/`. Stale local or remote probes cannot satisfy a new run.
- Fields match the probe script:
  - `os`: null or `{id, version_id, pretty_name, version, name}` from `/etc/os-release`, with nullable strings; `kernel`: string or null.
  - `nproc`, `memory_kb` (MemTotal in KiB), `disk_home_avail_bytes` (available bytes on `$HOME`'s filesystem): integers or null.
  - `nvidia`: null or `{gpus, driver_version, cuda_version}`; `gpus` is an array of GPU name strings, versions are strings or null. CUDA here is the driver's reported CUDA version.
  - `nvcc`: an array of `{path, version}` for deduplicated executable paths from `command -v nvcc`, `/usr/local/cuda*/bin/nvcc`, and `/usr/lib/cuda*/bin/nvcc`; `version` is captured `nvcc --version` text or null. Missing nvcc yields `[]`.
  - `cmake`, `gcc`, `g++`, `make`, `git`, `python3`, `pip`: null or `{path, version}`, with a string path and nullable version text. `pip` falls back to `pip3`.
  - `apt_sources`: an array of `{file, lines}` naming apt source files and their lines mentioning cuda or nvidia. Commented matches may be included when no uncommented matches exist; these do not authorize enabling a repository. Missing matches yield `[]`.
  - `apt_enabled_sources`: an array of `{file, entries}` covering every apt source the image enables, whatever it mentions: for `/etc/apt/sources.list` and `/etc/apt/sources.list.d/*.list`, `entries` holds each line whose first token is `deb` (commented lines are excluded); for `/etc/apt/sources.list.d/*.sources` (deb822), `entries` holds one string per stanza not marked `Enabled: no`, joining its `Types`, `URIs`, `Suites` and `Components` fields as `Types: <v> URIs: <v> Suites: <v> Components: <v>` (absent fields omitted). Files with no entries are omitted; none yields `[]`. `apt_sources` is unchanged. Both fields read the apt directory `${M5_PROBE_APT_DIR:-/etc/apt}` (its `sources.list` and `sources.list.d/`), so tests can point the probe at a fixture; the pipeline never sets this variable.
  - `sudo_nopasswd`: boolean indicating whether `sudo -n true` succeeds.
- Individual missing tools or unavailable facts yield null/empty collections without failing the probe. Probe upload/run failure, nonzero boxrun exit, failed fetch, or missing/invalid JSON fails reproduce with `error_class: infra`, before any harness call; the probe has no agent repair; a timeout permits the single identical command retry defined below.
- Full JSON content is included in the harness prompt and every setup and anchor repair prompt. Agents must use discovered paths and versions and never hard-code a toolkit path absent from the probe. Select a CUDA toolkit root discovered in `probe.json` with both `include/cuda_runtime.h` and `lib64/libcudart.so`, checking both with `ls` on the box from the scripts. Pass it explicitly via `CUDAToolkit_ROOT` or `-DCMAKE_CUDA_COMPILER=<root>/bin/nvcc`, and prepend `<root>/bin` to `PATH`. Never rely on `/usr/bin/nvcc` when a complete toolkit root exists. A tool or system library the published baseline needs but the stock image lacks may be installed with `sudo apt-get install -y` from any source the probe reports in `apt_enabled_sources` (after `sudo apt-get update`), once `apt-cache policy <package>` shows an install candidate. Never add repositories, keys or source lines, and never enable a commented or disabled source. Setup prints each package it installs and its installed version (`dpkg-query -W <package>`). Otherwise only cmake may fall back to pip. If neither route applies, scripts must fail with a clear message. The harness prompt and every setup and anchors repair prompt state this rule. Run evidence (blind-01 run6, 2026-10-31): setup failed three times on a missing runtime library packaged in the Ubuntu archive (universe); the rule then allowed apt only from the CUDA/NVIDIA lines in `apt_sources`, so neither repair could install it.

## A/harness/ (written by the harness agent or copied from a previous run)
- Optional `args.harness_from` is a non-empty directory path to a previous run's `A/harness/`, resolved relative to the pipeline working directory. After a successful fresh box probe, the pipeline copies the exact bytes of `setup.sh`, `run_anchors.sh` and `run_command.sh` into the current `A/harness/` and skips the initial harness agent call. If present, `run_evaluation.sh` is copied too. Missing or unreadable required scripts, or an invalid argument, fail reproduce with `error_class: parse`; there is no fallback harness generation. Without this argument, harness generation is unchanged.
- Reuse writes script-owned `C/harness_source.json` as `{source, files}`. `source` is the absolute source harness directory; `files` maps each copied filename to `{sha256, modified}`. `sha256` is the lowercase 64-digit SHA-256 of the exact original copied bytes and remains unchanged after repair. `modified` starts false and becomes true after an accepted repair of that script, before its upload/rerun, even if that rerun fails. Reuse permits the same bounded setup and anchor repairs (at most four for setup, two for anchors) as generated harnesses; every repair receives the fresh probe. Reuse adds no stage facts and does not reuse probe results, measurements, or stock verification.
- `setup.sh`, `run_anchors.sh`, `run_command.sh` are bash scripts. The pipeline invokes them as `bash harness/<name>` from one fresh `/tmp/m5-<uuid>` directory on the already-running operator-managed box. They share that directory across reproduce and profile. No dev lifecycle commands are issued. `BOX` and `FETCH` are inherited unchanged by `boxrun.sh`, including injected executables.
- Harness uploads (the initial upload of every harness script, and the re-upload of rewritten scripts after each accepted repair) use the implement upload encoding, so no process argument or remote command line grows with script size. For each script, the upload truncates `harness/<name>` (`: > harness/<name>`) and then appends its base64 in independently decodable chunks of at most 24,576 characters (`printf %s <chunk> | base64 -d >> harness/<name>`); an empty script is created empty. These lines are batched in order into boxrun commands below 32,768 characters. Every batch begins with `set -e` and `mkdir -p harness out`, runs as operation `upload` under the setup budget, and has its own receipt. A batch that fails (nonzero exit, failed fetch, missing receipt, or a timeout after its identical retry) ends the upload: later batches are not sent and the harness script does not run, and the step fails as a failed upload does today (`infra`, or `timeout` on a timeout). After all batches succeed, the uploaded files are byte-identical to the local harness files. A harness small enough for one batch uploads in exactly one `upload` command, as before. Run evidence (blind-01 run5, 2026-10-31): the single upload command exceeded the operating system's 131,072-byte limit on one argument, spawning boxrun failed with E2BIG before any receipt was written, and reproduce stopped with `infra` before setup ran.
- `setup.sh` installs/builds the exact published baseline in the stock image; sudo is allowed only for apt. Published source/configuration stays under `baseline-published/`; inputs stay under `data/`. Setup builds and checks only the baseline; the fixed pipeline profiler owns profiling tools and installation. Setup must tolerate one retry in the same directory. Tuning is deferred.
- `run_anchors.sh` runs the published protocol at the intake's representative scale and writes `out/anchors_measured.json` as an object mapping each intake item ID (anchors and references) to a finite measured number; with an empty anchors.json it still runs the published command and writes `{}`. Missing or non-numeric measurements fail the corresponding anchor; booleans and nonfinite values count as non-numeric. Additional measurements are ignored for scoring.
- `run_command.sh` contains only the exact measured baseline command and complete environment at the representative scale, including working directory, arguments, CUDA visibility and GPU count. It runs the published binary, saves its output for anchor parsing, and propagates its exit status. `run_anchors.sh` invokes `bash harness/run_command.sh` from the shared working directory without overriding its environment or duplicating the command. Profiling invokes that same file from that same directory. No agent writes profiling scripts or profile outputs.
- `run_command.sh` uses paths relative to its working directory, never absolute paths into the run directory, and writes only under `out/` or temporary files. The concurrency probe and evaluation run it from sibling work directories that link the same trees (see Concurrency probe). Harness and repair prompts state this requirement.
- Optional unit files (U50): `run_units.sh` and `units.json`, used only by the unit equivalence check (U51) and the unit-mode concurrency probe. `units.json` is exactly `{"units": [...]}` with at least four entries, in the order the published full run processes them, each exactly `{id, outputs, cost_s}`: `id` is a unique string matching `^[A-Za-z0-9][A-Za-z0-9._:+=-]{0,127}$` that identifies that unit to `run_units.sh`; `outputs` is a non-empty array of unique relative paths naming that unit's result files under `out/`, each one or more `/`-separated components made of `[A-Za-z0-9._+=-]`, none of them `.` or `..`; `cost_s` is a finite positive number, the unit's own seconds as recorded in the reproduce run's logs or outputs. `bash harness/run_units.sh <id>...` runs the exact measured command of `run_command.sh` (same binary, configuration, environment and scale) restricted to the listed units (one or more), in the order given, by one of two means: the published program's own subset selection when it takes effect, or otherwise a restricted copy of the prepared input list that the measured command reads, holding only the listed units' original records copied byte for byte in the list's own format, written under `out/` or a temporary directory and passed through an argument, configuration value or environment variable the measured command already accepts. Either way it retains the measured baseline's per-unit code, parameters and inputs exactly as `run_command.sh` runs them, including any documented setup or anchors repairs the measured baseline already carries: the reference is the measured baseline, not the pristine upstream program, and no new code change is allowed. A path-rule conflict that `run_command.sh` already has is inherited and recorded separately; the unit files add none. Reader evidence (run10_diff, 2026-11-01): the entry point's command-line selector exists but has no effect; the measured command reads a prepared input list whose path it already accepts, a restricted list of original records under `out/` adds no write elsewhere, and the per-unit code differences earlier subsetting attempts were flagged for are inherited repairs. Owner decision 2026-11-01: allow selection of original prepared input records while retaining the measured baseline's per-unit code, parameters and inputs. It obeys every `run_command.sh` rule (relative paths, writes only under `out/` or temporary files, no `CUDA_MPS_*` changes), writes each listed unit's `outputs` under `out/` at the same paths as the full run, and propagates the exit status. Under `args.harness_from`, each of the two files present in the source is copied with its exact bytes and recorded in `C/harness_source.json` like the scripts. Files present in `A/harness/` are uploaded with the initial harness upload (same encoding and batching), never later. No repair changes them: after every setup or anchors repair the pipeline restores their bytes (or their absence), as it restores `run_evaluation.sh`. The harness agent is not asked to write them; fresh harness generation is unchanged. The unit equivalence check (U51) and the probe's comparison with the frozen baseline outputs (see Concurrency probe) are their validation.
- The pipeline owns CUDA MPS. No harness script (`setup.sh`, `run_anchors.sh`, `run_command.sh`, `run_evaluation.sh`) may set, unset or override any `CUDA_MPS_*` environment variable, or start or stop an MPS daemon; the scripts inherit these variables unchanged. Harness and repair prompts state this rule. (Method code written in implement is not a harness script and may manage MPS itself.)
- Harness prompts require the published build and binary to run and measurements to come from their OUTPUT. Scripts must never parse or assert on source text. Measurement checks fail only on missing or invalid output; deterministic scoring owns anchor comparisons.
- Without `args.harness_from`, there is one initial agent call (`harness`, `ls-writer`, `sonnet`). Setup permits up to four repairs (`harness-repair`) and anchors up to two (`anchors-repair`) after a nonzero exit, with the same role/model. Each repair receives the failure class and at most the last 200 log lines of the latest failed attempt, and its prompt states its attempt number and the step's limit (`repair attempt <n> of <limit>`). Each later repair runs only after the previous repaired script ran and failed again (nonzero exit or output-gate error); a declined (null) repair, an infrastructure or fetch failure, or a failed upload ends the step. Owner direction 2026-10-30: finish experiments rather than stop them on a fixable failure; a blind run spent its one setup repair on a build-dependency failure, the repair worked, and setup then failed on a different import error that a single repair could not reach. U46 run evidence (blind-01 run7, 2026-10-31): setup spent both of its two repairs on successive script errors; each repair's log tail held its error, each repair targeted it and none regressed, a static check before upload would have caught none, and setup reruns reuse the materials already fetched and verified, so an attempt after a repair costs tens of seconds; an authorized reader judged more repairs of the same kind the smallest sufficient fix. Anchors keep two repairs until a run shows otherwise. The setup repair may rewrite only `setup.sh`. The anchors step executes `run_anchors.sh` and the `run_command.sh` it invokes, so the anchors repair may rewrite either or both and nothing else; a rewritten `run_command.sh` still obeys every `run_command.sh` rule above, and the anchors repair prompt states this. After each repair every rewritten script is recopied, then the step reruns once, with its budget resolved at the rerun's start (U47). Under reuse, an accepted anchors repair marks `modified` true for each of the two scripts whose bytes it changed. Infrastructure/fetch failures do not trigger repairs. Timeouts use the same repairs (the step's own limit), never an extra one. Repair prompts include budget seconds, measured wall seconds and max(0, wall_s-budget_s) overrun seconds. Profiling has no agent repair or execution retry; output/gate failures stop downstream work.

## A/results/reproduce/ and deterministic anchor scoring
- Every reproduce box command fetches remote `out/` into `A/results/reproduce/out/`, and its `<receipt-id>.log` into `A/results/reproduce/`. Logs remain in the agent view. The local fetched `out/` is cleared before each command to prevent stale measurements. The final copy contains the anchor run's outputs. When reproduce passes, the pipeline freezes those outputs on the box: through boxrun, as operation `reproduce-freeze` under the `setup` budget, it runs `test ! -e reproduce-out` and then `cp -a out reproduce-out` in the shared run directory. Like every reproduce command, its fetch replaces `A/results/reproduce/out/`, so that local copy and remote `reproduce-out/` hold the same outputs: the baseline outputs the seal and the test author read. Later stages never write to `reproduce-out/`; remote `out/` after reproduce also collects profiler and probe outputs and further runs of the baseline command, which are not baseline outputs. A failed `reproduce-freeze` (nonzero exit, failed fetch, or timeout) fails reproduce with `error_class: infra`, or `timeout` on a timeout, without repair.
- `python3 m5/score_anchors.py <anchors.json> <measured.json> <out.json>` writes an atomic JSON object with exact keys `anchors`, `anchors_passed`, `anchors_total`, `all_passed`, `references_total`.
  - `anchors` preserves intake order and contains `{id, kind, published_value, measured_value, tolerance, passed}` for every item, with `kind` `"anchor"` or `"reference"`. Items with `uncertainty` keep it unchanged in their row. Reference rows have `passed: null` and `difference` (measured minus published, or null when unmeasured); an unmeasured reference row has `reason` `missing` or `non_numeric` and is never a failure. `tolerance` preserves its input form; `passed` is boolean. Missing or non-numeric measurements are represented by `measured_value: null`. Failed rows additionally contain `reason`: `unknown_comparison`, `missing`, `non_numeric`, `out_of_tolerance` (for `"=="`), or `threshold_not_met` (for inequalities). Unknown comparisons take precedence over measurement failures; missing measurements take precedence over non-numeric measurements. Passing rows have no `reason` field.
  - `anchors_passed` and `anchors_total` count anchors only and `references_total` counts references; all are nonnegative integers. `all_passed` is true exactly when every anchor passed, including when there are none. An empty array is valid. Duplicate IDs, invalid published values, invalid tolerances or uncertainties, and nonfinite calculated equality differences/tolerances are parse errors. Unknown comparisons and missing/non-numeric measurements are anchor failures rather than parse errors.
  - Exit 0 means every anchor passed; exit 4 means at least one anchor failed; exit 1 means invalid/missing input or an output write failure. Invalid input does not produce a new score file. Diagnostics contain no input content.
- The pipeline writes the score to `A/results/reproduce/anchors_scored.json`.

## Card calibration (U54)
- Purpose: a calibration run measures a tree card's load-bearing GUESS and PROXY inputs on the card's own protocol, and the measured values return to the card. Owner approval 2026-11-03 (contract gap G2 of the blind-02 science route): the tree's calibration record names those inputs, but nothing passed the record to an m5 run or wrote a measurement back, so a run's result could not be read against the card's value. A measured input that does not hold refutes the card's value; that is a result and never fails a stage. Science checks s10 and s11 (2026-11-03) fixed the rest: no agent of the run sees the card's values, bands, gate thresholds, predictions or anchor value; how each input is read from the run's output is fixed before the workload runs and applied by the pipeline, not by a harness script; the card record is sealed before any box command; where the card sets a gate on an input, the gate decides it. Without `args.card`, every stage is unchanged.
- Optional `args.card` is an object with exactly the keys `result` and `key`, and optionally `bands`. The launcher keeps the argument file of a card run under `control/` (agents never read it); any copy elsewhere in the run root omits `card` (second review of U54, 2026-11-03). `result` is a non-empty path, resolved relative to the pipeline working directory, to a tree run's `result.json`; `key` is a non-empty string. The card's record is the entry of that file's `calibration` array whose `key` equals `key`. It must have `state` `"calibration_required"` and a non-empty `required` array whose items each have a unique string `id` matching `^[a-z][a-z0-9_]{0,30}$` and `basis` `"GUESS"` or `"PROXY"`. `bands`, when present, maps some of those ids to `{"abs": x}` with `x` a finite number above 0: absolute bands fixed before the run by whoever launches it, for inputs a multiplicative band cannot judge. An invalid `args.card`, a missing or unreadable file, invalid JSON, no matching record, any other state, an invalid `required` or `bands`, or `args.card` together with `args.units_check` or `args.units_probe` fails intake with `error_class: parse` before any agent call.
- Optional `args.pipeline_commit` is a string naming the commit of the pipeline copy the run executes; `launch.js` writes it into every m5 `args.json` (the short commit it already records in RUN.md, or null when unknown). It changes no behaviour.
- Before the intake agent call and any box command, the pipeline writes, atomically and in this order: `C/card.json`, exactly `{source, source_sha256, record, bands}` (`source` the absolute path of `result`, `source_sha256` the lowercase hexadecimal SHA-256 of its exact bytes, `record` the matching record unchanged, `bands` the launch bands or `{}`); `C/card_seal.json`, exactly `{card_sha256, sealed_utc}` (the SHA-256 of the exact bytes of `C/card.json` and a UTC ISO time); and `A/card_inputs.json`, exactly `{inputs, anchor}`. `inputs` has one entry per `required` item in order, each exactly `{id, name, unit, measured_by, phase}`, with `phase` the item's `phase.what` or null and `name`/`unit` null when absent. `anchor` is `{"what": <the record anchor's what>}` when the record's anchor has a finite numeric `published_value`, otherwise null. `A/card_inputs.json` holds no value, basis, band, gate, cost line, budget, prediction or published value. Every later read of the card uses `C/card.json`, never `result`.
- Agents see only `A/card_inputs.json`. No file an agent of the run can read holds `args.card` or anything of `C/card.json` (the record, the launch bands or the `result` path): the workflow's run record (`agent/wf/run.json`) and every other agent-readable copy of the run's arguments omit `card` (review of U54, 2026-11-03). Card-mode prompts name it and never name `C/` or `result`; the existing rule that agents never read `control/` stands. Intake prompt, card mode only: this run calibrates the listed inputs, and EXECUTION.json's representative workload is the protocol of the phases they name (their `measured_by` and `phase`), not another workload. Harness prompt, card mode only: the representative run must write outputs from which each listed input, and the anchor quantity when `anchor` is non-null, can be read, and the harness agent declares in `harness/card_extract.json` how each one is read; no harness script computes, writes or asserts a card value.
- `A/harness/card_extract.json` is exactly `{"rules": [...]}`: one rule per `inputs` entry in order, then one rule with id `"anchor"` when `anchor` is non-null. Rules belong to inputs by position: the i-th rule's `id` must equal the i-th input's `id`, an input whose id is `anchor` is matched like any other, and the anchor rule is the one after the last input. Each rule is exactly `{id, file, kind, expr}`. `file` is a relative path under the run's `out/`, one or more `/`-separated components made of `[A-Za-z0-9._+=-]`, none `.` or `..`. `kind` `"json"`: `expr` is a JSON Pointer (RFC 6901) into that file, and the value there must be a finite JSON number (never a boolean). `kind` `"regex"`: `expr` is a Python `re` pattern with exactly one capturing group; the file is read as UTF-8 with replacement, the last match's group is parsed with `float()` and must be finite. With `args.harness_from`, the source harness directory must also hold `card_extract.json`, copied like the other scripts. The pipeline validates the file after harness generation or copy and before the harness upload; a missing or invalid file fails reproduce with `error_class: parse` before the upload. It then writes `C/card_extract_seal.json`, exactly `{extract_sha256, sealed_utc}`. No repair changes `card_extract.json`.
- Scoring: after `run_anchors.sh` exits 0 and its output gate passes, before anchor scoring and whatever the anchors score, the pipeline runs `python3 -I m5/score_card.py <C dir> <A/harness/card_extract.json> <A/results/reproduce/out dir> --run <run tag> --commit <pipeline_commit, or - when null>`. The script first checks the SHA-256 of `C/card.json` against `C/card_seal.json` and that of `card_extract.json` against `C/card_extract_seal.json`; then applies each rule to the fetched outputs (a missing or unreadable file, no match, or a value that is not a finite number gives null; a number whose double-precision value is not finite, such as an integer too long for a double, is not a finite number); then writes `C/card_scored.json` atomically, exactly `{key, run, pipeline_commit, box_type, box_started_utc, card_sha256, extract_sha256, predictions, anchor, rows, inputs_total, measured_total, holds_total, refuted_total}`. `box_type` and `box_started_utc` come from `C/box.json` (`type`, `started_utc`), null when unavailable; `pipeline_commit` is null for `-`; `predictions` is the record's `predictions` unchanged (null when absent).
  - `anchor` is null when `A/card_inputs.json` has no anchor; otherwise exactly `{published_value, tolerance, measured_value, difference, passed}`: `published_value` and `tolerance` copy the record anchor's; `difference` is measured minus published, null when unmeasured; `passed` is `abs(difference) <= t` for a finite nonnegative numeric tolerance `t` or `{"abs": t}`, `abs(difference) <= t * abs(published_value)` for `{"rel": t}`, and null for any other tolerance or when unmeasured. The anchor never decides an input.
  - `rows` follows `required` order, one row per item, each exactly `{id, name, unit, basis, value, band_source, band_lo, band_hi, measured_value, verdict, gate_passed, decided_by, decision, rule}`. `name` and `unit` copy the item's (null when absent); `basis` and `value` copy the item's; `rule` is the item's extraction rule without its `id`.
  - Band: a launch band (`bands[id]`) or else the item's own `band` when it is `{"abs": x}` gives `band_source` `"launch"` or `"card"` and `[value - x, value + x]` when `value` is a finite number. Otherwise the multiplicative band, `band_source` `"multiplicative"`, with `k` 2.5 for PROXY and 3 for GUESS: `[value/k, value*k]` for a finite `value` above 0 and `[value*k, value/k]` for a finite `value` below 0. Otherwise (`value` 0 or not a finite number) `band_source`, `band_lo` and `band_hi` are null.
  - `verdict` is `"not_measured"` when `measured_value` is null; otherwise `"no_band"` when the band is null; otherwise `"within_band"` when `band_lo <= measured_value <= band_hi`, `"below_band"` below it and `"above_band"` above it.
  - `gate_passed` is null unless the item's `phase.gate` is an object whose `on` equals the item's `id`, whose `op` is `">="` or `"<="` and whose `value` is a finite number, and `measured_value` is a number; then it is the boolean `measured_value <op> gate.value`.
  - `decided_by` is `"gate"` when `gate_passed` is a boolean, otherwise `"band"` when `verdict` is `within_band`, `below_band` or `above_band`, otherwise null. `decision` is `"holds"` or `"refuted"` by the gate (`gate_passed` true or false) when it decides, otherwise by the band (`within_band` holds; `below_band` and `above_band` refute); `"not_measured"` when unmeasured; `"undecidable"` when measured with neither a gate nor a band.
  - `inputs_total` counts rows, `measured_total` rows with a number, `holds_total` and `refuted_total` the rows with those decisions.
  - Arithmetic is exact: no band bound, anchor difference or comparison is lost to double overflow (a card value of 1e308 with a measurement of 1e308 is `within_band`; a published value of -1e308 measured as 1e308 with tolerance 1 has `passed` false). A number that cannot be written as a finite double is written as null; verdicts, decisions and `passed` use the exact values (second review, 2026-11-03).
  - Exit 0 after writing; exit 1 for invalid or missing input, a seal mismatch or a failed write, with no output file (an earlier `card_scored.json` in the C dir is removed before anything else, including argument parsing whenever the C dir argument is present, so a failed run never leaves one). Diagnostics contain no input content. A scoring failure fails reproduce with `error_class: parse`.
- Card rows never change reproduce's status, gate or `run_valid`: they are measured and reported, as references are.
- Reproduce facts add optional `card_inputs`, `card_measured`, `card_holds` and `card_refuted`, the four totals as nonnegative integers. All four are null outside card mode, on SKIPPED/stub records, and whenever `C/card_scored.json` was not written; records without them stay valid.

## Sealed comparison (U57, U58)
- Purpose: compare several published arms on one box under a design fixed before the run. Owner approval 2026-11-03 (contract gaps G1 comparison arms, G3 tolerance and equivalence, G6 compute metadata of the blind-02 science route); requirements from science steps s13 to s23. Arms are published programs or configurations that need no new code, run by the pipeline from sealed argument vectors. Each invocation runs one arm on one input, and invocations are interleaved on one box. No agent computes a number: every number comes from the pipeline's trusted wall time, from rules fixed before the run and applied by the pipeline, from a trusted comparator of two arms' outputs, or from a published evaluator that runs on each arm's output without access to the arm's identity. Criteria, margins, thresholds, reference values and timeouts are fixed by a science step before the run, sealed, and unreadable by the run's agents and by the processes of arms and evaluator. Compute is recorded twice and never mixed: per invocation as attribution and per box allocation as the bill. Never change a criterion after a result: every decision uses the sealed design. An outcome that is not supported is a result and never fails a stage. Comparisons that need more than one run are split by the science step into one design per run; a design whose launch depends on an earlier run's outcomes is launched only when the science step finds them in that run's `C/comparison_scored.json`. Without `args.comparison`, every stage is unchanged. Declared residual risks, which no rule below removes: the evaluator reads the arm's output files by design, so file names or content under `out/` that identify the program can reach it (the sealed `evaluate.sh` bytes make any dependence on them auditable after the run); state of shared hardware (device memory, caches, timing) is not cleared between parts; and a harness script that disobeys the rule that only `fetch_private.sh` handles the evaluator's private data can leave a transformed copy of them (an archive, a re-encoding, a derived file) where the arm part can read it, which the byte-identity check of Separated users step 7 does not detect (`setup.sh` and its repairs are kept in `A/harness/` and the stage's receipts, so such a copy is auditable after the run).
- Optional `args.comparison` is an object with exactly the key `design`: a non-empty path, resolved relative to the pipeline working directory, to a design JSON file. It is exclusive with `args.card`, `args.units_check` and `args.units_probe`. The design is exactly `{arms, inputs, outputs, metrics, evaluator, replicates, warmup, order_seed, timeout_s, budget_s, bootstrap_seed, bootstrap_resamples, comparisons}`:
  - `arms`: 2 to 5 items, each exactly `{id, what, commands, env}`; ids `"A0"`, `"A1"`, ... in order; `what` a non-empty string. `A0` is the published baseline that intake and reproduce handle as usual.
    - `commands`: 1 to 8 commands, each a non-empty array of non-empty strings: the exact published command lines of the arm, in order, as argument vectors run without a shell. The pipeline runs them (see Evaluate); the arm's adapter only prepares.
    - `env`: null or an object mapping names that match `^[A-Z_][A-Z0-9_]{0,63}$` and do not start with `CMP_` to strings; set for the arm's commands.
    - Placeholders, in command and `env` strings only: `{input}` (the input id), `{run}`, `{out}` (the absolute paths of the invocation's `run/` and `out/`) and `{spec:<p>}` with `<p>` a JSON Pointer (RFC 6901) into the input's `spec`, which must resolve in every input's `spec` to a string (inserted as is) or a finite number (inserted as `json.dumps` writes it). `{{` and `}}` stand for literal braces; any other `{` or `}` makes the design invalid. Substitution replaces every occurrence and is not repeated on its result.
  - `inputs`: 1 to 10 items, each exactly `{id, spec}`: `id` a unique string matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`; `spec` any JSON value (pins, case, configuration).
  - `outputs`: 0 to 10 items, each exactly `{name, what, format, select}`: a logical result each arm, or the evaluator, writes for an input, compared across arms. `name` unique, matching `^[a-z][a-z0-9_]{0,30}$`; `what` a non-empty string; `format` `"bytes"`, `"text_numbers"` (every number in the file's UTF-8 text, in order, as matched by `[-+]?(\d+\.?\d*|\.\d+)([eE][-+]?\d+)?` together with `nan`, `inf` and `-inf` tokens) or `"json_numbers"` (every number leaf of the JSON document, in document order; booleans are not numbers). `select` is null (the whole content) or, for `bytes` and `text_numbers` only, a Python `re` pattern with at least one capturing group: the content is read as UTF-8 with replacement, and the selected content is every group of every match of `re.finditer(select, text, re.MULTILINE)`, in order (an unmatched group as the empty string), joined by `"\n"`; `format` then applies to the selected content (`bytes` to its UTF-8 encoding). Several outputs may select different parts of the same file, each with its own comparison and tolerance.
  - `metrics`: 1 to 10 items, each exactly `{name, unit, what, source, reduce, expect_count}`: `name` unique, matching `^[a-z][a-z0-9_]{0,30}$`; `unit` and `what` non-empty strings; `source` `"trusted_wall"` or `"sealed_extraction"`.
    - `trusted_wall`: the invocation's wall seconds: the adapter's wall plus its commands' walls, plus the evaluator's wall when the design has an evaluator. `reduce` and `expect_count` are null.
    - `sealed_extraction`: read from fetched files by a rule the harness agent fixes before the run, reduced as the design states. `reduce` `"first"`, `"max"` or `"value_at_max_key"`; `expect_count` null or a positive integer, the number of matched values the rule must find.

With `"fail"`, a missing value of `arm` makes the unit `"not_supported"` with reason `"missing_values"`, and otherwise a missing value of `against` makes it void with reason `"missing_values"`.
  - Eligibility (`given`): for each listed comparison, its outcome for this unit is that comparison's row for the same input when both comparisons are decided per input, and otherwise that comparison's outcome, where `"per_input"` counts as supported only when every row is. When any of these is not `"supported"`, the unit is void with reason `"not_eligible"`.
  - Interval: for `all_pairs`, `[lo, hi]` is the minimum and maximum of the differences, and needs at least one difference. For `bootstrap`, the ratio of means is recomputed on `bootstrap_resamples` resamples (`B`) with replacement of the unit's paired replicates, drawn from one `random.Random(bootstrap_seed)` stream in comparison order, and `[lo, hi]` is the `(1 - confidence) / 2` and `(1 + confidence) / 2` empirical quantiles (sorted resamples, index `floor(q * (B - 1))`); it needs at least two replicates. `estimate` is the mean difference (`all_pairs`) or the ratio of means (`bootstrap`) on the full data. Too few values gives outcome `"void"` with reason `"insufficient_replicates"`.
  - Margin value `m`: 0 for a null margin, `x` for `{"abs": x}`.
  - Outcome per decision unit, in this order: eligibility; then, for agreement, any compared pair that disagrees makes the unit not supported; then the missing-value rule; then the interval's minimum count; then the criterion. The criterion gives `"supported"`, `"not_supported"` or else `"inconclusive"`: agreement is supported when at least one pair was compared, every compared pair agrees and none is missing (with no compared pair, it is void with reason `"missing_values"`); non-inferiority (`higher_better`) is supported when `lo >= -m`, not supported when `hi < -m`; non-inferiority (`lower_better`) is supported when `hi <= m`, not supported when `lo > m`; superiority (`two_sided`) is supported when `lo > m` or `hi < -m`, not supported when `-m <= lo` and `hi <= m`; ratio with `strict` false is supported when `lo >= threshold`, not supported when `hi < threshold`; ratio with `strict` true is supported when `lo > threshold`, not supported when `hi <= threshold`.
  - `sign` of a unit is `"higher"` when a superiority is supported with `lo > m`, `"lower"` when it is supported with `hi < -m`, and null otherwise.
  - A comparison's outcome: for `pooled_mean`, its one unit's outcome; for `per_input_all`, supported when every input is supported, not supported when any input is not supported, void when any input is void and none is not supported, otherwise inconclusive; for `per_input_each`, `"per_input"`, with each input's outcome in its rows.
  - `C/comparison_scored.json`, atomic, is exactly `{comparison_sha256, comparisons, totals}`. `comparisons` follows the design's order, each exactly `{id, arm, against, criterion, unit, outcome, rows}`; `rows` has one row per decision unit (`input` null for `pooled_mean`), each exactly `{input, n, n_missing, estimate, lo, hi, margin_value, threshold, outcome, sign, reason, pairs}`. `n` counts the differences, ratios or compared pairs; `pairs` is null for metric comparisons and, for agreement, the per-replicate rows `{replicate, agrees, missing, max_abs_error, max_rel_error}` (`agrees` null and `missing` true when a side is missing). Numbers are null when void; `reason` is `"missing_values"`, `"insufficient_replicates"` or `"not_eligible"` for a void unit, `"missing_values"` for a unit made not supported by the `"fail"` rule, and null otherwise. `totals` is exactly `{supported, not_supported, inconclusive, void}`, counting decision units over all comparisons.
  - Exit 0 after writing; exit 1 for invalid or missing input, a seal mismatch or a failed write, with no output file. A missing or invalid `wrap.json` or fetched file is not invalid input; it is a missing value. Diagnostics contain no input content. A scoring failure fails evaluate with `error_class: parse`.
- Evaluate status in comparison mode is PASS once `C/comparison_scored.json` was written, whatever the outcomes. Evaluate facts keep every existing key, null in comparison mode.

## A/results/profile/ and A/profile-packet.json
- Profile fetches remote `out/` to `A/results/profile/out/`; logs are `A/results/profile/<receipt-id>.log`. Its inputs are therefore under `A/results/profile/out/profile/`. Remote `out/profile/` is cleared before profiling to prevent stale evidence from passing.
- The pipeline uploads trusted `m5/profile_nsys.sh`, `m5/profile_summarise.py` and the collected probe into remote `profiler/`. Through boxrun, it invokes `bash profiler/profile_nsys.sh harness/run_command.sh out/profile <budget_s>`. The profiler reuses `nsys` from PATH or NVIDIA installation paths. Otherwise it tries `nsight-systems-cli` with apt using only source files listed by the probe, without enabling commented repositories or adding sources. If unavailable, it downloads the official Ubuntu 22.04 amd64 CLI package `NsightSystems-linux-cli-public-2025.3.1.90-3582212.deb` from `https://developer.download.nvidia.com/devtools/repos/ubuntu2204/amd64/` into a temporary directory outside `out/` that is removed after installation (the package never reaches `out/` or fetched results), verifies the SHA-256 pinned in the script, installs with `sudo -n dpkg -i` and runs `sudo -n apt-get -f install -y` for dependencies using the image's existing sources without adding repositories. This fixed profiler installation is an exception to the setup-script installation restrictions above. The profiler prepends the discovered Nsight binary directory to PATH. Missing tools, installation failures and collection/export failures emit `M5_PROFILER_INFRA`, write `out/profile/infra.json`, and exit 2; the pipeline classifies these as `infra` without agent calls.
- Collection uses `nsys profile --trace=cuda,nvtx,osrt --sample=none` around the shared command without modifying its environment. An inner launcher measures only that command with a monotonic clock; installation, profiler finalization and CSV export are excluded. The command's output is preserved in `baseline.log` as well as its own saved logs. Export uses `nsys stats --report cuda_gpu_kern_sum,cuda_gpu_mem_time_sum,cuda_api_sum --format csv`. Raw report, CSV files, tool version, export log, `raw_wall_s.json` and `gpu_util_raw.jsonl` remain in `out/profile/`.
- `python3 m5/profile_summarise.py <out_dir>` deterministically writes the three existing profile files. CSV total time/duration units ns, us/µs, ms and s are converted to seconds. Known Nsight skips for absent kernel/memory/API activity count as zero; missing or malformed reports fail parsing. A report is a known skip when its CSV file carries Nsight's `SKIPPED` line and no header row, or when its CSV file is absent, empty or whitespace-only and `stats.log` in the same directory states that the report does not contain its own activity: `does not contain CUDA kernel data` for `stats_cuda_gpu_kern_sum.csv`, `does not contain GPU memory data` for `stats_cuda_gpu_mem_time_sum.csv`, and `does not contain CUDA trace data` for `stats_cuda_api_sum.csv` (U48). These are Nsight's own wordings; the earlier phrases `CUDA memory data` and `CUDA API data` never occur in Nsight output and no longer count as statements. Nsight Systems 2025 writes an empty file for a skipped report where earlier versions wrote none. An absent, empty or whitespace-only file without that statement for its own activity, and any other missing or malformed report, still fails parsing. Run evidence (blind-01 run9, 2026-11-01): the baseline ran to completion under the profiler with no CUDA activity and no capture problem; Nsight 2025 logged the three skips and wrote three empty summary files, and the summariser failed on a missing CSV header, so profile stopped with `parse` instead of reaching its numeric gate. Replay of the merged U48 summariser on run9's saved files (2026-11-01) still failed: Nsight states the memory and API skips as `GPU memory data` and `CUDA trace data`; with those wordings the summariser exits 0 and the gate reports `numeric` (other host time within 2% of total wall). Five rows are emitted: `kernels` (compute), `memcpy H2D` (transfer), `memcpy D2H` (transfer), `CUDA API host time` (other), and `other host time` (other). GPU seconds retain the raw kernel/transfer sums; host GPU seconds are null. Aggregate CSV reports do not identify critical-path intervals: if the four reported sums exceed measured wall, their wall allocations are scaled proportionally to fit. Other host time is the nonnegative wall remainder. These allocations are an aggregate approximation, not measured exclusive phase durations. No stage timestamps are invented; aggregate rows omit `start_s`, so stage utilisation remains null. No bound uses stage utilisation; same-GPU headroom comes from the concurrency probe.
- `stages.json` is an array of `{stage, wall_s, gpu_s}`, optionally including `kind`: `compute`, `transfer`, or `other`, and `start_s`: finite nonnegative elapsed seconds sharing the telemetry clock. Fixed profiler supplies `kind`; legacy rows without it remain accepted. `stage` is a non-empty string; `wall_s` is finite nonnegative seconds; `gpu_s` is finite nonnegative seconds or null and must be present. Fixed profiler wall allocations sum to measured wall without exceeding it; overlapping aggregate durations use the approximation above. Extra input fields are not copied to the packet. Empty arrays parse but fail the numeric gate.
- `total_wall_s.json` is an object with finite positive numeric `total_wall_s` in seconds. The sum of stage wall times must also be finite.
- `gpu_util.json` is an array of `{t, util}` samples collected with `nvidia-smi` during the measured run. `t` is finite nonnegative elapsed seconds; `util` is a finite GPU utilisation percentage in [0,100]. The fixed sampler records the mean across GPUs returned by nvidia-smi, then the summarizer retains only samples during the shared command and rebases monotonic timestamps to its start. A sample with zero utilisation is valid. Empty arrays parse but fail the numeric gate; missing files or malformed samples fail parsing.
- The deterministic pipeline writes `A/profile-packet.json` with exact keys:
  - `stages`: the validated timing rows, preserving optional `kind`, each augmented with `wall_fraction = min(1, wall_s / total_wall_s)`, `start_s`, and `mean_gpu_util` (fraction in [0,1], or null). When supplied, `start_s` must be measured on the telemetry clock. Legacy rows without `start_s` record null start and utilisation; stage order does not establish a measured telemetry window. Stage endpoints must remain finite. Stage utilisation is the arithmetic mean of telemetry percentages divided by 100 in `[start_s, start_s + wall_s)`; no samples means null. Never substitute GPU busy seconds for utilisation;
  - `total_wall_s`: the measured total;
  - `timed_fraction = min(1, sum(stage.wall_s) / total_wall_s)`;
  - `gpu_telemetry`: true only when the validated `gpu_util.json` array is non-empty; stage `gpu_s` values do not establish telemetry.
  - `gpu_count`: `C/box.json.gpu_count` when nonnegative integer, otherwise count parsed from allocation `type` (`gpu_<N>x_...`), otherwise the collected probe's `nvidia.gpus.length`. Unavailable inventory defaults conservatively to 1; an empty inventory records 0.
  - `concurrency`: the validated `concurrency.json` object (see Concurrency probe), or null when the probe did not run or its output is missing or invalid.
  - `host_only`: boolean (U49). True exactly when the profile shows no CUDA activity: the rows `kernels`, `memcpy H2D`, `memcpy D2H` and `CUDA API host time` are all present, each with `wall_s` 0 and `gpu_s` 0 or null, and `gpu_util.json` holds at least one sample and every sample's `util` is 0. Otherwise false, including for profiles without those rows.
- Profile facts are `{profile_complete, timed_fraction, gpu_telemetry}` plus common `tokens_known` and `gpu_busy_known`, plus optional `headroom`: the packet's `concurrency.factor` (finite positive ratio) or null, and optional `host_only`: the packet's `host_only` boolean, or null when no packet was written. Every executed profile stage emits `headroom` and `host_only`; both are optional in the v2 schema so older records stay valid, and both are null on SKIPPED/stub records. `profile_complete` is true when the command exits 0 and all three inputs validate, even when the numeric gate fails. The deterministic gate requires at least three stages, no process wrappers, `timed_fraction >= 0.9`, and `gpu_telemetry=true`. A stage is a process wrapper if its name contains a case-insensitive token `process`, `wrapper`, `telemetry`, `total`, or `overall` delimited by whitespace, underscores, hyphens, or string boundaries, or if its `wall_s` is within 2% of `total_wall_s` (inclusive). Any wrapper fails the gate, even alongside three internal stages. In a host-only profile (packet `host_only` true) the `other host time` row is exempt from the 2% test, though not from the name test: the fixed profiler computes it as the wall-time remainder, so with no CUDA activity it is the whole command by construction rather than a wrapper around measured stages. Every other gate condition applies to host-only profiles unchanged, and profiles that are not host-only are gated exactly as before. A host-only profile leaves the pipelining and multi-GPU bounds at 1 (no transfer or compute time); its whole-workload bounds come only from the concurrency probe. Run evidence (blind-01 run9, replayed on its saved files 2026-11-01): the published baseline is CPU-only; Nsight recorded no CUDA kernel, memory or API activity, GPU utilisation was zero in every sample, and `other host time` was the whole command, so the 2% test failed the gate as `numeric` and the concurrency probe never ran. Owner decision 2026-11-01: CPU-only baselines are in scope. Numeric gate failures preserve the packet and use `error_class: numeric`; missing or invalid files use `error_class: parse`. A failed gate or parse stops downstream work without a profile repair.

## Concurrency probe: calibration of same-GPU headroom
- Purpose: measure, before any prediction or method exists, how much more throughput one GPU gives when the unchanged published command runs several times at once. This measured factor is the only source of same-GPU headroom for bounds. No model call is involved.
- When the profile command exits 0 and the profile gate passes, the pipeline uploads trusted `m5/concurrency_probe.py` to remote `profiler/` and, through boxrun as operation `concurrency` with the resolved `profile` budget, runs `python3 -I profiler/concurrency_probe.py harness/run_command.sh out/concurrency <budget_s>` from the shared run directory. Remote `out/concurrency/` is cleared first. Fetched files land in `A/results/profile/out/concurrency/`; the log is `A/results/profile/<receipt-id>.log`. There is no agent repair and no execution retry. Probe receipts count toward profile v1 `usd` and `gpu_s` like other box receipts.
- Each invocation runs `bash harness/run_command.sh` with its working directory set to a fresh `concurrency-work/<label>/` under the shared run directory. That directory holds a symlink to every top-level entry of the shared run directory except `out`, `profiler`, `concurrency-work` and `evaluation-work`, plus an empty `out/` directory. Labels are `single-1`, `single-2`, `single-3`, `n2-1`, `n2-2`, `n4-1` to `n4-4`. Each invocation's stdout and stderr go to `out/concurrency/logs/<label>.log` of the shared run directory. The environment is inherited unchanged apart from the MPS variables below. Nsight is not used.
- MPS: when `nvidia-cuda-mps-control` is on PATH, the probe starts a user-level daemon (`nvidia-cuda-mps-control -d`) with `CUDA_MPS_PIPE_DIRECTORY` and `CUDA_MPS_LOG_DIRECTORY` set to fresh directories under `concurrency-work/`, passes both variables to every invocation, and stops the daemon (`echo quit | nvidia-cuda-mps-control` with the same variables) before exiting, including after failures and on SIGTERM. If the daemon fails to start or any invocation fails under MPS, the probe stops the daemon, records `mps_failed: true`, and repeats the complete probe once without MPS in fresh work directories. Without the binary there is no MPS and `mps_failed` is false.
- MPS use is verified, not assumed. The daemon's `control.log` in its `CUDA_MPS_LOG_DIRECTORY` records each client connection as a line containing `NEW CLIENT <pid> from user <uid>`. After each single run and each batch under MPS, the probe counts these lines (case-sensitive substring `NEW CLIENT `, followed by an integer pid and ` from user `). The count must have grown by at least the number of copies just run (1 for a single run, n for a batch of n). A missing or unreadable log, or a smaller increase, means the copies did not run under MPS: the probe treats this like an invocation failure under MPS (stop the daemon, `mps_failed: true`, repeat the complete probe once without MPS). `mps: true` is therefore recorded only when every counted measurement was verified to run under MPS. No log content enters `concurrency.json`.
- Sequence: three single runs one after another, then 2 copies started together, then 4 copies started together. Wall seconds come from a monotonic clock around each subprocess; a batch's wall runs from launching its first copy to the exit of its last. `T1` is the median of the single walls. A single run that exits nonzero stops the probe with a null factor. Before each batch, the batch is skipped when `n * T1` exceeds `0.9 * budget_s` minus the probe's elapsed seconds. A batch counts only when every copy exits 0. For a counted batch, `factor_n = n * T1 / wall_n`.
- `out/concurrency/concurrency.json` is written atomically with exactly `{mps, mps_failed, single_wall_s, batches, factor}`:
  - `mps`: boolean, true when the recorded measurements ran under MPS; `mps_failed`: boolean;
  - `single_wall_s`: array of exactly three entries, each a finite positive number or null (failed or not run);
  - `batches`: exactly two rows, in order n=2 then n=4, each exactly `{n, wall_s, all_ok, skipped, factor}`; `wall_s` and `factor` are finite positive numbers or null, `all_ok` and `skipped` are booleans, and `factor` is null unless the batch counted;
  - `factor`: the largest counted `factor_n`, or null when any single run failed or no batch counted.
  The probe exits 0 whenever it writes the file, including with a null factor, and 2 when it cannot. It does not check output correctness: it measures throughput only.
- The probe never fails the profile stage and never changes the profile gate. A probe timeout, nonzero exit, or missing or invalid file gives packet `concurrency: null` and `headroom: null`. The pipeline validates the file against the exact shape above before copying it into the packet.
- Unit mode (U50b). The probe script's second form, `python3 -I profiler/concurrency_probe.py --units <run_units_file> <units_json> <out_dir> <budget_s> <reference_json>`, runs unit mode. Only the standalone unit probe (U52) invokes it; the profile stage always runs command mode exactly as described above (owner decision 2026-11-02: the standalone route; unit mode inside the profile stage is deferred). Unit mode never uses MPS and does not look for the MPS binary. It compares the same four units run in one invocation, as separate invocations one after another, and as separate invocations at once, holding inputs and per-unit configuration fixed and checking every output byte for byte. Owner decision 2026-11-01: the smallest bounded experiment that resolves whether a CPU-only baseline's units gain throughput when run at once, with only the pipeline changes that comparison needs. Reader evidence (blind-01 run9): units are distinct inputs, selectable by restricting the prepared input list to original records (the command-line selector has no effect); each unit writes its own result files at the same paths in full and subset runs, with no run-specific content, and its outputs repeat bit for bit; the reproduce logs record every unit's cost; whether a unit reads state left by earlier units of the same invocation is unknown, which the comparison with the recorded baseline tests; four median-cost units selected on their own reproduced run9's recorded result files byte for byte (run10, U51); units take 1 to 10 min with a cost spread over 50%; the baseline's own threads already use at least half the logical CPUs. Command mode would instead run three whole commands of 1 to 2 h and compare no outputs.
- Sample: units sorted by `cost_s` ascending, ties by manifest order; the sample is the four consecutive sorted units starting at sorted position floor((N - 4) / 2), N being the number of units, kept in that order as sample positions 0 to 3. Units near the median cost keep concurrent invocations of similar length, so a batch runs at its full width for nearly its whole wall time; the factor therefore describes typical units, not the shortest or longest.
- Arms run in this fixed order, every invocation in a fresh work directory built as in command mode (named `<label>` for an arm with one invocation, `<label>-<j>` for invocation j = 1, 2, ... of an arm with several):
  - `a-1`: one invocation `bash harness/run_units.sh <id0> <id1> <id2> <id3>` (sample order), the baseline's own serial mode;
  - `b-1`: four invocations of one unit each, one after another in sample order;
  - `c2-1`: sample units 0 and 1 started together, then, after both exit, units 2 and 3 started together;
  - `c4-1`: all four started together;
  - `c4-2`, `c2-2`, `b-2`, `a-2`: the same arms again in reverse order, to balance drift.
  Each invocation's stdout and stderr go to `out/concurrency/logs/<work directory name>.log` of the shared run directory, and its environment is inherited unchanged. An arm's wall runs on a monotonic clock from launching its first invocation to the exit of its last.
- Output checks. The reference file `<reference_json>` is exactly `{"sha256": {<output path>: <64 lowercase hex digits>}}`, keyed by every output path of the four sample units and nothing else. After `a-1`, every output path of every sample unit under `a-1`'s `out/` must exist and have the SHA-256 recorded for that path (`baseline_match`); a file missing under `a-1`, a path missing from the reference, or a reference file that is unreadable or not of that shape is a mismatch. When `a-1` exits nonzero or `baseline_match` is false, no later arm runs. After every later invocation, its units' output files must be byte-identical to `a-1`'s (`outputs_match`, true when every later executed invocation matched). An arm counts when all of its invocations exit 0 and all of their compared files match.
- Budget: before each arm, that arm and every later arm are skipped when its estimate exceeds `0.9 * budget_s` minus the probe's elapsed seconds. The estimate is the sum of the sample's `cost_s` for `a-1`, and `a-1`'s measured wall for every later arm.
- Resource use. For each invocation, from `os.wait4` on its process (which includes its waited-for descendants): `cpu_s` (user plus system seconds), `max_rss_kb`, `nivcsw` (involuntary context switches), `inblock` and `oublock`. For each arm, sampled about once a second while it runs: `busy_fraction` (mean non-idle share of total CPU time from `/proc/stat`, idle including iowait), `mem_available_min_kb` (the minimum `MemAvailable` from `/proc/meminfo`) and `threads_max` (the largest sum of `Threads` from `/proc/<pid>/status` over the processes of the arm's invocations; each invocation starts its own session and process group). An arm's `cpu_s` is the sum over its invocations and `effective_cores` is that sum divided by the arm's wall. Memory bandwidth and caches are not measured.
- Shared writes. Each arm records `shared_changes`: the number of non-directory entries under the shared run directory, outside `out/`, `concurrency-work/` and `profiler/`, that appeared, disappeared, or changed size or modification time (nanoseconds) between a snapshot taken just before the arm's first launch and one taken just after its last exit. Snapshots use `lstat` and never follow symbolic links, and are taken outside the arm's wall clock. Readers of run10 (`run10_post`, `run10_post2`) found that the measured command writes into the shared run directory, which concurrent invocations reach through their links, but could not establish which paths, how they are named or whether units read them back; the byte checks catch only collisions that change compared outputs or fail an invocation. The count is evidence for interpreting a factor, not a check: it never changes an outcome. Writes outside the shared run directory are not observed.
- In unit mode `out/concurrency/concurrency.json` is written atomically with exactly `{mode, mps, mps_failed, outcome, units_total, sample, baseline_match, outputs_match, serial_wall_s, separate_wall_s, batches, arms, nproc, mem_total_kb, factor}`:
  - `mode`: `"units"`; `mps` and `mps_failed`: false;
  - `outcome`: the first that applies of `"invalid_units"` (manifest unreadable, invalid or with fewer than four units), `"failed"` (an executed invocation exited nonzero), `"baseline_mismatch"`, `"outputs_mismatch"`, `"skipped"` (no `c2` or `c4` arm counted), otherwise `"measured"`;
  - `units_total`: N, or null for `invalid_units`; `sample`: four rows `{index, cost_s}` in sample order, `index` being the manifest position, or `[]` for `invalid_units`. No unit identifier or output path appears in the file;
  - `baseline_match` and `outputs_match`: booleans, or null when not evaluated;
  - `serial_wall_s`: the mean wall of the counted `a` arms; `separate_wall_s`: the mean wall of the counted `b` arms; each a finite positive number or null;
  - `batches`: exactly two rows, n=2 then n=4, each exactly `{n, wall_s, all_ok, skipped, factor}`: `wall_s` is the mean wall of the executed `c<n>` arms or null when none ran, `skipped` is true when none ran, `all_ok` is true when at least one ran and every executed one counted, and `factor` is `serial_wall_s / wall_s` when `all_ok` is true and `outcome` is `measured`, otherwise null;
  - `arms`: exactly eight rows in the fixed order, each exactly `{label, wall_s, all_ok, skipped, cpu_s, effective_cores, busy_fraction, mem_available_min_kb, threads_max, shared_changes, invocations}`, with `label` from `a-1` to `a-2`; numbers are finite and nonnegative (`shared_changes` an integer), or null when the arm did not run; `invocations` lists the executed invocations in launch order, each exactly `{units, rc, wall_s, cpu_s, max_rss_kb, nivcsw, inblock, oublock}`, `units` being sample positions;
  - `nproc`: `os.cpu_count()`; `mem_total_kb`: `MemTotal` from `/proc/meminfo`;
  - `factor`: the largest non-null batch factor, or null.
  The factor compares the baseline's own serial mode with concurrent invocations over the same units, so per-invocation start-up costs count against it; `separate_wall_s` minus `serial_wall_s` shows that cost. The probe exits 0 whenever it writes the file and 2 when it cannot.
- The standalone unit probe (U52) validates a unit-mode file against the exact shape above, including each batch factor and `factor` as the largest batch factor. A measured unit-mode factor below 1.05 is a valid negative finding.

## C/receipts/ and stage failure signatures
- Every box command (uploads, probe, setup attempts, anchor execution, profiling, implementation) runs through `m5/boxrun.sh`; every receipt is `C/receipts/NNNN-<operation>.json`. Operations are `upload`, `probe`, `setup`, `anchors`, `profile`, `concurrency`, `implement-baseline`, `adapter-smoke`, `implement-state`, `implement-upload`, `implement-patch`, `setup-method`, `run-method`, `run-tests`; numbering continues across existing receipts. Receipt/log IDs contain no benchmark labels.
- Receipts use the boxrun format: `{name, rc, timed_out, wall_s, budget_s, overrun, fetched, started_utc, ended_utc, gpu_busy_s, gpu_busy_known}`. `name` is the receipt ID; `rc` is an integer remote exit code or null; `timed_out` and `fetched` are booleans; `wall_s` is nonnegative integer elapsed seconds; `budget_s` is the positive integer timeout supplied to boxrun; `overrun` is boolean, true on timeout or when measured wall_s exceeds budget_s; timestamps are UTC strings. Remote `out/` is fetched using the unchanged boxrun interface. After the remote command finishes, boxrun fetches remote `out/` and then the operation log; a fetch that fails is retried up to four more times, waiting 60 s before each retry (environment `BOXRUN_FETCH_WAIT_S` overrides the wait, for tests), and `fetched` is true only when both fetches succeed. A retry repeats only the fetch, never the remote command. Retry waits count in `wall_s`. Receipt contents stay in control; runtime logs stay in agent results.
- Incremental fetch (U53). The fetched result is unchanged: after a successful fetch, `<--to>/<--fetch>/` holds exactly the regular files of remote `<--remote-dir>/<--fetch>/` at fetch time, at the same relative paths with the same bytes, and nothing else, symbolic links followed as `scp -r` follows them. What changes is the transfer: files unchanged since the previous fetch from the same remote directory are not sent again. With an injected `FETCH`, boxrun calls it exactly as before and keeps no mirror. Without `FETCH`, boxrun keeps a local mirror per remote directory at `<mirror root>/<base name of --remote-dir>/<--fetch>/`; the mirror root is `$BOXRUN_MIRROR_ROOT` when set (for tests), otherwise `$HOME/.cache/metis-serve/fetch-mirror`. Each run's remote directory is a fresh `/tmp/m5-<uuid>`, so mirrors never mix runs; the mirror lies outside the run root and is never fetched results or committed, and boxrun never deletes mirrors. Each fetch attempt of `<--fetch>` (the first and each retry) first runs `rsync` from PATH with options `-rLt --delete -z`, `-e` followed by the same ssh command and options the existing fetch uses (key, `ConnectTimeout`, `ServerAliveInterval`, `BatchMode`), and as its last two arguments the source `ubuntu@<ip>:<--remote-dir>/<--fetch>/` and the mirror directory with a trailing slash (created first when missing). When rsync exits 0, boxrun copies the mirror into `<--to>/<--fetch>/` so that it holds exactly the mirror's files (a local copy, never a transfer) and the attempt succeeds. When rsync exits nonzero (for example when the box lacks rsync), the same attempt falls back to the existing `scp -r` copy into `<--to>`, unchanged, and succeeds or fails as that copy does; a fallback leaves the mirror as rsync left it, so the next fetch may resend files. The operation log fetch (`<--remote-dir>/<name>.log`) is unchanged. Retries, waits, `fetched`, receipts, exit codes and every caller are unchanged; the pipeline still clears local fetched folders before each command as before. Run evidence (blind-02 run2, 2026-11-02; authorized reader `run2_progress2`): every box command fetched the whole remote `out/` again, including outputs unchanged since the previous command; after reproduce the remote `out/` held about 745 MB in 2,517 files, each fetch took about 23 min (the profile stage's upload of two small scripts took 1,424 s), box time was dominated by output fetches, and the reader projected the run to exceed its 12 h ceiling.
- Failed reproduce/profile signatures have fixed `error_class`: `infra` for unavailable box execution/receipts, failed upload, or failed fetch after a successful command, or a fixed profiler infrastructure marker; `install` for failed setup after the bounded repairs; `anchor` for an anchor-run failure or a failed anchor; `parse` for missing/invalid output files, unavailable harness files, or a nonzero profile command exit; `numeric` for a parsed profile that fails the stage-count, process-wrapper, coverage, or GPU telemetry gate. Exit codes are 4 for anchor failures, 3 for timeouts and 2 for the other failures. `infra` is added to the shared v1 error-class enum so the v2 envelope remains v1-valid. Box/fetch stdout and stderr are never copied into operator signatures.
- Any box receipt with rc=124 or timed_out=true records a timeout, even when fetch fails. A final timeout fails its stage with `error_class: timeout`, exit 3. Authored setup and anchor scripts consume their existing repairs (at most four for setup, two for anchors), and method/test scripts their one bounded repair; method/test timeout repairs expose only the fixed timeout count plus budget/elapsed/overrun seconds, never test content. Transport, patch, probe, integrity and immutable evaluator commands permit one identical retry under the same budget (under keys `setup`, `anchors` and `profile`, the budget resolved at the retry's start, U47), without editing scientific payloads or trusted scorers. A second timeout stops that operation and stage. The fixed profiler permits no repair or execution retry; its first timeout stops profiling with `error_class: timeout`.
- Reproduce, profile, implement and evaluate facts optionally add exactly typed timeout fields `{timed_out: boolean, budget_s: nonnegative integer, overrun: boolean}` when a box timeout occurs. `timed_out=true` records any attempt timing out, `budget_s` is the latest timed-out command's budget, and `overrun` is true when any timed-out receipt overruns. These fields survive a successful bounded repair; stage status then reflects the repaired result. Older records and SKIPPED/stub records retain their existing fact keys. No command output or new free-text fields enter signatures.
- Numeric ratio facts accept finite JSON numbers, including integer spellings such as `0` and `1`; booleans remain invalid. This permits fully timed profiles to emit the capped fraction `1`.
- Every stage records its own elapsed wall-clock seconds in v1 `wall_s`, excluding signature emission. SKIPPED stages measure only their skip handling, never the prior stage's duration.
- Runner results add boolean `tokens_known`, true when the provider reports input/output usage (including reported zeros). wf exposes `agent.usage()` as a cumulative snapshot `{calls, tokens_in, tokens_out, unknown}`; `unknown` counts runner attempts without usage. Repairs, failed attempts, shadow calls, and fallbacks all contribute; cached calls do not incur usage. Compatible runners without `tokens_known` are accepted when their input/output counts are integers.
- Stages aggregate reported input/output counts into v1 `tokens_in`/`tokens_out`; `facts.tokens_known` is true only when every runner attempt in that stage reports usage. With no attempts, existing unknown/null facts remain unchanged. Unknown counts retain numeric zero placeholders required by v1. `gpu_busy_known` reflects box receipt telemetry for reproduce/profile (see Compute metadata); harness profile evidence is reported separately. Downstream scientific stages are skipped after either failed gate; takeaways still runs.

## A/bounds.json (computed before the seal agent)
- `python3 m5/bounds.py <profile-packet.json> <out.json>` writes an atomic JSON object keyed by the five menu methods. Each value is `{p, k, bound, feasible, k_derivation, stages}`. `stages` contains actionable rows `{stage, kind, wall_fraction, mean_gpu_util, methods}`; `methods` lists every menu method that acts on that stage: whole-workload methods act on every stage, the others on stages of their kind. Exit 0 means success; exit 1 means invalid/missing input or unavailable output, with content-free diagnostics. Legacy packets without `gpu_count` default to 1. GPU counts must be nonnegative integers.
- Explicit stage `kind` takes precedence. Without it, lowercase stage names are split into ASCII alphanumeric tokens. Any token `transfer`, `transfers`, `h2d`, `d2h`, `htod`, `dtoh`, `copy`, `memcpy`, `upload`, or `download` means transfer; otherwise any token `compute`, `kernel`, `kernels`, `inference`, `training`, `forward`, or `backward` means compute. All other names mean other. Other stages and unmeasured time remain serial.
- The fixed mapping and maximum factors are:

  | Method | Acts on | p | Maximum factor k | bound |
  | --- | --- | --- | --- | --- |
  | data-parallel over inputs | whole workload | 1 | min(8, factor) | k |
  | ensembles | whole workload | 1 | min(8, factor) | k |
  | batching | whole workload | 1 | min(4, factor) | k |
  | pipelining | transfer stages | transfer fraction | 2 | Amdahl |
  | multi-GPU | compute stages | compute fraction | max(1, gpu_count) | Amdahl / k |

- `factor` is the packet's `concurrency.factor`: the same-GPU concurrent throughput measured during calibration (see Concurrency probe). When the packet has no `concurrency` key, `concurrency` is null, or its factor is null or below 1, whole-workload methods use `k=1` (bound 1, infeasible): missing measurements never manufacture headroom. A `concurrency` value that is neither null nor an object, or a factor that is neither null nor a finite number, fails parsing.
- `Amdahl = 1 / ((1-p) + p/k)` with `p = min(1, sum(actionable stage.wall_s) / total_wall_s)`. Fractions are recomputed from timings, never trusted from supplied `wall_fraction`. The multi-GPU bound is speedup per GPU-second, `Amdahl / k`: the same equal-cost basis that evaluation applies (`cost_ratio <= 1`) against a one-GPU baseline. It exceeds 1 only with superlinear evidence, which Amdahl cannot supply. Zero GPUs uses `k=1`.
- `k_derivation`: whole-workload methods record `{rule:"min(fixed_cap, concurrency factor)", fixed_cap, factor, mps}` (`factor` and `mps` null when unavailable); pipelining records `{rule:"fixed_cap", fixed_cap:2}`; multi-GPU records `{rule:"max(1, gpu_count)", gpu_count, amdahl, cost_basis:"equal_gpu_seconds"}`. Stage `mean_gpu_util` is carried for information only and never sets a factor.
- These are ceilings for sealed intervals, not measured method improvements. The concurrency factor is the measured throughput of plain concurrent runs; method code may exceed it in evaluation, but sealed intervals may not. `feasible` is true exactly when `bound >= 1.05`.
- The seal and propose prompts describe the bounds this way: whole-workload bounds are measured concurrent throughput on one GPU; pipelining is Amdahl over transfer time; multi-GPU bounds are per GPU-second at equal cost.
- The pipeline regenerates `A/bounds.json` before sealing, reads it before the agent call, and supplies its path and contents in the seal prompt. Missing or invalid profile evidence fails sealing; stale bounds cannot substitute for it.

## A/PREDICTIONS.json (written by the seal agent; checked, then sealed)
- `predictions`: an array, one item per feasible method, with unique methods taken from the menu ["data-parallel over inputs", "batching", "multi-GPU", "ensembles", "pipelining"]. Each item has:
  - `expected_speedup_interval` with finite numbers satisfying `low > 0`, `low <= high <= bound`, and width `high-low <= bound-1` for that method;
  - `outcome_vs_compute_points`, holding for every value in compute_budgets one {compute_budget, predicted_outcome, uncertainty}, all non-empty. `predicted_outcome` and `uncertainty` must not be null, empty strings, or empty objects/arrays. When no numeric forecast is supported, use an explicit non-empty declaration such as `predicted_outcome={not_applicable:true,reason:"fixed-work benchmark; no calibrated outcome curve"}` and explain unavailable evidence in `uncertainty`. Do not invent a number. `equal_outcome_target.not_applicable` does not waive these point fields.
- `outputs_stochastic` is a required boolean. It is true for Monte Carlo, sampling, or outputs affected by random seeds, including reproducible fixed-seed runs.
- Stochastic seals require statistical `equivalence_metrics` with positive absolute margins and non-empty names/sources, `paired_seed_tests.kind="paired_median"` with unique integer seeds, and `confidence_rule.equivalence={kind:"paired_median",confidence}` with finite confidence in [0.5,1). The sealed significance level is `1-confidence`. Margins come from scientific requirements or baseline variability (for example Monte Carlo standard error); paired-difference confidence intervals must lie within the sealed margins. Exact/bitwise rules, zero margins, relative margins, deterministic seed declarations, and prose-only rules are rejected for stochastic outputs. The check reads executable fields only: evaluation applies each metric's `name` and numeric `tolerance`, so an exact or bitwise rule is a zero or missing absolute margin. Free-text metric fields (`comparison`, `kind`, `rule` and any others) are never scanned for words; statistical terms such as "exact binomial bound" are allowed. Exact or bitwise rules apply only to deterministic outputs.
- The seal agent reads `A/intake/`, `A/profile-packet.json`, `A/bounds.json` and the baseline's measured outputs under `A/results/reproduce/` (the fetched `out/`, logs and `anchors_scored.json`), and nothing else. A margin derived from baseline variability names, in its `source`, the measured file and the statistic used (for example the standard deviation of a per-seed outcome across the baseline's seeds). When neither a scientific requirement nor measured baseline variability supports a positive margin, the seal agent never invents one, and the seal fails `stochastic_equivalence_invalid` as before. The seal prompt states all three.
- Required non-empty keys: equivalence_metrics, paired_seed_tests, sample_sizes, confidence_rule, hardware_cost_basis, timing_scope, minimum_worthwhile_gain (a number > 1), evaluation_inputs, splits, compute_budgets (at least 3 distinct positive numbers), repetitions (an integer >= 5), warmup, scheduling_order, equal_outcome_target and baseline_invocation_s.
- `baseline_invocation_s` is `{seconds, source}`. `seconds` is a finite positive number: the expected process wall, from launch to exit, of one complete baseline equivalence invocation over all sealed seeds and inputs (what the implement adapter smoke measures), derived from the reproduce measurements. `source` is a non-empty string naming the measured file, the measured value and the arithmetic (for example two sequential eight-replica ensembles at the measured ensemble wall, plus process start-up). Any other shape is `protocol_incomplete`. The seal check projects one complete performance scorer at that estimate, with the adapter smoke's rule: `projected_s` = (`warmup` + `repetitions`) × 2 × `seconds`, plus, unless `equal_outcome_target.not_applicable` is true, `b / baseline_gpus + b / method_gpus` for each compute budget `b` (GPU counts from `hardware_cost_basis`). When at least one method is feasible and `projected_s` exceeds 0.9 × the resolved `evaluate` budget, the seal fails `protocol_cost`; a seal with no feasible method skips this check. The seal prompt states the resolved `evaluate` budget in seconds, this projection and the 0.9 factor, and says that `seconds` comes from the measurements and is never lowered to fit: the protocol fits through its choice of seeds, inputs, warmup, repetitions and compute budgets. The adapter smoke still measures the real cost.
- `infeasible_methods` is a required array of `{method, reason}`, exactly once for every method with `bound < 1.05`; reasons are non-empty strings. These methods must never appear in predictions. Every feasible method must appear exactly once in predictions and never in infeasible_methods. With at least two feasible methods, all prediction intervals must not be identical. One feasible method is exempt from this comparison.
- Seal failures use `error_class: numeric` (exit 2), including invalid protocol, invalid intervals, missing/duplicate method coverage, or unavailable bounds. Facts retain exactly `seal_present`, `seal_verified`, `prediction_count` plus common facts; `prediction_count` counts submitted prediction rows, excluding infeasible entries. An empty feasible menu may be sealed as a negative result: a verified seal with zero predictions (every menu method listed in `infeasible_methods`) PASSes the seal stage with `prediction_count=0` and `reason_codes: []`. Propose then decides whether the absence is a negative finding or missing measurements.
- The seal prompt embeds stochastic and deterministic JSON skeletons generated by `m5/seal_protocol.js`, using the same constants as its deterministic validation. Both specify `equivalence_metrics=[{name,source,tolerance:{abs:number}}]` with non-empty **string** names and sources, never citation objects. The stochastic example uses `paired_seed_tests={kind:"paired_median",seeds:[0,1,2,3,4,5]}` and a positive absolute margin; the deterministic example uses `{kind:"deterministic",justification:"scientific reason"}` and zero absolute tolerance. Both include `evaluation_inputs={ids:["held-out-1"]}`, matching `sample_sizes={inputs:1,seeds:6}` (stochastic) or `{inputs:1,seeds:1}` (deterministic), `confidence_rule={performance:{kind:"paired_median",confidence:0.95},equivalence:{kind:"paired_median",confidence:0.95}}`, and `baseline_invocation_s={seconds:<placeholder number>,source:"<placeholder>"}`. Example metric names, sources, margins, identities and justifications must be replaced with supported scientific choices. Six seeds give finite two-sided 95% bounds for one metric; more metrics or higher confidence can require more seeds. Deterministic evaluation uses one null seed.
- One bounded repair is allowed for a readable but invalid protocol or a missing/malformed predictions file, before any immutable seal files are written. Initial `seal` and optional `seal-repair` calls use `ls-writer`, requested model `sonnet`, `repairable:false`, `fresh:true`; runner-level repair is disabled. The repair prompt supplies only script-owned failing reason codes and field paths as validation feedback, without values, evidence, bounds, measurements, exception text or model commentary. The agent may read and rewrite only `A/PREDICTIONS.json`, preserving scientific intent without inventing evidence or loosening tolerances. The complete deterministic checks run again exactly once; failure stops, success proceeds to the existing seal writer. Bounds generation, agent execution, seal storage/verification failures and verified negative results do not trigger repair. Repair never allocates a seal number or modifies prior receipts/frozen predictions. No field paths or feedback enter operator signatures. For `protocol_cost` the field paths are `warmup`, `repetitions`, `paired_seed_tests.seeds`, `evaluation_inputs.ids`, `compute_budgets` and `baseline_invocation_s`, and the repair prompt also restates the resolved `evaluate` budget in seconds and the projection rule from the seal prompt; it supplies no other value.
- `C/stages/seal.json` adds `reason_codes`, an array containing the final failed check's fixed code, or `[]` for PASS, SKIPPED, and stub results. Checks stop at the first failure, in the order below. Exceptions use the code for the operation/check in progress. Codes are script-owned literals; no agent text, exception messages, methods, paths, or scientific content enter this field. Existing numeric error class, exit code, signature facts, and immutable seal receipt format are unchanged.

  | Code | Failed check or operation |
  | --- | --- |
  | `bounds_generation_failed` | Regenerate and read bounds from the profile packet. |
  | `agent_failed` | Seal agent threw or returned no reply. |
  | `predictions_read_failed` | Read and parse the predictions file. |
  | `predictions_invalid` | Predictions object must contain a predictions array. |
  | `protocol_incomplete` | Required fields, stochastic flag, budgets, repetitions, worthwhile gain, unique menu methods, or finite positive ordered intervals are invalid. |
  | `compute_points_incomplete` | Every predicted method needs a point at every budget with non-empty outcome and uncertainty. |
  | `stochastic_equivalence_invalid` | Stochastic paired seeds, confidence rule, or positive absolute statistical margins are invalid. |
  | `protocol_cost` | With at least one feasible method, one complete performance scorer projected at `baseline_invocation_s` exceeds 0.9 × the resolved `evaluate` budget. |
  | `bounds_coverage_invalid` | Feasible prediction coverage or infeasible exclusions/reasons are invalid. |
  | `interval_bounds_invalid` | An interval exceeds its bound or its allowed width. |
  | `intervals_identical` | At least two methods are feasible but all intervals are identical. |
  | `seal_write_failed` | Canonicalize/write predictions and create the immutable seal files. |
  | `seal_verification_failed` | Read/hash verification of the current and frozen predictions failed. |

- Seal: C/seals/NNNN.json {sha256, path, utc}. The sha256 is over the canonical JSON: keys sorted recursively, array order kept, compact separators, UTF-8. Numbering continues; nothing is overwritten.

## Propose, independent votes, and the one-shot gate
- Before reading profile/bounds or calling any agent, propose selects the highest-numbered `C/seals/NNNN.json` and hashes the exact bytes of both `A/PREDICTIONS.json` and the receipt's frozen `path`. Both must match `sha256`. A missing, unreadable, or mismatched seal fails with `error_class: other` (exit 2), with no model calls.
- The deterministic step reads `A/profile-packet.json`, `A/bounds.json`, and the verified predictions. Feasible predicted methods have `bounds[method].feasible=true` and `bound >= 1.05`. Their ranking score is `min(low/2 + high/2, bound)`, descending; ties follow the fixed menu order. Unknown/duplicate methods or malformed intervals fail parsing.
- Resource guards use `C/box.json.gpu_count` when supplied (a nonnegative integer), otherwise the count in allocation `type` such as `gpu_1x_a10`. Probe capacity is `A/results/probe/probe.json.nvidia.gpus.length`. Available GPUs are the smaller count; either inventory unavailable means no method passes. Ordinary methods require one GPU; multi-GPU requires `max(2, bounds[method].k)` GPUs, matching the factor used for its bound. Methods failing these guards are excluded from selection.
- `A/propose-packet.json` contains only `{ranked_methods, stage_to_method, bounds, sealed_equivalence_rule}`. Ranked rows are `{method,bounds}` in deterministic ranking order, restricted to feasible resource-safe methods. `stage_to_method` contains every stage as `{stage,wall_fraction,mean_gpu_util,methods}`; other stages map to an empty method list. `bounds` contains all five bounds and their `k_derivation` and actionable stages. `sealed_equivalence_rule` contains only `outputs_stochastic`, `equivalence_metrics`, `paired_seed_tests`, `sample_sizes`, and the equivalence portion of `confidence_rule`. No raw profile, predicted outcome curves, intake, resource inventory, performance protocol, or other content enters the packet. Prompts state that ranked methods already passed deterministic GPU resource guards. Proposer and all five skeptics receive the identical packet; skeptics additionally receive the validated proposal. When no feasible resource-safe method remains (including a verified seal with zero predictions), propose makes no model calls, writes `A/propose-packet.json` and `A/GATE.json` as usual, and keeps `method="none"`, `expected_speedup=null` and `gate_pass=false`. The absence is a negative finding exactly when it rests on measurements: the profile packet's `concurrency.factor` is a finite number; its MPS state is verified, meaning `concurrency.mps` is true, or `concurrency.mps` and `concurrency.mps_failed` are both false (MPS absent from the box); and both GPU inventories used by the resource guards (box and probe) are available with at least one GPU each. Then the stage PASSes with `outcome="no_feasible_method"`; implement and evaluate are SKIPPED with null facts, takeaways runs, and the run's stop point is propose. Otherwise (concurrency missing, null or not finite; `concurrency.mps_failed` true, meaning MPS exists on the box but the measurement could not use it; or either GPU inventory unavailable or reporting zero GPUs) the absence reflects missing measurements: the stage FAILs with `numeric` (exit 2) as before and `outcome` stays null. The finding is bounded: no method on the fixed menu has measured headroom of at least 1.05 on this hardware (concurrency factor of plain concurrent copies, GPU count, measured transfer share). It does not show that no method could speed up the workload.
- One `propose` call (`ls-writer`, requested model `sonnet`) reads only the embedded packet and writes `A/proposal.json`, with exactly `{method, rationale, plan_steps, files_expected, risks}`. `method` must be in the ranked list; `rationale` is a non-empty string; the remaining fields are arrays of non-empty strings. `plan_steps` and `files_expected` must be non-empty; `risks` may be empty. The call cannot implement code or access the box. Invalid/missing proposals fail with `error_class: parse` (exit 2).
- Five concurrent skeptic calls (`qt-bare`, requested model `haiku`, mapping to the cheap tier) each start a fresh session. Ballot `i` uses label `skeptic-<i>`, so names are `x-<raid>-skeptic-1` through `x-<raid>-skeptic-5` with no sibling suffix. Each receives the same prepared packet and validated proposal, plus its ballot number, and no other votes. Model family/endpoint selection remains with the workflow configuration (see m5 model policy); the pipeline pins no endpoint.
- Ballots have exactly `{vote, reason_codes}`. `vote` is `approve`, `reject`, or `abstain`; `reason_codes` is an array (possibly empty) containing only `exceeds_bound`, `not_parallelisable`, `changes_method`, `equivalence_risk`, `resource_mismatch`, `weak_profile_evidence`, or `other`. The pipeline writes `A/votes/1.json` through `5.json`; missing/failed/invalid responses are written as JSON `null` (null ballots). No vote repair or replacement is allowed.
- Ballot meanings. `reject` names a defect that would make the proposed method fail as planned: it exceeds its bound, cannot be parallelised as planned, changes the sealed method, risks breaking the sealed equivalence rule, or mismatches the resources (codes `exceeds_bound`, `not_parallelisable`, `changes_method`, `equivalence_risk`, `resource_mismatch`, or `other`). `abstain` means the packet is insufficient to judge (typically `weak_profile_evidence`); it is not a judgement against the method. `approve` means no defect is found and the evidence is adequate. The skeptic prompt states these three meanings and that missing or weak evidence warrants abstain, not reject. The gate counts only the `vote` field; reason codes never reclassify a ballot. Skeptic review records evidence about the proposal; a vote count is not scientific ground truth, and execution plus independent evaluation decide the claim.
- These calls use wf option `repairable:false`: no repair turn, schema/no-JSON failures cannot trigger fallback, panels are bypassed, and shadow mode becomes fallback. Transport failures can still use the configured family chain. This preserves existing default behavior for other calls. `fresh:true` bypasses the resume cache for proposer and skeptics; every ballot starts a new runner session.
- `A/GATE.json` records the propose facts. Its presence prevents another proposal/vote round in the same run (fails with `other`). Gate requires at most one ballot that is a rejection or null (abstentions never count against the gate, and no minimum number of approvals applies), the selected sealed interval's `high >= minimum_worthwhile_gain`, `high <= bound`, and passing resource guards. Gate failures use `numeric` (exit 2); malformed inputs use `parse`. Downstream stages skip after failure; takeaways still runs.
- Facts have exactly `{method, expected_speedup, votes_approve, votes_total, vote_share, gate_pass}` plus common `tokens_known` and `gpu_busy_known`. `method` is a menu entry or `none`; `expected_speedup` is the selected sealed interval midpoint, or null before selection. Executed stages initialize `votes_approve=0`, `votes_total=5`, `vote_share=0`, and `gate_pass=false`; `vote_share=votes_approve/5`. Missing votes never reduce the denominator. vote_share is diagnostic only. SKIPPED/stub stages retain the existing null facts contract. Scientific text and reason codes remain in the agent view.
- Propose facts add optional `votes_reject` and `votes_abstain` (nonnegative integers) and `outcome` (`"approved"`, `"rejected"`, `"conditions_unmet"`, `"no_feasible_method"`, or null). They are optional in the v2 schema so older records stay valid; every executed propose stage emits all three, initialised to 0, 0 and null, and SKIPPED/stub records hold null. Null ballots number `5 - votes_approve - votes_reject - votes_abstain`. Once ballots are counted: `outcome="approved"` exactly when the gate passes; `"rejected"` when two or more ballots are rejections or null; `"conditions_unmet"` when the ballot condition holds but an interval or resource condition fails. `"no_feasible_method"` is set only by the measured negative finding above, with all ballot counts 0. `outcome` stays null when the stage stops before ballots are counted for any other reason (seal, packet, proposal or parse failures, no feasible method without measurements, or an existing `A/GATE.json`). `OPERATOR_TAKEAWAY.md` shows `outcome` and the four ballot counts (approve, reject, abstain, null) in the propose row. Its null-ballot count is `5 - votes_approve - votes_reject - votes_abstain` only when ballots were counted (outcome `approved`, `rejected` or `conditions_unmet`); otherwise it shows null, because no ballot was requested. When propose has `outcome="no_feasible_method"`, it also adds the fixed line `Finding: negative. No menu method has measured headroom of at least 1.05 on this hardware.`; it adds no such line otherwise.

## Implement, frozen independent tests, and launch review
- `implement` verifies the latest seal against both prediction copies before doing work, and checks that the proposal selects a sealed method with equivalence metrics and a paired-seed protocol. It rechecks the seal before authoring, each attempt, and after review. A new latest seal, even with identical prediction bytes, invalidates the in-progress implementation. Existing `C/implement/`, `A/tests/`, `A/method/`, or `A/REVIEW.json` prevents restarting this stage and resetting its repair budget. Explicit `args.stub.implement` retains the existing stub contract.
- The pipeline first snapshots the already-built remote `baseline-published/`, `data/`, and a copy of the frozen baseline outputs, remote `reproduce-out/`, at `baseline-out/` (never the current `out/`). A missing or symlinked `reproduce-out/` fails the snapshot like any other snapshot failure. It does not rebuild or substitute the published baseline. All snapshots and subsequent integrity checks run through boxrun. Source, data, and baseline-output hashes must remain unchanged after authoring and around both attempts.
- Baseline adapter smoke: after the snapshot and before the test author call, implement runs the baseline adapter evaluate will use (`harness/run_evaluation.sh`, or `harness/run_anchors.sh` when absent) once, as box operation `adapter-smoke` under the method_run budget. It runs exactly as an evaluate invocation in a fresh `evaluation-work/smoke/0/baseline/`, with `EVAL_ARM=baseline`, `EVAL_MODE=equivalence`, the sealed `EVAL_PROTOCOL` and `EVAL_INPUTS`, empty `EVAL_COMPUTE_BUDGET`, and `EVAL_SEEDS` equal to the sealed `paired_seed_tests` object unchanged. Evaluate never passes a subset of the sealed seeds, so the smoke does not either: it is one complete baseline equivalence invocation. The smoke passes when the command exits 0 and `EVAL_OUT/evaluation.json` meets the evaluation record rules: one record per sealed seed and input id, seeds first, then input ids, in sealed order (seed null under a deterministic seal); the sealed `timing_scope`; the sealed `gpu_count`; finite positive `wall_s` for reported timing; and every sealed `equivalence_metrics` name in each record's `metrics` as a finite number. The smoke also checks its cost. Remote `out/smoke.json` is removed before each smoke; the smoke script times the adapter command with a monotonic clock from launch to exit and always writes `out/smoke.json` as exactly `{"process_wall_s": <finite nonnegative number>}`, including after a nonzero exit or TERM. When the records and metrics pass, implement projects one complete performance scorer from that measurement: `projected_s` = (sealed `warmup` + sealed `repetitions`) × 2 × `process_wall_s`, charging the method arm at the baseline's cost, plus, unless `equal_outcome_target.not_applicable` is true, `b / baseline_gpus + b / method_gpus` for each sealed compute budget `b` (each curve invocation's bound, with the GPU counts from `hardware_cost_basis`). The smoke passes only when `projected_s` is at most 0.9 × the resolved `evaluate` budget; otherwise it fails with category `cost`. A missing or malformed `smoke.json` after the records and metrics pass is category `missing_output`. On failure, one `adapter-repair` call (`harness` role and model, `retry: 1`, fresh session) may rewrite only `run_evaluation.sh` (creating it when absent). It receives the sealed predictions, intake files, current harness scripts, the fixed failure category (`exit`, `timeout`, `missing_output`, `records`, `metrics`, `cost`) and at most the last 200 log lines; for `cost` it also receives `process_wall_s`, the sealed warmup and repetitions, `projected_s` and the evaluate budget seconds, as numbers; its prompt states the evaluation adapter interface. Rewrites of any other file are discarded, as in reproduce repairs; a repair that leaves no nonempty `run_evaluation.sh` passing `bash -n` counts as a second failure. The rewritten script is copied to `A/harness/`, uploaded as `implement-upload`, and smoked once more. A second failure stops implement before any test or method author call: status `VOID`, `error_class: parse` (exit 2), or `timeout` (exit 3) when that smoke timed out, with `patch_applies`, `tests_pass`, `blind_tests` and `launch_review_pass` null. Smoke logs and outputs go to `A/results/implement/adapter/<attempt>/`; they are not measurements and evaluate never reads them. Test and method authors see the harness after any repair.
- There is one initial `tests` call and one initial `implement` call, both `ls-writer`, requested model `sonnet`, `repairable:false`, `fresh:true`. Tests are authored and frozen **before** the method-author call, so method results cannot precede the freeze. The test author receives only proposal, intake, baseline harness/interface and reproduced baseline outputs, and the sealed predictions/protocol. The method author receives proposal, intake, baseline harness, box probe and sealed predictions, and in its prompt the frozen `method_outputs` paths (see A/tests/); it never receives the tests' other content, fixtures or test transcripts. Only the initial method-author call may access the already-running box through `~/.cache/metis-serve/box.sh`.
- wf's optional agent setting `isolation` has `{directory, hidden, box_access}`: an absolute private view directory, an array of absolute paths hidden from that role, and a boolean permitting box credentials. It overrides cwd and add-dirs, disables resume-cache reuse and provider-session export, and is forwarded to every dispatched family, including fallbacks. Real dispatch uses bubblewrap with a read-only host filesystem, private `/tmp`, PID/IPC namespaces, hidden run/workflow paths and provider histories, and a fresh writable HOME containing authentication files only. The view is the only writable host directory. The initial implementer additionally receives read-only access to the existing box wrapper and SSH keys. Test, review and repair roles cannot access them. No sandbox fallback grants broader access: missing bubblewrap or unavailable namespaces fails the call. That outer namespace is the only sandbox: hosts that restrict unprivileged user namespaces (Ubuntu's AppArmor `bwrap-userns-restrict`) deny any namespace nested inside it, so a provider's own sandbox would fail every command. Inside the namespace a Codex agent therefore runs with `danger-full-access`, never `workspace-write` or `read-only`. That mode follows only from the call being dispatched inside the namespace, never from an environment variable: a Codex call outside isolation keeps `workspace-write` or `read-only` even when `CODEX_EPHEMERAL=1` is set. A role whose tools include Write, Edit or Bash keeps the view writable; any other role gets the view mounted read-only, with only its private HOME and temporary directory writable. `WF_STUB` remains an explicit test double, bypassing provider execution. Temporary views/provider state are removed after the stage; raw provider logs remain under the role's workflow transcript directory and are hidden from other roles.
- Each view has top-level `proposal.json`, `PREDICTIONS.json`, `intake/`, and `harness/`. Test views additionally have `baseline-out/`, a copy of `A/results/reproduce/out/`, so frozen tests run against the same baseline outputs their author saw; method views have `probe.json` and, on repair, the previous three method files. Writable author output is `tests/` or `method/`. Review views contain `method/`, proposal, predictions, intake, `implement-payload.json` and `seal.json`; `seal.json` is the existing seal receipt plus `receipt`, its numbered receipt filename. Review receives these scientific inputs embedded in its prompt, using the tool-free `qt-bare` role. No view contains another role's source or transcripts except the method source explicitly supplied to review.

### A/method/ and remote execution interface
- The method author writes three required nonempty files: `method.patch` (git-style paths relative to the published source root), `setup_method.sh`, and `run_method.sh`. An optional fourth file, `run_anchors.sh`, implements the method anchor protocol. No other files are allowed. Shell scripts must pass `bash -n`. The pipeline copies them from the private view into `A/method/`; neither author writes control state.
- Each attempt uploads method files to remote `payload/method/` and frozen tests/fixtures to `payload/tests/`. Uploads append independently decodable base64 chunks of at most 24,576 characters, batching commands below 32,768 characters to avoid shell argument limits; each batch has its own receipt. It creates a fresh source copy at `method/` using `cp -a baseline-published method`; patch checking and application use `git apply` with an explicit detached Git context and that copy as work tree, so copied repository/worktree metadata cannot redirect writes into the baseline. A retry always starts from a fresh copy.
- The scripts run from the same remote run directory used by reproduce: `bash payload/method/setup_method.sh`, then `bash payload/method/run_method.sh`, then `bash payload/tests/run_tests.sh`. All receive absolute environment paths `BASELINE_DIR` (original published source), `METHOD_DIR` (patched source copy), `BASELINE_OUT` (frozen baseline outputs), and `METHOD_OUT` (remote `out/`). Setup builds the patched copy; run uses the same representative scale, inputs and seeds and writes actual method outputs in exactly the baseline's format and relative output locations. The method author prompt and the method repair prompt list the frozen `method_outputs` paths and state that `run_method.sh` writes each of them under `METHOD_OUT` at that relative path, as the baseline outputs do. After `run_method.sh` exits 0 and its `out/` is fetched, and before any test command, implement checks that every `method_outputs` path exists in that fetched copy as a file or symlink. When any is missing the attempt fails with pipeline failure category `layout` and the tests are not run for that attempt. Fixtures resolve relative to `run_tests.sh`. Remote `out/` is cleared before setup and again before method execution; `out/tests.json` is removed immediately before tests. A previous baseline/method/report cannot satisfy a new attempt.
- `A/implement-payload.json` records the current attempt with exactly `{attempt, remote_directory, baseline_directory, method_directory, baseline_outputs, method_outputs, tests_sha256, seal_sha256, method_files, timeouts}`. `attempt` is 1 or 2. Relative directory values are `baseline-published`, `method`, `baseline-out`, and `out`; `remote_directory` is the absolute shared remote directory. `method_files` contains `{path, sha256}` for every provided method file, using relative names and SHA-256 of exact bytes. `timeouts` has positive integer seconds for `setup_method`, `run_method`, `run_tests`. Hashes are lowercase 64-digit hexadecimal strings. The payload is regenerated after repair and reviewed only in its final form.

### A/tests/ and out/tests.json
- The test author writes `run_tests.sh`, `outputs.json` and optional fixtures under its private `tests/`. `outputs.json` is exactly `{"method_outputs": [path, ...]}`: a nonempty array of unique relative POSIX paths (no leading `/`, no empty, `.` or `..` segments) naming every file the tests read under `METHOD_OUT`. Each names a regular file under the test view's `baseline-out/`, because the method writes its outputs at the baseline's relative locations. A missing or invalid `outputs.json` fails the test author output like a missing `run_tests.sh`. It is frozen and hashed with the tests. The test author prompt states these rules. Files and nested directories must be regular files/directories, never symlinks or special files; the same restriction applies when copying evidence and method artifacts across views. Scripts must pass `bash -n`. After copying to `A/tests/`, all files become mode 0444 and directories 0555; the pipeline records their tree hash in `C/implement/tests.json` before any method-author call. Remote tests receive the same modes. The pipeline checks the frozen local hash repeatedly and the remote test hash before/after execution, including failed method attempts. Changing tests invalidates blindness and stops the stage without repair.
- Tests check actual outputs for input loss, duplication, ordering, non-divisible tails/final inputs, paired seeds or the seal's justified deterministic declaration, and scientific equivalence within sealed tolerances. Tests see exactly two sets of outputs: `BASELINE_OUT`, the frozen baseline outputs, and `METHOD_OUT`, one method run at the same representative scale, inputs and seeds. Evaluation records (`evaluation.json`), held-out seeds, timing repetitions and compute budgets exist only in evaluate, and no case may require them. The `equivalence` case pairs baseline and method outputs by input and seed and applies the sealed `equivalence_metrics` margins and confidence rule to those representative pairs, at the sealed confidence for the number of pairs available. It fails only when the pairs reject equivalence: for some metric the interval is disjoint from the open interval (−margin, +margin), or, under a deterministic seal, some paired difference exceeds the sealed tolerance. An interval that overlaps (−margin, +margin), or pairs too few for a finite interval, cannot reject, and the case passes; acceptance is decided in evaluate. The test author prompt states these rules. They may reuse upstream tests but must not assert on method source or execute/read method scripts. A valid report must include unique case IDs `dropped_inputs`, `duplicated_inputs`, `ordering`, `tail_handling`, `seeds`, and `equivalence`; additional unique nonempty IDs are allowed.
- Remote `out/tests.json` has **exactly** `{passed, failed, cases}`. Counts are nonnegative integers equal to the passing/failing case counts. `cases` is nonempty; each row has exactly `{id, pass, reason_code}`. `pass` is boolean. Passing rows require `reason_code:null`; failing rows require one of `dropped_inputs`, `duplicated_inputs`, `ordering`, `tail_handling`, `seeds`, `equivalence`, `missing_output`, `invalid_output`, `upstream`, `other`. Reports with extra keys, duplicate/missing required IDs, inconsistent counts, unknown reasons, or missing/invalid values fail parsing. Tests pass only when the command exits 0, a valid report is present, and `failed=0`. A nonzero exit cannot be overridden by a passing report.
- There are at most two execution attempts and one method repair, never another test-author call or a second review. Repair uses the same `implement` label, requested model `sonnet`, `retry:1`, a new isolated session, the original scientific inputs and previous method files. Failure feedback is a `reason_code_counts` object with positive integer counts, plus numeric budget, elapsed and overrun seconds for a timeout. Failed test cases are aggregated by their fixed `reason_code`; infrastructure, logs, case IDs, values and test source are never passed to the author. Pipeline failure categories are `patch_applies`, `setup_failed`, `run_failed`, `layout`, `invalid_report`, `tests_failed` (nonzero test exit with no failing cases), or `timeout`. For `layout` the feedback also has `missing_paths`, the sorted `method_outputs` paths absent from the method's `out/`; these are baseline output locations, which the method author is already given, not test content. Infrastructure/fetch and integrity failures stop immediately without repair. Any second execution failure stops.

### Implementation control records, results and verdict
- `C/implement/started.json` has exactly `{seal_sha256, utc}` and marks the consumed implementation budget. `C/implement/baseline.json` has exactly `{baseline_sha256, data_sha256, baseline_outputs_sha256}`. Digests are lowercase SHA-256 strings.
- `C/implement/tests.json` is created exclusively, mode 0444, with exactly `{sha256, files, seal_sha256, utc}`. `sha256` is the frozen tree digest. `files` is an ordered list of `{path, sha256}` with slash-separated paths relative to `A/tests/` and individual file-content hashes. This immutable receipt precedes all method-author work. `C/implement/attempt-1.json` and, on a second failure, `attempt-2.json` contain exactly `{attempt, reason_code_counts}`; categories are the fixed enums above, never content-derived strings.
- `m5/implement_state.py` accepts key/directory pairs and prints one JSON object mapping those keys to tree digests; it exits 1 with a content-free diagnostic on invalid trees or arguments. It traverses each directory depth first, sorting sibling names by Unicode code point, without following links. Its digest input is compact ASCII JSON (`ensure_ascii=true`) of rows: `[relative_path,"directory",mode]`, `[relative_path,"file",mode,file_sha256]`, or `[relative_path,"link",mode,link_target]`; modes are integer permission bits and relative paths use `/`. The root itself and timestamps are excluded. Baseline links are hashed by target string; linked content outside the frozen trees is not included. Special files and symlink roots are rejected.
- Each remote integrity command writes `out/implement-state.json`, containing the three baseline/data/output digests above and, once tests are uploaded, `tests_sha256` and `method_payload_sha256` (the uploaded `payload/method/` tree). The latter must remain equal to the pre-execution digest for that attempt, so setup/run/tests cannot replace the uploaded patch or scripts. All are computed from actual remote trees with the committed helper fed to `python3 -I`; method scripts cannot replace a stored helper to forge an integrity check. Control receipts, never model replies, establish these hashes.
- All command receipts use the existing `C/receipts/` contract. Baseline snapshot logs/fetched outputs go to `A/results/implement/baseline/`. Attempts use `A/results/implement/attempt-<1|2>/<phase>/`, with phases `upload`, `before`, `patch`, `setup`, `run`, `after-method`, `tests`, `after-tests`. Each command fetches `out/` and its numbered log there; commands not reached have no phase directory. The post-author integrity check is under `attempt-0/after-author/`. The latest completed attempt's method outputs, test report when available and integrity metadata are also copied to `A/results/implement/out/`, preserving prior attempts separately.
- After successful tests and any repair, one `review` call (`qt-bare`, requested model `sonnet`, `repairable:false`, `fresh:true`; routed to Claude by the m5 model policy, so the reviewer's family differs from the Codex method author) checks the final patch/scripts, proposal, verified seal, execution contract and payload before downstream launch/evaluation. `A/REVIEW.json` has exactly `{pass, reason_codes}`. `pass` is boolean; reasons are an array containing only `changes_method`, `equivalence_risk`, `resource_mismatch`, `changes_baseline`, `changes_protocol`, `invalid_payload`, `cost_guard`, `other`. Passing review requires an empty reasons array. Missing/malformed review fails parsing. Reviewer cannot change tests.
- Implement facts have exactly `{patch_applies, tests_pass, blind_tests, launch_review_pass}` plus common facts. Executed stages initialize all four false; skipped/stub stages retain null facts. `patch_applies` describes the latest attempt's actual check/application; `tests_pass` requires both report and successful exit; `blind_tests` requires the prior immutable freeze, isolated authors and unchanged tests; `launch_review_pass` reflects the final independent review. PASS requires all four true and the seal still verifying. Parse failures use `parse`, setup failures `install`, failed method/test execution or equivalence `numeric`, infrastructure/fetch failures `infra`, and baseline/test integrity, restart or rejected-review failures `other`, with exit 2 except timeouts (`timeout`, exit 3). Failed/skipped downstream stages and takeaways follow the existing pipeline contract. No test content or reason-count maps enter operator signatures.

## Evaluate: executable sealed protocol (v1)

Evaluation uses deterministic Python scorers, with no model calls or repairs. It verifies the latest seal, launch review, implementation payload and frozen independent tests before running workloads. It never builds a tuned control; `speedup_tuned` is always null in v1. Explicit `args.stub.evaluate` retains the existing stub contract. Other stage stubs do not supply evaluation evidence.

The seal must supply the following executable fields. Existing prose-only or unsupported protocols produce VOID; the evaluator never interprets prose as executable rules or substitutes defaults for scientific decisions.

```json
{
  "evaluation_inputs": {"ids": ["input-0", "input-1"], "pin": "immutable input specification"},
  "sample_sizes": {"inputs": 2, "seeds": 1},
  "equivalence_metrics": [{"name": "accuracy", "tolerance": {"abs": 0.001}, "source": "scientific requirement citation"}],
  "paired_seed_tests": {"kind": "deterministic", "justification": "scientific reason"},
  "confidence_rule": {
    "equivalence": {"kind": "paired_median", "confidence": 0.95},
    "performance": {"kind": "paired_median", "confidence": 0.95}
  },
  "timing_scope": {"kind": "process_wall", "gpu_synchronization": "adapter", "description": "includes launch, transfer, compute and merge"},
  "hardware_cost_basis": {"baseline_gpus": 1, "method_gpus": 1, "budget_unit": "gpu_s"},
  "warmup": 1,
  "repetitions": 7,
  "scheduling_order": {"kind": "randomized_pairs", "seed": 42},
  "minimum_worthwhile_gain": 1.05,
  "compute_budgets": [60, 120, 240],
  "equal_outcome_target": {"metric": "accuracy", "comparison": ">=", "target": 0.9}
}
```

- Input IDs are unique nonempty strings. Records must cover exactly the Cartesian product, in seed-major then input-ID order. `sample_sizes.inputs` and `.seeds` are integer counts that must match the fixed lists. Deterministic runs use one null seed. Stochastic protocols use `{kind:"paired_median", seeds:[unique integers]}` instead; the same seeds apply to both arms. Input pins/specifications and splits remain part of the complete sealed protocol supplied to each adapter.
- Metrics have unique nonempty `name`, nonempty `source` and tolerance. Deterministic tolerance is a finite nonnegative absolute number, `{abs:x}` or `{rel:x}`. Each paired row must satisfy `abs(method-baseline) <= tolerance`; relative tolerance multiplies `abs(baseline)`, including exact agreement at zero. All reported metric values must be finite numbers, never booleans.
- Stochastic metrics require absolute tolerance. For each metric and seed, average the paired method-minus-baseline differences over fixed inputs. Use an exact sign-test confidence interval for the median of those seed averages. Equivalence requires the entire interval inside `[-tolerance,+tolerance]`, including endpoints. Bonferroni divides the two-sided error probability across sealed metrics. This tests equivalence of the median paired effect defined by the seal; it is not a failure-to-reject difference test.
- Confidence is finite in `[0.5,1)`. For sorted samples `x` of length `n`, select the largest `k >= 1` with `P(Binomial(n,0.5) < k) <= alpha/2` for equivalence or `<= alpha` for performance. Equivalence bounds are `[x[k-1],x[n-k]]`; performance uses lower bound `x[k-1]` and an unbounded upper endpoint represented by null. No admissible `k` means insufficient measurements and VOID. At 95%, one metric needs at least six independent seed pairs; performance needs at least five timing pairs. More metrics or greater confidence can require more seeds. No bootstrap randomness or asymptotic approximation is used.
- `warmup` is an integer >=0, measured but excluded from performance statistics; `repetitions` is an integer >=5. Each pair contains one run of each arm in independently shuffled order from Python's `random.Random(sealed_seed)`. Warmup pairs and curve arm order use the same RNG stream. Both arms use the same box, sealed inputs, seeds, configuration and scope. Published baseline is never tuned.
- `timing_scope.kind` is `process_wall` (trusted `perf_counter` around the complete adapter subprocess) or `reported_wall` (adapter's measured `wall_s`, for scopes requiring program timers). Both arms must echo the exact sealed scope. Adapters must synchronize all used GPUs before completion/timer stop and include launch/transfer/merge overhead required by the scope. Missing or mismatched scope is VOID. Reported timings are actual program measurements, never extrapolated estimates.
- `hardware_cost_basis` declares positive integer GPU counts per arm, bounded by both box and probe capacity. `C/box.json.price_usd_h` must be finite and positive. Per-GPU tariff is box hourly price divided by available box GPUs; run USD is measured seconds times GPUs used times this tariff /3600. Pair speedup is baseline seconds / method seconds; `speedup_published` is the median pair speedup. `cost_ratio` is the median paired method-USD / baseline-USD ratio. `equal_cost` means `cost_ratio <= 1`. Performance requires matched scientific outputs on warmups and timed pairs, the sealed one-sided confidence lower bound >= `minimum_worthwhile_gain`, and equal cost. `prediction_ratio` divides median speedup by the selected sealed interval's midpoint. Zero or unavailable pricing cannot establish equal cost.
- Curves use GPU-second budgets. Each invocation receives the sealed budget and is bounded by both its script timeout and budget / GPUs used. Allocation seconds include the complete subprocess, even with reported timing. Both arms must finish within the budget and echo it exactly. Each complete budget produces one point with both measured outcomes; no interpolation or extrapolation occurs. `equal_outcome_target` defines a metric, finite numeric `target`, and comparison `==`, `>`, `>=`, `<` or `<=`; each outcome is the mean metric over fixed rows and records `target_achieved`. `uncertainty:{min,max}` reports the observed range, not a confidence interval. A failed or unachieved target is retained. If this benchmark has no outcome curve, seal `{not_applicable:true,reason:"explicit scientific reason"}` instead; `curve_points=0`, `not_applicable=true`.

### Baseline and method adapter interface

The harness may additionally provide `A/harness/run_evaluation.sh`, uploaded during reproduce. Otherwise the evaluator uses `harness/run_anchors.sh` for baseline evaluation. The baseline adapter must run the exact published configuration. The method adapter is `payload/method/run_method.sh`. For validity, use optional `payload/method/run_anchors.sh`; absent that file, derive the anchor invocation by running `run_method.sh` with `EVAL_MODE=anchors`. Both routes must rerun the complete published anchor protocol under the method and write `out/anchors_measured.json`; copying baseline or published values is forbidden.

Every invocation runs in a fresh `evaluation-work/<phase>/<index>/<arm>/` with empty `out/` and links to the fixed `baseline-published/`, `method/`, `data/`, `harness/`, `payload/`, `baseline-out/` trees. This preserves relative paths while separating repetitions. Environment:

- `BASELINE_DIR`, `METHOD_DIR`, `BASELINE_OUT`: absolute fixed source/output paths; `METHOD_OUT` and `EVAL_OUT`: this invocation's absolute empty output directory.
- `EVAL_ARM`: `baseline` or `method`; `EVAL_MODE`: `anchors`, `equivalence`, `warmup`, `performance`, or `curve`.
- `EVAL_PROTOCOL`: absolute path to the complete immutable sealed predictions JSON, including splits, input pins and seeds. `EVAL_INPUTS` and `EVAL_SEEDS` are JSON encodings of `evaluation_inputs` and `paired_seed_tests`. `EVAL_INPUTS` is an object whose `ids` array lists the sealed input identities in order; each record's `input_id` is one of those strings, and every other key (pins, configuration, generated-input descriptions) describes inputs and is never itself an input. `EVAL_SEEDS` is either `{kind:"paired_median",seeds:[integer,...]}`, whose seeds are the execution seeds in order, or `{kind:"deterministic",...}`, whose single execution seed is null; other keys are descriptive. The harness prompt (which writes `run_evaluation.sh` before the seal exists) and the method author prompt both state these two shapes.
- `EVAL_COMPUTE_BUDGET`: empty outside curves; numeric budget string for curve runs.

Non-anchor adapters write `EVAL_OUT/evaluation.json`:

```json
{
  "records": [{"input_id": "input-0", "seed": null, "metrics": {"accuracy": 0.95}}],
  "timing_scope": {"kind": "process_wall", "gpu_synchronization": "adapter", "description": "includes launch, transfer, compute and merge"},
  "gpu_count": 1,
  "wall_s": 1.2,
  "compute_budget": 60
}
```

`records` is required in all non-anchor modes. `wall_s` is required and finite positive only for reported timing. `gpu_count` must match the arm's sealed count. Curves require exact numeric `compute_budget`; it is optional otherwise. Additional program output fields are allowed. Arrays with missing/duplicate/reordered inputs, wrong seeds, unequal counts, or omitted final inputs fail equivalence. Each record's `metrics` holds every sealed `equivalence_metrics` name as a finite number for that input and seed, keyed by exactly that name. The method adapter's records mean the same as the baseline adapter's: for each input and seed, the same workload execution and the same metric definitions; the method author prompt states this. Missing/malformed files or metrics are unavailable measurements, producing VOID. Scripts exit nonzero on execution failure and must not modify baseline, data, frozen outputs/tests, harness, evaluator payload or method source during evaluation.

### Evaluation artifacts, provenance and failures

- `m5/eval_validity.py`, `eval_equivalence.py`, `eval_performance.py` accept `--stage <validity|equivalence|performance> --in <manifest.json> --out <directory>` (the corresponding stage only; stage flag is optional). `eval_common.py` shares IO, invocation and exact confidence calculations; validity calls `score_anchors.score` unchanged.
- Script-owned `C/evaluate/manifest.json` is created exclusively, mode 0444. Existing `C/evaluate/` prevents a new evaluation round. It contains `{remote_directory,protocol,prediction,box,gpu_count,run_timeout_s,method_files,anchors,input_hashes}`. `prediction` is the selected method's sealed prediction. `input_hashes` contains `seal_sha256`, the implementation's baseline/data/output/test/method-payload tree hashes, `anchors_sha256`, local `harness_sha256`, and `evaluators` mapping each uploaded Python filename to its exact-byte SHA-256. Method files must match the reviewed payload. Before/after every scorer, trusted integrity commands recheck source, data, frozen baseline outputs, tests, method payload, built method source, harness, evaluator helpers and manifest. Initial remote hashes additionally freeze method source, harness and evaluator payload for the evaluation round; source/harness modes can differ from local copies. The seal and local frozen tests are rechecked too.
- Helpers, manifest and sealed predictions are uploaded in bounded base64 chunks through boxrun. Operations are `evaluate-upload`, `evaluate-state-before-<stage>`, `evaluate-state-after-<stage>`, and `evaluate-<stage>`. Logs and each fetched `out/` remain in `A/results/evaluate/<operation>/`; repeated upload receipts/logs share their operation directory. Remote artifacts are `out/eval/{validity.json,equivalence.json,performance.json,curve.json,raw.jsonl}`. The final fetched evaluation files/logs are also copied directly to `A/results/evaluate/`. `out/evaluate-state.json` contains remote tree hashes. Nothing scientific enters operator signatures.
- All verdicts have `status` (`PASS`, `FAIL`, `VOID`) and, once executed, `input_hashes`. `validity.json` adds `validity_pass` and the exact anchor score fields `anchors`, `anchors_passed`, `anchors_total`, `all_passed`. `equivalence.json` adds `equivalence_pass` and `metrics`: deterministic rows `{metric,passed,max_abs_difference}`, stochastic rows `{metric,passed,difference_interval,confidence}`, or a failed alignment row `{passed:false,reason_code:"counts_or_alignment"}`. `performance.json` adds `performance_pass`, `equal_cost`, `speedup_published`, `speedup_tuned:null`, `cost_ratio`, `prediction_ratio`, `confidence`, `speedup_interval`, `matched_outcome`, `pairs`. Each pair has `{index,order,baseline_s,method_s,baseline_gpus,method_gpus,speedup,cost_ratio,baseline_usd,method_usd}`.
- `curve.json` has `{status,input_hashes,not_applicable,curve_points,points}`, plus a reason for not-applicable/invalid protocols. Each point has `compute_budget` and `baseline`/`method` objects. Successful arms have `{status:"PASS",outcome,target_achieved,uncertainty,allocated_gpu_hours,usd}`; unavailable arms have `{status:"VOID",outcome:null,reason_code}`. `curve_points` counts budgets with both outcomes measured. Failed budgets remain in `points`; partial successful budgets are saved after every iteration. An unachieved target is a measured outcome, not a missing point.
- `raw.jsonl` appends `{phase,index,arm,compute_budget,rc,process_wall_s}` immediately after execution and a second row with `output_sha256` and actual `report` after successful output parsing. Each invocation preserves its `<phase>-<index>-<arm>.log` and parsed `.json` alongside the verdicts. Anchor measurements are saved as `anchors_measured.json`.
- Before execution all four local verdicts start as `{status:"VOID",reason_code:"not_run"}`. Scorer parse/missing-output failures write `status:"VOID"`, the corresponding `*_pass:null`, and fixed `reason_code:"missing_or_invalid_measurements"`. Invalid manifests use `invalid_manifest`. Earlier raw/phase evidence is retained. Finite measurements are required: zero placeholders never establish PASS.
- Validity uses the same anchor/reference rules: references never fail validity, and with no anchors validity passes when the method arm's anchor protocol exits 0 with a valid measurement file; evaluate's `run_valid` is then null. Validity failure stops immediately: `status:FAIL`, `error_class:anchor`, exit 4 (`exit_kind:anchor`), `run_valid:false`. Nonzero anchor execution also fails validity; absent/invalid anchor files or any missing/non-numeric anchor (not reference) measurement are VOID with `validity_pass:null`, retaining scored rows when available. Equivalence/performance scientific failure uses FAIL, `numeric`, exit 5 (`later_stage`). Infrastructure/fetch/integrity or unavailable measurement failures use VOID, fixed `infra`/`other`/`parse`, exit 2; outer scorer timeout uses `timeout`, exit 3. Missing curves prevent overall PASS; an already measured performance failure retains FAIL/exit 5 while the curve stays VOID. Subsequent verdicts remain independently VOID when not run; no performance result can override invalidity. All failures still proceed to takeaways. A box timeout permits one identical bounded scorer retry; immutable reviewed payloads and sealed protocol cannot be changed during evaluation.
- Evaluate facts contain `{validity_pass,equivalence_pass,performance_pass,equal_cost,speedup_published,speedup_tuned,cost_ratio,prediction_ratio,curve_points,tokens_known,gpu_busy_known}`, plus the optional timeout fields defined above. Unavailable values are null, including unmeasured curves; explicitly inapplicable curves have count 0. No model calls means `tokens_known:true`; receipt telemetry owns `gpu_busy_known`. Overall PASS requires three passing verdicts and a complete or explicitly inapplicable curve. Stage stub/SKIPPED facts preserve their existing null contract.
- `stage_budgets_s.evaluate` bounds each complete scorer command, default 2400 seconds. Each subprocess uses the resolved method_run budget; uploads/integrity commands use method_setup. Configure budgets for the fixed sealed run count. Boxrun interface and content-free accounting remain unchanged.

## Compute metadata
- The shared v1 `model_family` enum now also accepts `cursor`: its complete set is `codex`, `cursor`, `opencode`, `lambda`, `claude`, `none`. Each stage uses the answering model in that stage's successful wf journal `result`/`cached` events, not the requested model or failed attempts. A `lambda/` model reports `lambda` despite OpenCode dispatch. With several answering families, the last answer wins; with no successful answer, the value is `none`.
- wf exposes `agent.journal`, the absolute journal path. Cached journal events now include `model`, preserved from the successful result in the resume source. Cached answers retain model provenance but incur no new token usage. Failed attempts and unused shadow answers do not replace the answering family.
- New `C/stages/<stage>.json` receipts contain `{stage, status, wall_s, gpu_s, usd, model_family, notes}`, plus any stage-provided v1 overrides and measured token counts. Stage/status/model families use their existing enums. `notes` is an array with either no entries or the single fixed code `multiple_model_families`; no model text, prompts, filenames, or scientific facts are copied into it. These receipts are separate from `C/receipts/` box command receipts.
- Both serve and dev `lambda_serve.sh up` write `$HOME/.cache/metis-serve/box.json` atomically alongside `state.json`. Its keys are `{type, region, price_usd_h, started_utc}`: Lambda instance-type and region identifiers, a numeric hourly USD price, and a UTC ISO timestamp. Repeated state saves preserve the allocation's start. Confirmed `down` retains `box.json` and adds `ended_utc` (UTC ISO timestamp) and `hours` (nonnegative elapsed allocation hours, including startup and termination polling). State archival behavior is unchanged. The next `up` replaces this record for the new allocation.
- At the start of reproduce, the pipeline copies the current shared `box.json` to `C/box.json`, replacing any stale run copy. Missing box metadata leaves pricing unavailable and stage USD at zero. At takeaways, a matching allocation record can refresh the copy with its confirmed end; a different allocation never replaces the snapshot. If reproduce was skipped, takeaways snapshots the current allocation to account for any run overlap.
- Box receipts add numeric nonnegative `gpu_busy_s` and boolean `gpu_busy_known`. The detached remote script writes `<receipt-id>.gpu` beside its log, sampling `nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader,nounits` immediately and every 2 seconds until the command exits or times out. Each finite utilization sample in [0,100] contributes `utilization / 100 * 2` seconds; samples from every GPU are summed. Missing/invalid samples contribute nothing. No valid samples means `gpu_busy_s=0`, `gpu_busy_known=false`. Telemetry collection failure does not change command/fetch success. Sampling survives loss of the local polling process; the remote runner stops sampling before publishing its exit marker.
- Stage v1 `gpu_s` sums its box receipts' `gpu_busy_s`, including failed commands and retries. For stages with box receipts, `facts.gpu_busy_known` is true only when every receipt has valid busy telemetry; partial telemetry contributes its measured values while the flag stays false. Harness profile timing remains separate evidence and never substitutes for receipt GPU accounting. This supersedes the earlier statement that reproduce/profile always leave this flag false.
- Stage v1 `usd` is `sum(its box receipts' wall_s) / 3600 * C/box.json.price_usd_h`, including uploads, probes, failed commands, polling/fetch time, and retries. Stage `wall_s` remains elapsed stage time and includes agent calls. No allocation or model-call envelopes are added.
- Takeaways facts optionally add `run_box_usd`, a finite nonnegative number or null; old v2 records without this key remain valid. The pipeline writes null for a SKIPPED takeaways stage; otherwise it writes the whole run's box charge here: the intersection of `[run start, takeaways accounting time]` with `[box.started_utc, box.ended_utc]`, multiplied by hourly price. An active box uses accounting time as its end. When timestamps or price are unavailable, it falls back to summed stage USD. This is a run summary, not extra stage spend; takeaways v1 `usd` retains only its own command attribution.
- `OPERATOR_TAKEAWAY.md` now has a Compute section: one row per stage with existing gate columns plus `wall_s`, `gpu_s`, `usd`, `tokens_in`, `tokens_out`, `model_family`; a box table; and run totals. The optional Python API is now `takeaway(records, raid=None, box=None)`. The CLI reads only validated signatures and sibling `C/box.json`; it does not read agent content. Run USD uses `facts.run_box_usd` when present, avoiding double-counting stage attribution; other totals preserve the existing launch/model-call preference and stage fallback.
- Operator box output whitelists only `type` and `price_usd_h`. Price must be a finite nonnegative JSON number (never a boolean); unavailable price renders `null`. Type is a fixed enum: `gpu_1x_a10`, `gpu_1x_a100`, `gpu_1x_a100_sxm4`, `gpu_1x_a100_sxm4_80gb`, `gpu_8x_a100`, `gpu_8x_a100_80gb_sxm4`, `gpu_1x_h100_pcie`, `gpu_1x_h100_sxm5`, `gpu_8x_h100_sxm5`, `gpu_1x_gh200`, `gpu_1x_h200`, `gpu_8x_h200_sxm5`, `gpu_1x_b200`, `gpu_8x_b200`, or `unknown`. Unknown types render `unknown`; region, timestamps, and all other box fields never enter operator output.
