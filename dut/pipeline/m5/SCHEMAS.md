# m5 data contracts (what test authors may rely on; implementers keep this file current)

## Run identity and agent chat names
- `args.blind` is a boolean, default false. `args.raid`, when supplied, is a non-empty single-line string and takes precedence over automatic selection. `launch.js stage --stage m5` also accepts `--raid <name>` and `--blind`.
- `m5/raids.json` is `{theme, public, blind}`: a theme string and two ordered arrays of base names. The heist theme uses separate public and blind lists. Automatic selection skips names already present in `m5/raids_used.jsonl`; after the base names it cycles through the same list with suffixes `2`, `3`, etc. Explicit names are recorded too.
- Each ledger row and `C/raid.json` has exactly `{raid, blind, run_root, utc}`; `run_root` is absolute and `utc` is an ISO UTC timestamp. Reservations are serialised. A run reuses its existing reservation and rejects conflicting raid/blind arguments. The launcher reserves against the original pipeline ledger before freezing its copy.
- m5 sets `args.chat_prefix = "x-<raid>"`. Other scripts opt in using `args.chat_prefix`, an agent option `chat_prefix`, or the workflow flag `--chat-prefix`. Without a prefix, runner naming stays unchanged.
- Names are `<chat_prefix>-<label>[-<descriptor>]`; labels are lowercased, non-`[a-z0-9-]` runs become `-`, edge hyphens are removed, and an empty label becomes `agent`. Concurrent sibling calls sharing a label within a stage add `1of<n>`, `2of<n>`, etc. Repair turns add `retry<k>` (starting at 1); fallback calls add `fb`. When needed together, descriptors appear in that order, separated by hyphens. Harness repair calls supply agent option `retry: 1`.
- wf passes the name to every runner as `name`. OpenCode uses `--title`, Claude uses `--name`, and Codex prepends `[<name>]` as the first prompt line, before role instructions.

## m5 model policy (workflow configuration)
- m5 runs use `node idea/wf.js --config m5/wf_config.json --script m5/pipeline.js ... --profile latent_skeptic --family codex`, without `--disable-family claude`. `m5/wf_config.json` holds a `workflow` section identical to `idea/config.json`'s and an `understudy` section with: `primary_family: "codex"`, `mode: "fallback"`, `on_refusal: "halt"`, `disabled_families: []`, `chain: {"codex": ["opencode"], "opencode": ["codex"], "claude": ["codex"], "cursor": ["codex"]}`, and `routes: [{"match": "^skeptic-[45]$", "primary": "claude/sonnet"}, {"match": "^review$", "primary": "claude/sonnet"}]`.
- Effect: skeptic ballots 1–3 and every other m5 call resolve to a Codex primary with only OpenCode behind it; no Claude model appears in their primary or chain. Ballots 4–5 and the launch review resolve to `claude/sonnet` with Codex as the only understudy. A Claude refusal is not handed over (`on_refusal: "halt"`): the call returns null, so a refused ballot counts against approval and a refused review fails as a missing review. Transport failures hand over to Codex as for any other call. Only `claude/sonnet` is routed (never Fable).
- The pipeline writes `S/OPERATOR_TAKEAWAY.md` from validated signatures after all stage records, with the raid only in its header. `m5/operator_takeaway.py` accepts optional `--raid`; its Python `takeaway(records, raid=None)` API preserves the old header when omitted. Raid is not added to stage facts or v1 signature IDs.

## A/intake/ (written by the intake agent; checked by the pipeline)
- benchmark.json, data.json: non-empty JSON objects.
- anchors.json: an array; each item has a unique non-empty string `id`, non-empty `quantity` and `source`, finite numeric `published_value`, and `tolerance`. Its length must equal facts.anchors_count. Zero is a valid published value or tolerance.
  - Optional `comparison` is one of `"=="` (the default), `">"`, `">="`, `"<"`, or `"<="`. For `"=="`, an anchor passes when `abs(measured_value - published_value) <= resolved_absolute_tolerance`. For inequalities, it passes when `measured_value <comparison> published_value`; tolerance is ignored and may be 0. Intake should specify `comparison` when the published criterion is a threshold.
  - `tolerance` is a finite nonnegative number (absolute tolerance), or an object with exactly one key: `{"abs": x}` or `{"rel": x}`, where `x` is finite and nonnegative. For `"=="`, relative tolerance resolves to `x * abs(published_value)`; a zero reference therefore requires exact agreement.
- baseline.json: non-empty repo, build_commands, run_commands and published_configuration, plus commit or pin.
- EXECUTION.json: non-empty representative_scale, inputs, outputs and timing_scope. Optional `stage_budgets_s` supplies positive integer seconds in [1, 999999999], with keys `setup`, `anchors`, `profile`, `method_setup`, `method_run`, `tests`, `evaluate`. Each key resolves independently from `EXECUTION.json.stage_budgets_s`, then `args.stage_budgets_s`, then defaults: setup=1200, anchors=1200, profile=1200, method_setup=1200, method_run=1200, tests=900, evaluate=2400. Legacy `timeout_s` and `timeouts` no longer set pipeline box budgets. Every box command passes its resolved budget as `boxrun --timeout`. Harness uploads/probes use setup; implementation uploads, baseline snapshots, patch application and integrity checks use method_setup; evaluation uploads/integrity checks use method_setup. Script retries retain the original budget.
- Every harness, test-author, method-author and repair prompt states the budget for each script it writes. All require one fixed scale from EXECUTION.json, no scale search or doubling loops, and completion well within the budget. Baseline run_evaluation.sh and method run_anchors.sh use method_run per invocation; evaluate bounds each complete scorer, including all repetitions and curves.
- The intake passes only when the files are complete and found is true, anchors_count >= 1, data is "available", licence is "permitted", and stock_environment is not false.

## A/results/probe/probe.json (collected before the harness agent)
- The pipeline uploads the committed `m5/box_probe.sh` and runs it through boxrun in the same remote working directory as the harness. Both operations write receipts under `C/receipts/`, using the setup timeout. Fetched `out/probe.json` is validated as a JSON object and copied to `A/results/probe/probe.json`. Logs and fetched `out/` remain under `A/results/probe/`. Stale local or remote probes cannot satisfy a new run.
- Fields match the probe script:
  - `os`: null or `{id, version_id, pretty_name, version, name}` from `/etc/os-release`, with nullable strings; `kernel`: string or null.
  - `nproc`, `memory_kb` (MemTotal in KiB), `disk_home_avail_bytes` (available bytes on `$HOME`'s filesystem): integers or null.
  - `nvidia`: null or `{gpus, driver_version, cuda_version}`; `gpus` is an array of GPU name strings, versions are strings or null. CUDA here is the driver's reported CUDA version.
  - `nvcc`: an array of `{path, version}` for deduplicated executable paths from `command -v nvcc`, `/usr/local/cuda*/bin/nvcc`, and `/usr/lib/cuda*/bin/nvcc`; `version` is captured `nvcc --version` text or null. Missing nvcc yields `[]`.
  - `cmake`, `gcc`, `g++`, `make`, `git`, `python3`, `pip`: null or `{path, version}`, with a string path and nullable version text. `pip` falls back to `pip3`.
  - `apt_sources`: an array of `{file, lines}` naming apt source files and their lines mentioning cuda or nvidia. Commented matches may be included when no uncommented matches exist; these do not authorize enabling a repository. Missing matches yield `[]`.
  - `sudo_nopasswd`: boolean indicating whether `sudo -n true` succeeds.
- Individual missing tools or unavailable facts yield null/empty collections without failing the probe. Probe upload/run failure, nonzero boxrun exit, failed fetch, or missing/invalid JSON fails reproduce with `error_class: infra`, before any harness call; the probe has no agent repair; a timeout permits the single identical command retry defined below.
- Full JSON content is included in the harness prompt and every setup and anchor repair prompt. Agents must use discovered paths and versions and never hard-code a toolkit path absent from the probe. Select a CUDA toolkit root discovered in `probe.json` with both `include/cuda_runtime.h` and `lib64/libcudart.so`, checking both with `ls` on the box from the scripts. Pass it explicitly via `CUDAToolkit_ROOT` or `-DCMAKE_CUDA_COMPILER=<root>/bin/nvcc`, and prepend `<root>/bin` to `PATH`. Never rely on `/usr/bin/nvcc` when a complete toolkit root exists. Missing tools may be installed with apt only from listed sources, without adding repositories; otherwise only cmake may fall back to pip. If neither route applies, scripts must fail with a clear message.

## A/harness/ (written by the harness agent or copied from a previous run)
- Optional `args.harness_from` is a non-empty directory path to a previous run's `A/harness/`, resolved relative to the pipeline working directory. After a successful fresh box probe, the pipeline copies the exact bytes of `setup.sh`, `run_anchors.sh` and `run_command.sh` into the current `A/harness/` and skips the initial harness agent call. If present, `run_evaluation.sh` is copied too. Missing or unreadable required scripts, or an invalid argument, fail reproduce with `error_class: parse`; there is no fallback harness generation. Without this argument, harness generation is unchanged.
- Reuse writes script-owned `C/harness_source.json` as `{source, files}`. `source` is the absolute source harness directory; `files` maps each copied filename to `{sha256, modified}`. `sha256` is the lowercase 64-digit SHA-256 of the exact original copied bytes and remains unchanged after repair. `modified` starts false and becomes true after an accepted repair of that script, before its upload/rerun, even if that rerun fails. Reuse permits the same one bounded setup repair and one bounded anchor repair as generated harnesses; every repair receives the fresh probe. Reuse adds no stage facts and does not reuse probe results, measurements, or stock verification.
- `setup.sh`, `run_anchors.sh`, `run_command.sh` are bash scripts. The pipeline invokes them as `bash harness/<name>` from one fresh `/tmp/m5-<uuid>` directory on the already-running operator-managed box. They share that directory across reproduce and profile. No dev lifecycle commands are issued. `BOX` and `FETCH` are inherited unchanged by `boxrun.sh`, including injected executables.
- `setup.sh` installs/builds the exact published baseline in the stock image; sudo is allowed only for apt. Published source/configuration stays under `baseline-published/`; inputs stay under `data/`. Setup builds and checks only the baseline; the fixed pipeline profiler owns profiling tools and installation. Setup must tolerate one retry in the same directory. Tuning is deferred.
- `run_anchors.sh` runs the published protocol at the intake's representative scale and writes `out/anchors_measured.json` as an object mapping each intake anchor ID to a finite measured number. Missing or non-numeric measurements fail the corresponding anchor; booleans and nonfinite values count as non-numeric. Additional measurements are ignored for scoring.
- `run_command.sh` contains only the exact measured baseline command and complete environment at the representative scale, including working directory, arguments, CUDA visibility and GPU count. It runs the published binary, saves its output for anchor parsing, and propagates its exit status. `run_anchors.sh` invokes `bash harness/run_command.sh` from the shared working directory without overriding its environment or duplicating the command. Profiling invokes that same file from that same directory. No agent writes profiling scripts or profile outputs.
- `run_command.sh` uses paths relative to its working directory, never absolute paths into the run directory, and writes only under `out/` or temporary files. The concurrency probe and evaluation run it from sibling work directories that link the same trees (see Concurrency probe). Harness and repair prompts state this requirement.
- Harness prompts require the published build and binary to run and measurements to come from their OUTPUT. Scripts must never parse or assert on source text. Measurement checks fail only on missing or invalid output; deterministic scoring owns anchor comparisons.
- Without `args.harness_from`, there is one initial agent call (`harness`, `ls-writer`, `sonnet`). Setup and anchors each permit one repair after a nonzero exit: `harness-repair` and `anchors-repair`, with the same role/model. The agent receives the failure class and at most the last 200 log lines and may rewrite only the failing script within its scope. Only that script is recopied, then rerun once with its original budget. Infrastructure/fetch failures do not trigger repairs. Timeouts use the same single repair, never an extra repair. Repair prompts include budget seconds, measured wall seconds and max(0, wall_s-budget_s) overrun seconds. Profiling has no agent repair or execution retry; output/gate failures stop downstream work.

## A/results/reproduce/ and deterministic anchor scoring
- Every reproduce box command fetches remote `out/` into `A/results/reproduce/out/`, and its `<receipt-id>.log` into `A/results/reproduce/`. Logs remain in the agent view. The local fetched `out/` is cleared before each command to prevent stale measurements. The final copy contains the anchor run's outputs.
- `python3 m5/score_anchors.py <anchors.json> <measured.json> <out.json>` writes an atomic JSON object with exact keys `anchors`, `anchors_passed`, `anchors_total`, `all_passed`.
  - `anchors` preserves intake order and contains `{id, published_value, measured_value, tolerance, passed}` for every anchor. `tolerance` preserves its input form; `passed` is boolean. Missing or non-numeric measurements are represented by `measured_value: null`. Failed rows additionally contain `reason`: `unknown_comparison`, `missing`, `non_numeric`, `out_of_tolerance` (for `"=="`), or `threshold_not_met` (for inequalities). Unknown comparisons take precedence over measurement failures; missing measurements take precedence over non-numeric measurements. Passing rows have no `reason` field.
  - `anchors_passed` and `anchors_total` are nonnegative integer counts; `all_passed` is boolean. Empty anchor arrays, duplicate IDs, invalid published values, invalid equality tolerances, and nonfinite calculated equality differences/tolerances are parse errors. Unknown comparisons and missing/non-numeric measurements are anchor failures rather than parse errors.
  - Exit 0 means every anchor passed; exit 4 means at least one anchor failed; exit 1 means invalid/missing input or an output write failure. Invalid input does not produce a new score file. Diagnostics contain no input content.
- The pipeline writes the score to `A/results/reproduce/anchors_scored.json`.
- Reproduce facts are `{anchors_passed, anchors_total, stock_verified, tuned_control_valid}` plus common `tokens_known` and `gpu_busy_known`. Counts remain null until scoring succeeds; `stock_verified` is true only after setup exits 0; `tuned_control_valid` remains null. The gate passes only when stock is verified and every anchor passes. `run_valid` is true/false when anchor scoring passes/fails.

## A/results/profile/ and A/profile-packet.json
- Profile fetches remote `out/` to `A/results/profile/out/`; logs are `A/results/profile/<receipt-id>.log`. Its inputs are therefore under `A/results/profile/out/profile/`. Remote `out/profile/` is cleared before profiling to prevent stale evidence from passing.
- The pipeline uploads trusted `m5/profile_nsys.sh`, `m5/profile_summarise.py` and the collected probe into remote `profiler/`. Through boxrun, it invokes `bash profiler/profile_nsys.sh harness/run_command.sh out/profile <budget_s>`. The profiler reuses `nsys` from PATH or NVIDIA installation paths. Otherwise it tries `nsight-systems-cli` with apt using only source files listed by the probe, without enabling commented repositories or adding sources. If unavailable, it downloads the official Ubuntu 22.04 amd64 CLI package `NsightSystems-linux-cli-public-2025.3.1.90-3582212.deb` from `https://developer.download.nvidia.com/devtools/repos/ubuntu2204/amd64/` into a temporary directory outside `out/` that is removed after installation (the package never reaches `out/` or fetched results), verifies the SHA-256 pinned in the script, installs with `sudo -n dpkg -i` and runs `sudo -n apt-get -f install -y` for dependencies using the image's existing sources without adding repositories. This fixed profiler installation is an exception to the setup-script installation restrictions above. The profiler prepends the discovered Nsight binary directory to PATH. Missing tools, installation failures and collection/export failures emit `M5_PROFILER_INFRA`, write `out/profile/infra.json`, and exit 2; the pipeline classifies these as `infra` without agent calls.
- Collection uses `nsys profile --trace=cuda,nvtx,osrt --sample=none` around the shared command without modifying its environment. An inner launcher measures only that command with a monotonic clock; installation, profiler finalization and CSV export are excluded. The command's output is preserved in `baseline.log` as well as its own saved logs. Export uses `nsys stats --report cuda_gpu_kern_sum,cuda_gpu_mem_time_sum,cuda_api_sum --format csv`. Raw report, CSV files, tool version, export log, `raw_wall_s.json` and `gpu_util_raw.jsonl` remain in `out/profile/`.
- `python3 m5/profile_summarise.py <out_dir>` deterministically writes the three existing profile files. CSV total time/duration units ns, us/µs, ms and s are converted to seconds. Known Nsight skips for absent kernel/memory/API activity count as zero; missing or malformed reports fail parsing. Five rows are emitted: `kernels` (compute), `memcpy H2D` (transfer), `memcpy D2H` (transfer), `CUDA API host time` (other), and `other host time` (other). GPU seconds retain the raw kernel/transfer sums; host GPU seconds are null. Aggregate CSV reports do not identify critical-path intervals: if the four reported sums exceed measured wall, their wall allocations are scaled proportionally to fit. Other host time is the nonnegative wall remainder. These allocations are an aggregate approximation, not measured exclusive phase durations. No stage timestamps are invented; aggregate rows omit `start_s`, so stage utilisation remains null. No bound uses stage utilisation; same-GPU headroom comes from the concurrency probe.
- `stages.json` is an array of `{stage, wall_s, gpu_s}`, optionally including `kind`: `compute`, `transfer`, or `other`, and `start_s`: finite nonnegative elapsed seconds sharing the telemetry clock. Fixed profiler supplies `kind`; legacy rows without it remain accepted. `stage` is a non-empty string; `wall_s` is finite nonnegative seconds; `gpu_s` is finite nonnegative seconds or null and must be present. Fixed profiler wall allocations sum to measured wall without exceeding it; overlapping aggregate durations use the approximation above. Extra input fields are not copied to the packet. Empty arrays parse but fail the numeric gate.
- `total_wall_s.json` is an object with finite positive numeric `total_wall_s` in seconds. The sum of stage wall times must also be finite.
- `gpu_util.json` is an array of `{t, util}` samples collected with `nvidia-smi` during the measured run. `t` is finite nonnegative elapsed seconds; `util` is a finite GPU utilisation percentage in [0,100]. The fixed sampler records the mean across GPUs returned by nvidia-smi, then the summarizer retains only samples during the shared command and rebases monotonic timestamps to its start. A sample with zero utilisation is valid. Empty arrays parse but fail the numeric gate; missing files or malformed samples fail parsing.
- The deterministic pipeline writes `A/profile-packet.json` with exact keys:
  - `stages`: the validated timing rows, preserving optional `kind`, each augmented with `wall_fraction = min(1, wall_s / total_wall_s)`, `start_s`, and `mean_gpu_util` (fraction in [0,1], or null). When supplied, `start_s` must be measured on the telemetry clock. Legacy rows without `start_s` record null start and utilisation; stage order does not establish a measured telemetry window. Stage endpoints must remain finite. Stage utilisation is the arithmetic mean of telemetry percentages divided by 100 in `[start_s, start_s + wall_s)`; no samples means null. Never substitute GPU busy seconds for utilisation;
  - `total_wall_s`: the measured total;
  - `timed_fraction = min(1, sum(stage.wall_s) / total_wall_s)`;
  - `gpu_telemetry`: true only when the validated `gpu_util.json` array is non-empty; stage `gpu_s` values do not establish telemetry.
  - `gpu_count`: `C/box.json.gpu_count` when nonnegative integer, otherwise count parsed from allocation `type` (`gpu_<N>x_...`), otherwise the collected probe's `nvidia.gpus.length`. Unavailable inventory defaults conservatively to 1; an empty inventory records 0.
  - `concurrency`: the validated `concurrency.json` object (see Concurrency probe), or null when the probe did not run or its output is missing or invalid.
- Profile facts are `{profile_complete, timed_fraction, gpu_telemetry}` plus common `tokens_known` and `gpu_busy_known`, plus optional `headroom`: the packet's `concurrency.factor` (finite positive ratio) or null. Every executed profile stage emits `headroom`; it is optional in the v2 schema so older records stay valid, and it is null on SKIPPED/stub records. `profile_complete` is true when the command exits 0 and all three inputs validate, even when the numeric gate fails. The deterministic gate requires at least three stages, no process wrappers, `timed_fraction >= 0.9`, and `gpu_telemetry=true`. A stage is a process wrapper if its name contains a case-insensitive token `process`, `wrapper`, `telemetry`, `total`, or `overall` delimited by whitespace, underscores, hyphens, or string boundaries, or if its `wall_s` is within 2% of `total_wall_s` (inclusive). Any wrapper fails the gate, even alongside three internal stages. Numeric gate failures preserve the packet and use `error_class: numeric`; missing or invalid files use `error_class: parse`. A failed gate or parse stops downstream work without a profile repair.

## Concurrency probe: calibration of same-GPU headroom
- Purpose: measure, before any prediction or method exists, how much more throughput one GPU gives when the unchanged published command runs several times at once. This measured factor is the only source of same-GPU headroom for bounds. No model call is involved.
- When the profile command exits 0 and the profile gate passes, the pipeline uploads trusted `m5/concurrency_probe.py` to remote `profiler/` and, through boxrun as operation `concurrency` with the resolved `profile` budget, runs `python3 -I profiler/concurrency_probe.py harness/run_command.sh out/concurrency <budget_s>` from the shared run directory. Remote `out/concurrency/` is cleared first. Fetched files land in `A/results/profile/out/concurrency/`; the log is `A/results/profile/<receipt-id>.log`. There is no agent repair and no execution retry. Probe receipts count toward profile v1 `usd` and `gpu_s` like other box receipts.
- Each invocation runs `bash harness/run_command.sh` with its working directory set to a fresh `concurrency-work/<label>/` under the shared run directory. That directory holds a symlink to every top-level entry of the shared run directory except `out`, `profiler`, `concurrency-work` and `evaluation-work`, plus an empty `out/` directory. Labels are `single-1`, `single-2`, `single-3`, `n2-1`, `n2-2`, `n4-1` to `n4-4`. Each invocation's stdout and stderr go to `out/concurrency/logs/<label>.log` of the shared run directory. The environment is inherited unchanged apart from the MPS variables below. Nsight is not used.
- MPS: when `nvidia-cuda-mps-control` is on PATH, the probe starts a user-level daemon (`nvidia-cuda-mps-control -d`) with `CUDA_MPS_PIPE_DIRECTORY` and `CUDA_MPS_LOG_DIRECTORY` set to fresh directories under `concurrency-work/`, passes both variables to every invocation, and stops the daemon (`echo quit | nvidia-cuda-mps-control` with the same variables) before exiting, including after failures and on SIGTERM. If the daemon fails to start or any invocation fails under MPS, the probe stops the daemon, records `mps_failed: true`, and repeats the complete probe once without MPS in fresh work directories. Without the binary there is no MPS and `mps_failed` is false.
- Sequence: three single runs one after another, then 2 copies started together, then 4 copies started together. Wall seconds come from a monotonic clock around each subprocess; a batch's wall runs from launching its first copy to the exit of its last. `T1` is the median of the single walls. A single run that exits nonzero stops the probe with a null factor. Before each batch, the batch is skipped when `n * T1` exceeds `0.9 * budget_s` minus the probe's elapsed seconds. A batch counts only when every copy exits 0. For a counted batch, `factor_n = n * T1 / wall_n`.
- `out/concurrency/concurrency.json` is written atomically with exactly `{mps, mps_failed, single_wall_s, batches, factor}`:
  - `mps`: boolean, true when the recorded measurements ran under MPS; `mps_failed`: boolean;
  - `single_wall_s`: array of exactly three entries, each a finite positive number or null (failed or not run);
  - `batches`: exactly two rows, in order n=2 then n=4, each exactly `{n, wall_s, all_ok, skipped, factor}`; `wall_s` and `factor` are finite positive numbers or null, `all_ok` and `skipped` are booleans, and `factor` is null unless the batch counted;
  - `factor`: the largest counted `factor_n`, or null when any single run failed or no batch counted.
  The probe exits 0 whenever it writes the file, including with a null factor, and 2 when it cannot. It does not check output correctness: it measures throughput only.
- The probe never fails the profile stage and never changes the profile gate. A probe timeout, nonzero exit, or missing or invalid file gives packet `concurrency: null` and `headroom: null`. The pipeline validates the file against the exact shape above before copying it into the packet.

## C/receipts/ and stage failure signatures
- Every box command (uploads, probe, setup attempts, anchor execution, profiling, implementation) runs through `m5/boxrun.sh`; every receipt is `C/receipts/NNNN-<operation>.json`. Operations are `upload`, `probe`, `setup`, `anchors`, `profile`, `concurrency`, `implement-baseline`, `implement-state`, `implement-upload`, `implement-patch`, `setup-method`, `run-method`, `run-tests`; numbering continues across existing receipts. Receipt/log IDs contain no benchmark labels.
- Receipts use the boxrun format: `{name, rc, timed_out, wall_s, budget_s, overrun, fetched, started_utc, ended_utc, gpu_busy_s, gpu_busy_known}`. `name` is the receipt ID; `rc` is an integer remote exit code or null; `timed_out` and `fetched` are booleans; `wall_s` is nonnegative integer elapsed seconds; `budget_s` is the positive integer timeout supplied to boxrun; `overrun` is boolean, true on timeout or when measured wall_s exceeds budget_s; timestamps are UTC strings. Remote `out/` is fetched using the unchanged boxrun interface. Receipt contents stay in control; runtime logs stay in agent results.
- Failed reproduce/profile signatures have fixed `error_class`: `infra` for unavailable box execution/receipts, failed upload, or failed fetch after a successful command, or a fixed profiler infrastructure marker; `install` for failed setup after the bounded repair; `anchor` for an anchor-run failure or a failed anchor; `parse` for missing/invalid output files, unavailable harness files, or a nonzero profile command exit; `numeric` for a parsed profile that fails the stage-count, process-wrapper, coverage, or GPU telemetry gate. Exit codes are 4 for anchor failures, 3 for timeouts and 2 for the other failures. `infra` is added to the shared v1 error-class enum so the v2 envelope remains v1-valid. Box/fetch stdout and stderr are never copied into operator signatures.
- Any box receipt with rc=124 or timed_out=true records a timeout, even when fetch fails. A final timeout fails its stage with `error_class: timeout`, exit 3. Authored setup/anchor/method/test scripts consume their existing one bounded repair; method/test timeout repairs expose only the fixed timeout count plus budget/elapsed/overrun seconds, never test content. Transport, patch, probe, integrity and immutable evaluator commands permit one identical retry under the same budget, without editing scientific payloads or trusted scorers. A second timeout stops that operation and stage. The fixed profiler permits no repair or execution retry; its first timeout stops profiling with `error_class: timeout`.
- Reproduce, profile, implement and evaluate facts optionally add exactly typed timeout fields `{timed_out: boolean, budget_s: nonnegative integer, overrun: boolean}` when a box timeout occurs. `timed_out=true` records any attempt timing out, `budget_s` is the latest timed-out command's budget, and `overrun` is true when any timed-out receipt overruns. These fields survive a successful bounded repair; stage status then reflects the repaired result. Older records and SKIPPED/stub records retain their existing fact keys. No command output or new free-text fields enter signatures.
- Numeric ratio facts accept finite JSON numbers, including integer spellings such as `0` and `1`; booleans remain invalid. This permits fully timed profiles to emit the capped fraction `1`.
- Every stage records its own elapsed wall-clock seconds in v1 `wall_s`, excluding signature emission. SKIPPED stages measure only their skip handling, never the prior stage's duration.
- Runner results add boolean `tokens_known`, true when the provider reports input/output usage (including reported zeros). wf exposes `agent.usage()` as a cumulative snapshot `{calls, tokens_in, tokens_out, unknown}`; `unknown` counts runner attempts without usage. Repairs, failed attempts, shadow calls, and fallbacks all contribute; cached calls do not incur usage. Compatible runners without `tokens_known` are accepted when their input/output counts are integers.
- Stages aggregate reported input/output counts into v1 `tokens_in`/`tokens_out`; `facts.tokens_known` is true only when every runner attempt in that stage reports usage. With no attempts, existing unknown/null facts remain unchanged. Unknown counts retain numeric zero placeholders required by v1. `gpu_busy_known` reflects box receipt telemetry for reproduce/profile (see Compute metadata); harness profile evidence is reported separately. Downstream scientific stages are skipped after either failed gate; takeaways still runs.

## A/bounds.json (computed before the seal agent)
- `python3 m5/bounds.py <profile-packet.json> <out.json>` writes an atomic JSON object keyed by the five menu methods. Each value is `{p, k, bound, feasible, k_derivation, stages}`. `stages` contains actionable rows `{stage, kind, wall_fraction, mean_gpu_util, methods}`; `methods` lists every menu method that acts on that stage: whole-workload methods act on every stage, the others on stages of their kind. Exit 0 means success; exit 1 means invalid/missing input or unavailable output, with content-free diagnostics. Legacy packets without `gpu_count` default to 1. GPU counts must be nonnegative integers.
- Explicit stage `kind` takes precedence. Without it, lowercase stage names are split into ASCII alphanumeric tokens. Any token `transfer`, `transfers`, `h2d`, `d2h`, `htod`, `dtoh`, `copy`, `memcpy`, `upload`, or `download` means transfer; otherwise any token `compute`, `kernel`, `kernels`, `inference`, `training`, `forward`, or `backward` means compute. All other names mean other. Other stages and unmeasured time remain serial.
- The fixed mapping and maximum factors are:

  | Method | Acts on | p | Maximum factor k | bound |
  | --- | --- | --- | --- | --- |
  | data-parallel over inputs | whole workload | 1 | min(8, factor) | k |
  | ensembles | whole workload | 1 | min(8, factor) | k |
  | batching | whole workload | 1 | min(4, factor) | k |
  | pipelining | transfer stages | transfer fraction | 2 | Amdahl |
  | multi-GPU | compute stages | compute fraction | max(1, gpu_count) | Amdahl / k |

- `factor` is the packet's `concurrency.factor`: the same-GPU concurrent throughput measured during calibration (see Concurrency probe). When the packet has no `concurrency` key, `concurrency` is null, or its factor is null or below 1, whole-workload methods use `k=1` (bound 1, infeasible): missing measurements never manufacture headroom. A `concurrency` value that is neither null nor an object, or a factor that is neither null nor a finite number, fails parsing.
- `Amdahl = 1 / ((1-p) + p/k)` with `p = min(1, sum(actionable stage.wall_s) / total_wall_s)`. Fractions are recomputed from timings, never trusted from supplied `wall_fraction`. The multi-GPU bound is speedup per GPU-second, `Amdahl / k`: the same equal-cost basis that evaluation applies (`cost_ratio <= 1`) against a one-GPU baseline. It exceeds 1 only with superlinear evidence, which Amdahl cannot supply. Zero GPUs uses `k=1`.
- `k_derivation`: whole-workload methods record `{rule:"min(fixed_cap, concurrency factor)", fixed_cap, factor, mps}` (`factor` and `mps` null when unavailable); pipelining records `{rule:"fixed_cap", fixed_cap:2}`; multi-GPU records `{rule:"max(1, gpu_count)", gpu_count, amdahl, cost_basis:"equal_gpu_seconds"}`. Stage `mean_gpu_util` is carried for information only and never sets a factor.
- These are ceilings for sealed intervals, not measured method improvements. The concurrency factor is the measured throughput of plain concurrent runs; method code may exceed it in evaluation, but sealed intervals may not. `feasible` is true exactly when `bound >= 1.05`.
- The seal and propose prompts describe the bounds this way: whole-workload bounds are measured concurrent throughput on one GPU; pipelining is Amdahl over transfer time; multi-GPU bounds are per GPU-second at equal cost.
- The pipeline regenerates `A/bounds.json` before sealing, reads it before the agent call, and supplies its path and contents in the seal prompt. Missing or invalid profile evidence fails sealing; stale bounds cannot substitute for it.

## A/PREDICTIONS.json (written by the seal agent; checked, then sealed)
- `predictions`: an array, one item per feasible method, with unique methods taken from the menu ["data-parallel over inputs", "batching", "multi-GPU", "ensembles", "pipelining"]. Each item has:
  - `expected_speedup_interval` with finite numbers satisfying `low > 0`, `low <= high <= bound`, and width `high-low <= bound-1` for that method;
  - `outcome_vs_compute_points`, holding for every value in compute_budgets one {compute_budget, predicted_outcome, uncertainty}, all non-empty. `predicted_outcome` and `uncertainty` must not be null, empty strings, or empty objects/arrays. When no numeric forecast is supported, use an explicit non-empty declaration such as `predicted_outcome={not_applicable:true,reason:"fixed-work benchmark; no calibrated outcome curve"}` and explain unavailable evidence in `uncertainty`. Do not invent a number. `equal_outcome_target.not_applicable` does not waive these point fields.
- `outputs_stochastic` is a required boolean. It is true for Monte Carlo, sampling, or outputs affected by random seeds, including reproducible fixed-seed runs.
- Stochastic seals require statistical `equivalence_metrics` with positive absolute margins and non-empty names/sources, `paired_seed_tests.kind="paired_median"` with unique integer seeds, and `confidence_rule.equivalence={kind:"paired_median",confidence}` with finite confidence in [0.5,1). The sealed significance level is `1-confidence`. Margins come from scientific requirements or baseline variability (for example Monte Carlo standard error); paired-difference confidence intervals must lie within the sealed margins. Exact/bitwise rules, zero margins, relative margins, deterministic seed declarations, and prose-only rules are rejected for stochastic outputs. Exact or bitwise rules apply only to deterministic outputs.
- Required non-empty keys: equivalence_metrics, paired_seed_tests, sample_sizes, confidence_rule, hardware_cost_basis, timing_scope, minimum_worthwhile_gain (a number > 1), evaluation_inputs, splits, compute_budgets (at least 3 distinct positive numbers), repetitions (an integer >= 5), warmup, scheduling_order and equal_outcome_target.
- `infeasible_methods` is a required array of `{method, reason}`, exactly once for every method with `bound < 1.05`; reasons are non-empty strings. These methods must never appear in predictions. Every feasible method must appear exactly once in predictions and never in infeasible_methods. With at least two feasible methods, all prediction intervals must not be identical. One feasible method is exempt from this comparison.
- Seal failures use `error_class: numeric` (exit 2), including invalid protocol, invalid intervals, missing/duplicate method coverage, or unavailable bounds. Facts retain exactly `seal_present`, `seal_verified`, `prediction_count` plus common facts; `prediction_count` counts submitted prediction rows, excluding infeasible entries. An empty feasible menu may be sealed as a negative result, then fails the gate and stops method work.
- The seal prompt embeds stochastic and deterministic JSON skeletons generated by `m5/seal_protocol.js`, using the same constants as its deterministic validation. Both specify `equivalence_metrics=[{name,source,tolerance:{abs:number}}]` with non-empty **string** names and sources, never citation objects. The stochastic example uses `paired_seed_tests={kind:"paired_median",seeds:[0,1,2,3,4,5]}` and a positive absolute margin; the deterministic example uses `{kind:"deterministic",justification:"scientific reason"}` and zero absolute tolerance. Both include `evaluation_inputs={ids:["held-out-1"]}`, matching `sample_sizes={inputs:1,seeds:6}` (stochastic) or `{inputs:1,seeds:1}` (deterministic), and `confidence_rule={performance:{kind:"paired_median",confidence:0.95},equivalence:{kind:"paired_median",confidence:0.95}}`. Example metric names, sources, margins, identities and justifications must be replaced with supported scientific choices. Six seeds give finite two-sided 95% bounds for one metric; more metrics or higher confidence can require more seeds. Deterministic evaluation uses one null seed.
- One bounded repair is allowed for a readable but invalid protocol or a missing/malformed predictions file, before any immutable seal files are written. Initial `seal` and optional `seal-repair` calls use `ls-writer`, requested model `sonnet`, `repairable:false`, `fresh:true`; runner-level repair is disabled. The repair prompt supplies only script-owned failing reason codes and field paths as validation feedback, without values, evidence, bounds, measurements, exception text or model commentary. The agent may read and rewrite only `A/PREDICTIONS.json`, preserving scientific intent without inventing evidence or loosening tolerances. The complete deterministic checks run again exactly once; failure stops, success proceeds to the existing seal writer. Bounds generation, agent execution, seal storage/verification failures and verified negative results do not trigger repair. Repair never allocates a seal number or modifies prior receipts/frozen predictions. No field paths or feedback enter operator signatures.
- `C/stages/seal.json` adds `reason_codes`, an array containing the final failed check's fixed code, or `[]` for PASS, SKIPPED, and stub results. Checks stop at the first failure, in the order below. Exceptions use the code for the operation/check in progress. Codes are script-owned literals; no agent text, exception messages, methods, paths, or scientific content enter this field. Existing numeric error class, exit code, signature facts, and immutable seal receipt format are unchanged.

  | Code | Failed check or operation |
  | --- | --- |
  | `bounds_generation_failed` | Regenerate and read bounds from the profile packet. |
  | `agent_failed` | Seal agent threw or returned no reply. |
  | `predictions_read_failed` | Read and parse the predictions file. |
  | `predictions_invalid` | Predictions object must contain a predictions array. |
  | `protocol_incomplete` | Required fields, stochastic flag, budgets, repetitions, worthwhile gain, unique menu methods, or finite positive ordered intervals are invalid. |
  | `compute_points_incomplete` | Every predicted method needs a point at every budget with non-empty outcome and uncertainty. |
  | `stochastic_equivalence_invalid` | Stochastic paired seeds, confidence rule, or positive absolute statistical margins are invalid. |
  | `bounds_coverage_invalid` | Feasible prediction coverage or infeasible exclusions/reasons are invalid. |
  | `interval_bounds_invalid` | An interval exceeds its bound or its allowed width. |
  | `intervals_identical` | At least two methods are feasible but all intervals are identical. |
  | `seal_write_failed` | Canonicalize/write predictions and create the immutable seal files. |
  | `seal_verification_failed` | Read/hash verification of the current and frozen predictions failed. |
  | `no_feasible_methods` | Verified negative seal has zero predictions; stop method work. |

- Seal: C/seals/NNNN.json {sha256, path, utc}. The sha256 is over the canonical JSON: keys sorted recursively, array order kept, compact separators, UTF-8. Numbering continues; nothing is overwritten.

## Propose, independent votes, and the one-shot gate
- Before reading profile/bounds or calling any agent, propose selects the highest-numbered `C/seals/NNNN.json` and hashes the exact bytes of both `A/PREDICTIONS.json` and the receipt's frozen `path`. Both must match `sha256`. A missing, unreadable, or mismatched seal fails with `error_class: other` (exit 2), with no model calls.
- The deterministic step reads `A/profile-packet.json`, `A/bounds.json`, and the verified predictions. Feasible predicted methods have `bounds[method].feasible=true` and `bound >= 1.05`. Their ranking score is `min(low/2 + high/2, bound)`, descending; ties follow the fixed menu order. Unknown/duplicate methods or malformed intervals fail parsing.
- Resource guards use `C/box.json.gpu_count` when supplied (a nonnegative integer), otherwise the count in allocation `type` such as `gpu_1x_a10`. Probe capacity is `A/results/probe/probe.json.nvidia.gpus.length`. Available GPUs are the smaller count; either inventory unavailable means no method passes. Ordinary methods require one GPU; multi-GPU requires `max(2, bounds[method].k)` GPUs, matching the factor used for its bound. Methods failing these guards are excluded from selection.
- `A/propose-packet.json` contains only `{ranked_methods, stage_to_method, bounds, sealed_equivalence_rule}`. Ranked rows are `{method,bounds}` in deterministic ranking order, restricted to feasible resource-safe methods. `stage_to_method` contains every stage as `{stage,wall_fraction,mean_gpu_util,methods}`; other stages map to an empty method list. `bounds` contains all five bounds and their `k_derivation` and actionable stages. `sealed_equivalence_rule` contains only `outputs_stochastic`, `equivalence_metrics`, `paired_seed_tests`, `sample_sizes`, and the equivalence portion of `confidence_rule`. No raw profile, predicted outcome curves, intake, resource inventory, performance protocol, or other content enters the packet. Prompts state that ranked methods already passed deterministic GPU resource guards. Proposer and all five skeptics receive the identical packet; skeptics additionally receive the validated proposal. When no feasible resource-safe method remains, the gate fails without model calls.
- One `propose` call (`ls-writer`, requested model `sonnet`) reads only the embedded packet and writes `A/proposal.json`, with exactly `{method, rationale, plan_steps, files_expected, risks}`. `method` must be in the ranked list; `rationale` is a non-empty string; the remaining fields are arrays of non-empty strings. `plan_steps` and `files_expected` must be non-empty; `risks` may be empty. The call cannot implement code or access the box. Invalid/missing proposals fail with `error_class: parse` (exit 2).
- Five concurrent skeptic calls (`qt-bare`, requested model `haiku`, mapping to the cheap tier) each start a fresh session. Ballot `i` uses label `skeptic-<i>`, so names are `x-<raid>-skeptic-1` through `x-<raid>-skeptic-5` with no sibling suffix. Each receives the same prepared packet and validated proposal, plus its ballot number, and no other votes. Model family/endpoint selection remains with the workflow configuration (see m5 model policy); the pipeline pins no endpoint.
- Ballots have exactly `{vote, reason_codes}`. `vote` is `approve`, `reject`, or `abstain`; `reason_codes` is an array (possibly empty) containing only `exceeds_bound`, `not_parallelisable`, `changes_method`, `equivalence_risk`, `resource_mismatch`, `weak_profile_evidence`, or `other`. The pipeline writes `A/votes/1.json` through `5.json`; missing/failed/invalid responses are written as JSON `null` and count against approval. No vote repair or replacement is allowed.
- These calls use wf option `repairable:false`: no repair turn, schema/no-JSON failures cannot trigger fallback, panels are bypassed, and shadow mode becomes fallback. Transport failures can still use the configured family chain. This preserves existing default behavior for other calls. `fresh:true` bypasses the resume cache for proposer and skeptics; every ballot starts a new runner session.
- `A/GATE.json` records the propose facts. Its presence prevents another proposal/vote round in the same run (fails with `other`). Gate requires at least four approvals, the selected sealed interval's `high >= minimum_worthwhile_gain`, `high <= bound`, and passing resource guards. Gate failures use `numeric` (exit 2); malformed inputs use `parse`. Downstream stages skip after failure; takeaways still runs.
- Facts have exactly `{method, expected_speedup, votes_approve, votes_total, vote_share, gate_pass}` plus common `tokens_known` and `gpu_busy_known`. `method` is a menu entry or `none`; `expected_speedup` is the selected sealed interval midpoint, or null before selection. Executed stages initialize `votes_approve=0`, `votes_total=5`, `vote_share=0`, and `gate_pass=false`; `vote_share=votes_approve/5`. Missing votes never reduce the denominator. SKIPPED/stub stages retain the existing null facts contract. Scientific text and reason codes remain in the agent view.

## Implement, frozen independent tests, and launch review
- `implement` verifies the latest seal against both prediction copies before doing work, and checks that the proposal selects a sealed method with equivalence metrics and a paired-seed protocol. It rechecks the seal before authoring, each attempt, and after review. A new latest seal, even with identical prediction bytes, invalidates the in-progress implementation. Existing `C/implement/`, `A/tests/`, `A/method/`, or `A/REVIEW.json` prevents restarting this stage and resetting its repair budget. Explicit `args.stub.implement` retains the existing stub contract.
- The pipeline first snapshots the already-built remote `baseline-published/`, `data/`, and a copy of the baseline `out/` at `baseline-out/`. It does not rebuild or substitute the published baseline. All snapshots and subsequent integrity checks run through boxrun. Source, data, and baseline-output hashes must remain unchanged after authoring and around both attempts.
- There is one initial `tests` call and one initial `implement` call, both `ls-writer`, requested model `sonnet`, `repairable:false`, `fresh:true`. Tests are authored and frozen **before** the method-author call, so method results cannot precede the freeze. The test author receives only proposal, intake, baseline harness/interface and reproduced baseline outputs, and the sealed predictions/protocol. The method author receives proposal, intake, baseline harness, box probe and sealed predictions; it never receives independent tests, fixtures or test transcripts. Only the initial method-author call may access the already-running box through `~/.cache/metis-serve/box.sh`.
- wf's optional agent setting `isolation` has `{directory, hidden, box_access}`: an absolute private view directory, an array of absolute paths hidden from that role, and a boolean permitting box credentials. It overrides cwd and add-dirs, disables resume-cache reuse and provider-session export, and is forwarded to every dispatched family, including fallbacks. Real dispatch uses bubblewrap with a read-only host filesystem, private `/tmp`, PID/IPC namespaces, hidden run/workflow paths and provider histories, and a fresh writable HOME containing authentication files only. The view is the only writable host directory. The initial implementer additionally receives read-only access to the existing box wrapper and SSH keys. Test, review and repair roles cannot access them. No sandbox fallback grants broader access: missing bubblewrap or unavailable namespaces fails the call. `WF_STUB` remains an explicit test double, bypassing provider execution. Temporary views/provider state are removed after the stage; raw provider logs remain under the role's workflow transcript directory and are hidden from other roles.
- Each view has top-level `proposal.json`, `PREDICTIONS.json`, `intake/`, and `harness/`. Test views additionally have `baseline-out/`; method views have `probe.json` and, on repair, the previous three method files. Writable author output is `tests/` or `method/`. Review views contain `method/`, proposal, predictions, intake, `implement-payload.json` and `seal.json`; `seal.json` is the existing seal receipt plus `receipt`, its numbered receipt filename. Review receives these scientific inputs embedded in its prompt, using the tool-free `qt-bare` role. No view contains another role's source or transcripts except the method source explicitly supplied to review.

### A/method/ and remote execution interface
- The method author writes three required nonempty files: `method.patch` (git-style paths relative to the published source root), `setup_method.sh`, and `run_method.sh`. An optional fourth file, `run_anchors.sh`, implements the method anchor protocol. No other files are allowed. Shell scripts must pass `bash -n`. The pipeline copies them from the private view into `A/method/`; neither author writes control state.
- Each attempt uploads method files to remote `payload/method/` and frozen tests/fixtures to `payload/tests/`. Uploads append independently decodable base64 chunks of at most 24,576 characters, batching commands below 32,768 characters to avoid shell argument limits; each batch has its own receipt. It creates a fresh source copy at `method/` using `cp -a baseline-published method`; patch checking and application use `git apply` with an explicit detached Git context and that copy as work tree, so copied repository/worktree metadata cannot redirect writes into the baseline. A retry always starts from a fresh copy.
- The scripts run from the same remote run directory used by reproduce: `bash payload/method/setup_method.sh`, then `bash payload/method/run_method.sh`, then `bash payload/tests/run_tests.sh`. All receive absolute environment paths `BASELINE_DIR` (original published source), `METHOD_DIR` (patched source copy), `BASELINE_OUT` (frozen baseline outputs), and `METHOD_OUT` (remote `out/`). Setup builds the patched copy; run uses the same representative scale, inputs and seeds and writes actual method outputs in exactly the baseline's format and relative output locations. Fixtures resolve relative to `run_tests.sh`. Remote `out/` is cleared before setup and again before method execution; `out/tests.json` is removed immediately before tests. A previous baseline/method/report cannot satisfy a new attempt.
- `A/implement-payload.json` records the current attempt with exactly `{attempt, remote_directory, baseline_directory, method_directory, baseline_outputs, method_outputs, tests_sha256, seal_sha256, method_files, timeouts}`. `attempt` is 1 or 2. Relative directory values are `baseline-published`, `method`, `baseline-out`, and `out`; `remote_directory` is the absolute shared remote directory. `method_files` contains `{path, sha256}` for every provided method file, using relative names and SHA-256 of exact bytes. `timeouts` has positive integer seconds for `setup_method`, `run_method`, `run_tests`. Hashes are lowercase 64-digit hexadecimal strings. The payload is regenerated after repair and reviewed only in its final form.

### A/tests/ and out/tests.json
- The test author writes `run_tests.sh` and optional fixtures under its private `tests/`. Files and nested directories must be regular files/directories, never symlinks or special files; the same restriction applies when copying evidence and method artifacts across views. Scripts must pass `bash -n`. After copying to `A/tests/`, all files become mode 0444 and directories 0555; the pipeline records their tree hash in `C/implement/tests.json` before any method-author call. Remote tests receive the same modes. The pipeline checks the frozen local hash repeatedly and the remote test hash before/after execution, including failed method attempts. Changing tests invalidates blindness and stops the stage without repair.
- Tests check actual outputs for input loss, duplication, ordering, non-divisible tails/final inputs, paired seeds or the seal's justified deterministic declaration, and scientific equivalence within sealed tolerances. They may reuse upstream tests but must not assert on method source or execute/read method scripts. A valid report must include unique case IDs `dropped_inputs`, `duplicated_inputs`, `ordering`, `tail_handling`, `seeds`, and `equivalence`; additional unique nonempty IDs are allowed.
- Remote `out/tests.json` has **exactly** `{passed, failed, cases}`. Counts are nonnegative integers equal to the passing/failing case counts. `cases` is nonempty; each row has exactly `{id, pass, reason_code}`. `pass` is boolean. Passing rows require `reason_code:null`; failing rows require one of `dropped_inputs`, `duplicated_inputs`, `ordering`, `tail_handling`, `seeds`, `equivalence`, `missing_output`, `invalid_output`, `upstream`, `other`. Reports with extra keys, duplicate/missing required IDs, inconsistent counts, unknown reasons, or missing/invalid values fail parsing. Tests pass only when the command exits 0, a valid report is present, and `failed=0`. A nonzero exit cannot be overridden by a passing report.
- There are at most two execution attempts and one method repair, never another test-author call or a second review. Repair uses the same `implement` label, requested model `sonnet`, `retry:1`, a new isolated session, the original scientific inputs and previous method files. Failure feedback is a `reason_code_counts` object with positive integer counts, plus numeric budget, elapsed and overrun seconds for a timeout. Failed test cases are aggregated by their fixed `reason_code`; infrastructure, logs, case IDs, values and test source are never passed to the author. Pipeline failure categories are `patch_applies`, `setup_failed`, `run_failed`, `invalid_report`, `tests_failed` (nonzero test exit with no failing cases), or `timeout`. Infrastructure/fetch and integrity failures stop immediately without repair. Any second execution failure stops.

### Implementation control records, results and verdict
- `C/implement/started.json` has exactly `{seal_sha256, utc}` and marks the consumed implementation budget. `C/implement/baseline.json` has exactly `{baseline_sha256, data_sha256, baseline_outputs_sha256}`. Digests are lowercase SHA-256 strings.
- `C/implement/tests.json` is created exclusively, mode 0444, with exactly `{sha256, files, seal_sha256, utc}`. `sha256` is the frozen tree digest. `files` is an ordered list of `{path, sha256}` with slash-separated paths relative to `A/tests/` and individual file-content hashes. This immutable receipt precedes all method-author work. `C/implement/attempt-1.json` and, on a second failure, `attempt-2.json` contain exactly `{attempt, reason_code_counts}`; categories are the fixed enums above, never content-derived strings.
- `m5/implement_state.py` accepts key/directory pairs and prints one JSON object mapping those keys to tree digests; it exits 1 with a content-free diagnostic on invalid trees or arguments. It traverses each directory depth first, sorting sibling names by Unicode code point, without following links. Its digest input is compact ASCII JSON (`ensure_ascii=true`) of rows: `[relative_path,"directory",mode]`, `[relative_path,"file",mode,file_sha256]`, or `[relative_path,"link",mode,link_target]`; modes are integer permission bits and relative paths use `/`. The root itself and timestamps are excluded. Baseline links are hashed by target string; linked content outside the frozen trees is not included. Special files and symlink roots are rejected.
- Each remote integrity command writes `out/implement-state.json`, containing the three baseline/data/output digests above and, once tests are uploaded, `tests_sha256` and `method_payload_sha256` (the uploaded `payload/method/` tree). The latter must remain equal to the pre-execution digest for that attempt, so setup/run/tests cannot replace the uploaded patch or scripts. All are computed from actual remote trees with the committed helper fed to `python3 -I`; method scripts cannot replace a stored helper to forge an integrity check. Control receipts, never model replies, establish these hashes.
- All command receipts use the existing `C/receipts/` contract. Baseline snapshot logs/fetched outputs go to `A/results/implement/baseline/`. Attempts use `A/results/implement/attempt-<1|2>/<phase>/`, with phases `upload`, `before`, `patch`, `setup`, `run`, `after-method`, `tests`, `after-tests`. Each command fetches `out/` and its numbered log there; commands not reached have no phase directory. The post-author integrity check is under `attempt-0/after-author/`. The latest completed attempt's method outputs, test report when available and integrity metadata are also copied to `A/results/implement/out/`, preserving prior attempts separately.
- After successful tests and any repair, one `review` call (`qt-bare`, requested model `sonnet`, `repairable:false`, `fresh:true`; routed to Claude by the m5 model policy, so the reviewer's family differs from the Codex method author) checks the final patch/scripts, proposal, verified seal, execution contract and payload before downstream launch/evaluation. `A/REVIEW.json` has exactly `{pass, reason_codes}`. `pass` is boolean; reasons are an array containing only `changes_method`, `equivalence_risk`, `resource_mismatch`, `changes_baseline`, `changes_protocol`, `invalid_payload`, `cost_guard`, `other`. Passing review requires an empty reasons array. Missing/malformed review fails parsing. Reviewer cannot change tests.
- Implement facts have exactly `{patch_applies, tests_pass, blind_tests, launch_review_pass}` plus common facts. Executed stages initialize all four false; skipped/stub stages retain null facts. `patch_applies` describes the latest attempt's actual check/application; `tests_pass` requires both report and successful exit; `blind_tests` requires the prior immutable freeze, isolated authors and unchanged tests; `launch_review_pass` reflects the final independent review. PASS requires all four true and the seal still verifying. Parse failures use `parse`, setup failures `install`, failed method/test execution or equivalence `numeric`, infrastructure/fetch failures `infra`, and baseline/test integrity, restart or rejected-review failures `other`, with exit 2 except timeouts (`timeout`, exit 3). Failed/skipped downstream stages and takeaways follow the existing pipeline contract. No test content or reason-count maps enter operator signatures.

## Evaluate: executable sealed protocol (v1)

Evaluation uses deterministic Python scorers, with no model calls or repairs. It verifies the latest seal, launch review, implementation payload and frozen independent tests before running workloads. It never builds a tuned control; `speedup_tuned` is always null in v1. Explicit `args.stub.evaluate` retains the existing stub contract. Other stage stubs do not supply evaluation evidence.

The seal must supply the following executable fields. Existing prose-only or unsupported protocols produce VOID; the evaluator never interprets prose as executable rules or substitutes defaults for scientific decisions.

```json
{
  "evaluation_inputs": {"ids": ["input-0", "input-1"], "pin": "immutable input specification"},
  "sample_sizes": {"inputs": 2, "seeds": 1},
  "equivalence_metrics": [{"name": "accuracy", "tolerance": {"abs": 0.001}, "source": "scientific requirement citation"}],
  "paired_seed_tests": {"kind": "deterministic", "justification": "scientific reason"},
  "confidence_rule": {
    "equivalence": {"kind": "paired_median", "confidence": 0.95},
    "performance": {"kind": "paired_median", "confidence": 0.95}
  },
  "timing_scope": {"kind": "process_wall", "gpu_synchronization": "adapter", "description": "includes launch, transfer, compute and merge"},
  "hardware_cost_basis": {"baseline_gpus": 1, "method_gpus": 1, "budget_unit": "gpu_s"},
  "warmup": 1,
  "repetitions": 7,
  "scheduling_order": {"kind": "randomized_pairs", "seed": 42},
  "minimum_worthwhile_gain": 1.05,
  "compute_budgets": [60, 120, 240],
  "equal_outcome_target": {"metric": "accuracy", "comparison": ">=", "target": 0.9}
}
```

- Input IDs are unique nonempty strings. Records must cover exactly the Cartesian product, in seed-major then input-ID order. `sample_sizes.inputs` and `.seeds` are integer counts that must match the fixed lists. Deterministic runs use one null seed. Stochastic protocols use `{kind:"paired_median", seeds:[unique integers]}` instead; the same seeds apply to both arms. Input pins/specifications and splits remain part of the complete sealed protocol supplied to each adapter.
- Metrics have unique nonempty `name`, nonempty `source` and tolerance. Deterministic tolerance is a finite nonnegative absolute number, `{abs:x}` or `{rel:x}`. Each paired row must satisfy `abs(method-baseline) <= tolerance`; relative tolerance multiplies `abs(baseline)`, including exact agreement at zero. All reported metric values must be finite numbers, never booleans.
- Stochastic metrics require absolute tolerance. For each metric and seed, average the paired method-minus-baseline differences over fixed inputs. Use an exact sign-test confidence interval for the median of those seed averages. Equivalence requires the entire interval inside `[-tolerance,+tolerance]`, including endpoints. Bonferroni divides the two-sided error probability across sealed metrics. This tests equivalence of the median paired effect defined by the seal; it is not a failure-to-reject difference test.
- Confidence is finite in `[0.5,1)`. For sorted samples `x` of length `n`, select the largest `k >= 1` with `P(Binomial(n,0.5) < k) <= alpha/2` for equivalence or `<= alpha` for performance. Equivalence bounds are `[x[k-1],x[n-k]]`; performance uses lower bound `x[k-1]` and an unbounded upper endpoint represented by null. No admissible `k` means insufficient measurements and VOID. At 95%, one metric needs at least six independent seed pairs; performance needs at least five timing pairs. More metrics or greater confidence can require more seeds. No bootstrap randomness or asymptotic approximation is used.
- `warmup` is an integer >=0, measured but excluded from performance statistics; `repetitions` is an integer >=5. Each pair contains one run of each arm in independently shuffled order from Python's `random.Random(sealed_seed)`. Warmup pairs and curve arm order use the same RNG stream. Both arms use the same box, sealed inputs, seeds, configuration and scope. Published baseline is never tuned.
- `timing_scope.kind` is `process_wall` (trusted `perf_counter` around the complete adapter subprocess) or `reported_wall` (adapter's measured `wall_s`, for scopes requiring program timers). Both arms must echo the exact sealed scope. Adapters must synchronize all used GPUs before completion/timer stop and include launch/transfer/merge overhead required by the scope. Missing or mismatched scope is VOID. Reported timings are actual program measurements, never extrapolated estimates.
- `hardware_cost_basis` declares positive integer GPU counts per arm, bounded by both box and probe capacity. `C/box.json.price_usd_h` must be finite and positive. Per-GPU tariff is box hourly price divided by available box GPUs; run USD is measured seconds times GPUs used times this tariff /3600. Pair speedup is baseline seconds / method seconds; `speedup_published` is the median pair speedup. `cost_ratio` is the median paired method-USD / baseline-USD ratio. `equal_cost` means `cost_ratio <= 1`. Performance requires matched scientific outputs on warmups and timed pairs, the sealed one-sided confidence lower bound >= `minimum_worthwhile_gain`, and equal cost. `prediction_ratio` divides median speedup by the selected sealed interval's midpoint. Zero or unavailable pricing cannot establish equal cost.
- Curves use GPU-second budgets. Each invocation receives the sealed budget and is bounded by both its script timeout and budget / GPUs used. Allocation seconds include the complete subprocess, even with reported timing. Both arms must finish within the budget and echo it exactly. Each complete budget produces one point with both measured outcomes; no interpolation or extrapolation occurs. `equal_outcome_target` defines a metric, finite numeric `target`, and comparison `==`, `>`, `>=`, `<` or `<=`; each outcome is the mean metric over fixed rows and records `target_achieved`. `uncertainty:{min,max}` reports the observed range, not a confidence interval. A failed or unachieved target is retained. If this benchmark has no outcome curve, seal `{not_applicable:true,reason:"explicit scientific reason"}` instead; `curve_points=0`, `not_applicable=true`.

### Baseline and method adapter interface

The harness may additionally provide `A/harness/run_evaluation.sh`, uploaded during reproduce. Otherwise the evaluator uses `harness/run_anchors.sh` for baseline evaluation. The baseline adapter must run the exact published configuration. The method adapter is `payload/method/run_method.sh`. For validity, use optional `payload/method/run_anchors.sh`; absent that file, derive the anchor invocation by running `run_method.sh` with `EVAL_MODE=anchors`. Both routes must rerun the complete published anchor protocol under the method and write `out/anchors_measured.json`; copying baseline or published values is forbidden.

Every invocation runs in a fresh `evaluation-work/<phase>/<index>/<arm>/` with empty `out/` and links to the fixed `baseline-published/`, `method/`, `data/`, `harness/`, `payload/`, `baseline-out/` trees. This preserves relative paths while separating repetitions. Environment:

- `BASELINE_DIR`, `METHOD_DIR`, `BASELINE_OUT`: absolute fixed source/output paths; `METHOD_OUT` and `EVAL_OUT`: this invocation's absolute empty output directory.
- `EVAL_ARM`: `baseline` or `method`; `EVAL_MODE`: `anchors`, `equivalence`, `warmup`, `performance`, or `curve`.
- `EVAL_PROTOCOL`: absolute path to the complete immutable sealed predictions JSON, including splits, input pins and seeds. `EVAL_INPUTS` and `EVAL_SEEDS` are JSON encodings of `evaluation_inputs` and `paired_seed_tests`.
- `EVAL_COMPUTE_BUDGET`: empty outside curves; numeric budget string for curve runs.

Non-anchor adapters write `EVAL_OUT/evaluation.json`:

```json
{
  "records": [{"input_id": "input-0", "seed": null, "metrics": {"accuracy": 0.95}}],
  "timing_scope": {"kind": "process_wall", "gpu_synchronization": "adapter", "description": "includes launch, transfer, compute and merge"},
  "gpu_count": 1,
  "wall_s": 1.2,
  "compute_budget": 60
}
```

`records` is required in all non-anchor modes. `wall_s` is required and finite positive only for reported timing. `gpu_count` must match the arm's sealed count. Curves require exact numeric `compute_budget`; it is optional otherwise. Additional program output fields are allowed. Arrays with missing/duplicate/reordered inputs, wrong seeds, unequal counts, or omitted final inputs fail equivalence. Missing/malformed files or metrics are unavailable measurements, producing VOID. Scripts exit nonzero on execution failure and must not modify baseline, data, frozen outputs/tests, harness, evaluator payload or method source during evaluation.

### Evaluation artifacts, provenance and failures

- `m5/eval_validity.py`, `eval_equivalence.py`, `eval_performance.py` accept `--stage <validity|equivalence|performance> --in <manifest.json> --out <directory>` (the corresponding stage only; stage flag is optional). `eval_common.py` shares IO, invocation and exact confidence calculations; validity calls `score_anchors.score` unchanged.
- Script-owned `C/evaluate/manifest.json` is created exclusively, mode 0444. Existing `C/evaluate/` prevents a new evaluation round. It contains `{remote_directory,protocol,prediction,box,gpu_count,run_timeout_s,method_files,anchors,input_hashes}`. `prediction` is the selected method's sealed prediction. `input_hashes` contains `seal_sha256`, the implementation's baseline/data/output/test/method-payload tree hashes, `anchors_sha256`, local `harness_sha256`, and `evaluators` mapping each uploaded Python filename to its exact-byte SHA-256. Method files must match the reviewed payload. Before/after every scorer, trusted integrity commands recheck source, data, frozen baseline outputs, tests, method payload, built method source, harness, evaluator helpers and manifest. Initial remote hashes additionally freeze method source, harness and evaluator payload for the evaluation round; source/harness modes can differ from local copies. The seal and local frozen tests are rechecked too.
- Helpers, manifest and sealed predictions are uploaded in bounded base64 chunks through boxrun. Operations are `evaluate-upload`, `evaluate-state-before-<stage>`, `evaluate-state-after-<stage>`, and `evaluate-<stage>`. Logs and each fetched `out/` remain in `A/results/evaluate/<operation>/`; repeated upload receipts/logs share their operation directory. Remote artifacts are `out/eval/{validity.json,equivalence.json,performance.json,curve.json,raw.jsonl}`. The final fetched evaluation files/logs are also copied directly to `A/results/evaluate/`. `out/evaluate-state.json` contains remote tree hashes. Nothing scientific enters operator signatures.
- All verdicts have `status` (`PASS`, `FAIL`, `VOID`) and, once executed, `input_hashes`. `validity.json` adds `validity_pass` and the exact anchor score fields `anchors`, `anchors_passed`, `anchors_total`, `all_passed`. `equivalence.json` adds `equivalence_pass` and `metrics`: deterministic rows `{metric,passed,max_abs_difference}`, stochastic rows `{metric,passed,difference_interval,confidence}`, or a failed alignment row `{passed:false,reason_code:"counts_or_alignment"}`. `performance.json` adds `performance_pass`, `equal_cost`, `speedup_published`, `speedup_tuned:null`, `cost_ratio`, `prediction_ratio`, `confidence`, `speedup_interval`, `matched_outcome`, `pairs`. Each pair has `{index,order,baseline_s,method_s,baseline_gpus,method_gpus,speedup,cost_ratio,baseline_usd,method_usd}`.
- `curve.json` has `{status,input_hashes,not_applicable,curve_points,points}`, plus a reason for not-applicable/invalid protocols. Each point has `compute_budget` and `baseline`/`method` objects. Successful arms have `{status:"PASS",outcome,target_achieved,uncertainty,allocated_gpu_hours,usd}`; unavailable arms have `{status:"VOID",outcome:null,reason_code}`. `curve_points` counts budgets with both outcomes measured. Failed budgets remain in `points`; partial successful budgets are saved after every iteration. An unachieved target is a measured outcome, not a missing point.
- `raw.jsonl` appends `{phase,index,arm,compute_budget,rc,process_wall_s}` immediately after execution and a second row with `output_sha256` and actual `report` after successful output parsing. Each invocation preserves its `<phase>-<index>-<arm>.log` and parsed `.json` alongside the verdicts. Anchor measurements are saved as `anchors_measured.json`.
- Before execution all four local verdicts start as `{status:"VOID",reason_code:"not_run"}`. Scorer parse/missing-output failures write `status:"VOID"`, the corresponding `*_pass:null`, and fixed `reason_code:"missing_or_invalid_measurements"`. Invalid manifests use `invalid_manifest`. Earlier raw/phase evidence is retained. Finite measurements are required: zero placeholders never establish PASS.
- Validity failure stops immediately: `status:FAIL`, `error_class:anchor`, exit 4 (`exit_kind:anchor`), `run_valid:false`. Nonzero anchor execution also fails validity; absent/invalid anchor files or any missing/non-numeric anchor measurement are VOID with `validity_pass:null`, retaining scored rows when available. Equivalence/performance scientific failure uses FAIL, `numeric`, exit 5 (`later_stage`). Infrastructure/fetch/integrity or unavailable measurement failures use VOID, fixed `infra`/`other`/`parse`, exit 2; outer scorer timeout uses `timeout`, exit 3. Missing curves prevent overall PASS; an already measured performance failure retains FAIL/exit 5 while the curve stays VOID. Subsequent verdicts remain independently VOID when not run; no performance result can override invalidity. All failures still proceed to takeaways. A box timeout permits one identical bounded scorer retry; immutable reviewed payloads and sealed protocol cannot be changed during evaluation.
- Evaluate facts contain `{validity_pass,equivalence_pass,performance_pass,equal_cost,speedup_published,speedup_tuned,cost_ratio,prediction_ratio,curve_points,tokens_known,gpu_busy_known}`, plus the optional timeout fields defined above. Unavailable values are null, including unmeasured curves; explicitly inapplicable curves have count 0. No model calls means `tokens_known:true`; receipt telemetry owns `gpu_busy_known`. Overall PASS requires three passing verdicts and a complete or explicitly inapplicable curve. Stage stub/SKIPPED facts preserve their existing null contract.
- `stage_budgets_s.evaluate` bounds each complete scorer command, default 2400 seconds. Each subprocess uses the resolved method_run budget; uploads/integrity commands use method_setup. Configure budgets for the fixed sealed run count. Boxrun interface and content-free accounting remain unchanged.

## Compute metadata
- The shared v1 `model_family` enum now also accepts `cursor`: its complete set is `codex`, `cursor`, `opencode`, `lambda`, `claude`, `none`. Each stage uses the answering model in that stage's successful wf journal `result`/`cached` events, not the requested model or failed attempts. A `lambda/` model reports `lambda` despite OpenCode dispatch. With several answering families, the last answer wins; with no successful answer, the value is `none`.
- wf exposes `agent.journal`, the absolute journal path. Cached journal events now include `model`, preserved from the successful result in the resume source. Cached answers retain model provenance but incur no new token usage. Failed attempts and unused shadow answers do not replace the answering family.
- New `C/stages/<stage>.json` receipts contain `{stage, status, wall_s, gpu_s, usd, model_family, notes}`, plus any stage-provided v1 overrides and measured token counts. Stage/status/model families use their existing enums. `notes` is an array with either no entries or the single fixed code `multiple_model_families`; no model text, prompts, filenames, or scientific facts are copied into it. These receipts are separate from `C/receipts/` box command receipts.
- Both serve and dev `lambda_serve.sh up` write `$HOME/.cache/metis-serve/box.json` atomically alongside `state.json`. Its keys are `{type, region, price_usd_h, started_utc}`: Lambda instance-type and region identifiers, a numeric hourly USD price, and a UTC ISO timestamp. Repeated state saves preserve the allocation's start. Confirmed `down` retains `box.json` and adds `ended_utc` (UTC ISO timestamp) and `hours` (nonnegative elapsed allocation hours, including startup and termination polling). State archival behavior is unchanged. The next `up` replaces this record for the new allocation.
- At the start of reproduce, the pipeline copies the current shared `box.json` to `C/box.json`, replacing any stale run copy. Missing box metadata leaves pricing unavailable and stage USD at zero. At takeaways, a matching allocation record can refresh the copy with its confirmed end; a different allocation never replaces the snapshot. If reproduce was skipped, takeaways snapshots the current allocation to account for any run overlap.
- Box receipts add numeric nonnegative `gpu_busy_s` and boolean `gpu_busy_known`. The detached remote script writes `<receipt-id>.gpu` beside its log, sampling `nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader,nounits` immediately and every 2 seconds until the command exits or times out. Each finite utilization sample in [0,100] contributes `utilization / 100 * 2` seconds; samples from every GPU are summed. Missing/invalid samples contribute nothing. No valid samples means `gpu_busy_s=0`, `gpu_busy_known=false`. Telemetry collection failure does not change command/fetch success. Sampling survives loss of the local polling process; the remote runner stops sampling before publishing its exit marker.
- Stage v1 `gpu_s` sums its box receipts' `gpu_busy_s`, including failed commands and retries. For stages with box receipts, `facts.gpu_busy_known` is true only when every receipt has valid busy telemetry; partial telemetry contributes its measured values while the flag stays false. Harness profile timing remains separate evidence and never substitutes for receipt GPU accounting. This supersedes the earlier statement that reproduce/profile always leave this flag false.
- Stage v1 `usd` is `sum(its box receipts' wall_s) / 3600 * C/box.json.price_usd_h`, including uploads, probes, failed commands, polling/fetch time, and retries. Stage `wall_s` remains elapsed stage time and includes agent calls. No allocation or model-call envelopes are added.
- Takeaways facts optionally add `run_box_usd`, a finite nonnegative number or null; old v2 records without this key remain valid. The pipeline writes null for a SKIPPED takeaways stage; otherwise it writes the whole run's box charge here: the intersection of `[run start, takeaways accounting time]` with `[box.started_utc, box.ended_utc]`, multiplied by hourly price. An active box uses accounting time as its end. When timestamps or price are unavailable, it falls back to summed stage USD. This is a run summary, not extra stage spend; takeaways v1 `usd` retains only its own command attribution.
- `OPERATOR_TAKEAWAY.md` now has a Compute section: one row per stage with existing gate columns plus `wall_s`, `gpu_s`, `usd`, `tokens_in`, `tokens_out`, `model_family`; a box table; and run totals. The optional Python API is now `takeaway(records, raid=None, box=None)`. The CLI reads only validated signatures and sibling `C/box.json`; it does not read agent content. Run USD uses `facts.run_box_usd` when present, avoiding double-counting stage attribution; other totals preserve the existing launch/model-call preference and stage fallback.
- Operator box output whitelists only `type` and `price_usd_h`. Price must be a finite nonnegative JSON number (never a boolean); unavailable price renders `null`. Type is a fixed enum: `gpu_1x_a10`, `gpu_1x_a100`, `gpu_1x_a100_sxm4`, `gpu_1x_a100_sxm4_80gb`, `gpu_8x_a100`, `gpu_8x_a100_80gb_sxm4`, `gpu_1x_h100_pcie`, `gpu_1x_h100_sxm5`, `gpu_8x_h100_sxm5`, `gpu_1x_gh200`, `gpu_1x_h200`, `gpu_8x_h200_sxm5`, `gpu_1x_b200`, `gpu_8x_b200`, or `unknown`. Unknown types render `unknown`; region, timestamps, and all other box fields never enter operator output.
